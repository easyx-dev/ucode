# 输入方言（UCode Markdown）

输入框里写的、复制出来的、会话里回显的，是**同一份文本**——它是一份 Markdown，外加几条本项目的记号。
这份文本由 `@ucode/markdown` 解析成接口载荷（`command` / `skills` / `text` / `contexts` / `attachments`），
服务端只认载荷，不再从正文里去找 `/名字`。

## 命令与技能：容器围栏

````md
:::command[review]
看下 @src/auth.ts#L10-L40
:::

:::skill[pdf]
生成一份审查报告 PDF
:::
````

- 容器内容就是**参数**（可含引用、附件、列表、代码块），容器外的文本是**用户正文**。
- **命令最多一条**（本轮的主指令）；**技能可以写多条**，按出现顺序逐个注入；两者可以并存。
- 技能**不限条数**（只有一条很宽的健全性上限 32 条，防的是请求无界增长，正常用不到）；
  一条消息里带两条以上时，发送前给一次上下文占用提示（按清单里各技能正文的字节数估算，
  实测 marketplace 技能单份最大 75KB）。只提示，不阻断。
- 名字必须命中清单（命令来自 `prompts`，技能来自 `skills`），大小写敏感、最长 64 字符、不含空白。
- 容器**同级并列，不能嵌套**：容器里的收尾 `:::` 会先把外层关掉，嵌套写法会报 `容器里不能再写容器`。
- 围栏用三个以上冒号；里面要嵌一段带围栏的内容时，用更长的围栏包住短的。
- 行首三个以上冒号 + 别的名字（如 `:::note`）**不是本项目的语法**，原样保留——外部工具的自定义容器不会被判错。

手打 `/名字 参数` 也可以：命中清单时整段按上表处理（写成容器），这不是第二种语法，只是输入糖——
投递出去的文本里只有容器一种写法。留给客户端自己的名字（如 `/goal`）不走这条。

## 引用：`@路径`

| 写法 | 含义 |
| --- | --- |
| `@src/auth.ts` | 整个文件 |
| `@src/auth.ts#L10` | 第 10 行 |
| `@src/auth.ts#L10-L40` | 10–40 行 |
| `@src/auth.ts#L10-` | 10 行到文件尾 |
| `@docs/` | 目录清单（末尾斜杠） |
| `@[我的 笔记.md](我的 笔记.md#L1-L5)` | 路径含空白时 |

- 路径相对会话工作目录；写绝对路径或 `~/` 也行，但服务端只接受**工作目录内**的路径。
- 裸写法要求路径像个路径（含 `/` 或 `.`），并且 `@` 前不能紧挨着 ASCII 字母数字：`@用户名`、`foo@bar.com`
  都按普通文字处理，`看下@src/a.ts` 照算。要写真正的字面 `@` 用 `\@`。
- 同一个路径 + 同一段行范围出现多次时，引用内容只读一份，正文里两处标记都保留。
- **引用锚点**（`@<scheme>:<payload>`，如 `@design:<会话>/<页>/<节点>`）**不是**文件引用：
  哪些 scheme 算锚点由插件贡献声明（`ui.mentions`），宿主不认识任何一个具体 scheme。锚点的归属校验在
  插件侧做，解析时原样留在正文里、不进 `contexts`——否则发送时会去磁盘上找这个「文件」。

## 附件：标准图片语法 + `attachment:` scheme

```
![](attachment:image/<sha256>)
![季度报告.pdf](attachment:pdf/<sha256>)
```

- 类型由 mimeType 派生：`image` / `pdf` / `text` / `doc` / `sheet` / `slide` / `archive` / `audio` /
  `video` / `binary`。它只影响展示层的图标，正文里始终写全。
- id 是内容 sha256（64 位小写 hex）；**不接受 URL**（外链图片与 `attachment:https://…` 都不支持）。
- 图片本体走视觉通道，正文里的 `![](attachment:image/…)` 是位置标记；顺序即出现顺序。

## 为什么是这套记号

- **形状取自 remark-directive**（`:::name[label]`）：它不是本项目发明的语法，Markdown 生态里已有工具认识这个形状，
  而我们要的正是「外部工具能生成、纯文本工具能拼出来」。没自己造 `:::xxx` 变体，也没引入 MDX——
  MDX 的核心增量是可执行 JS / 组件，对我们全是负资产，而且 `<Command>` 与投递层的 `<command>` 撞名会让
  「用户写的命令」与「用户想发的字面标签」无法区分。
- **标记与投递层分开**：输入层是给人写的方言，投递层（模型看到的 `<command>` / `<skill>` / `<context>` 块）
  是安全边界，负责属性转义与同名标签中和。两层不共用记号，谁都不冒充谁。
- **附件用标准图片语法 + `attachment:` scheme**：外部渲染器不认识 scheme 时降级成一张裂图 + 可读文字，
  不会像自造记号那样整段消失。

## 多条技能怎么算

技能是**可叠加的参考指令**，不是被强制执行的流程：一条消息带多条时逐条注入，彼此冲突由模型自行裁决。
命令（最多一条）才是这一轮的主指令。

## 不解析的地方

行内代码 `` `@src/a.ts` ``、代码围栏（``` 或 ~~~）与行首四空格缩进块内的记号**一律是字面文字**。
`\` 可以让下一个字符变成字面（`\@`、`\!`、`\:`）；粘贴进来的文本默认按字面处理，需要它当语法时
显式去掉转义。

## 写错了会怎样

| 情形 | 表现 |
| --- | --- |
| 命令 / 技能名不存在 | 拦住发送并提示（消息不会变成普通文本悄悄发出去） |
| 一条消息写了两个 `:::command` | 拦住发送并提示 |
| 容器没有收尾 `:::` | 拦住发送并提示 |
| 容器里又写容器围栏 | 拦住发送并提示 |
| 附件 id 不合法 / 用了 URL | 按字面留着并提示，不拦发送 |
| 引用路径不存在或越界 | 服务端返回错误（客户端在发送前不读盘） |

## 与界面代码的对应

- 解析与还原：`packages/markdown`（`parseDialect` / `renderDialect` / `escapeDialect` / `docToDialect` / `entryToDoc`）。
- 输入框里那份文本：编辑器的文档是方言的视图（围栏与引用在编辑器里显示成芯片），发送、复制、编辑重发都走
  方言投影（`packages/ui/src/business/composer/document/dialect.ts`）；`:::` 菜单一步选到「哪条命令 / 技能」，
  写错的地方就地标红并给出原因。
- **草稿以编辑器文档为权威副本**（另有方言文本镜像）：文档里带着附件类型与显示名，只留文本会让回填丢芯片；
  镜像保证「只有文本的老草稿」也能还原出同一条命令。
- 回显与输入同形：对话列表里的用户气泡把技能 / 命令 chip 排在正文开头（技能按注入顺序、命令最后），
  与编辑器的 inline 芯片同一套顺序；两侧都靠服务端写的边界块认「这是哪条命令」。
- 会话条目里的形状（模型看到的那份）：[`session-entries.md`](./session-entries.md)。
