# 功能面归属分析

> **这是 v2 的输入材料，不是架构文档。** 它不改动 v1 的任何基准内容，只做一件事：把 ZCode 的功能面逐条判定"应该落在核心层、控制层、还是需要两者协作"。目的是回答"壳子能有多薄"以及"哪些功能迫使 v2 改动基准"。
>
> 事实来源为 ZCode 官方文档 27 页（`https://zcode.z.ai/cn/docs/`）的全量抓取，引用原文处以「」标出。

> **编号约定**：本目录的文件不带编号。正文里的「02 §2」「04 §7」等一律指 **v1 章节**（`docs/architecture/v1/`），数字命名空间专属于 v1。

## 结论摘要

1. **ZCode 的功能面里，没有任何一条智能体能力必须在桌面端。** 必须落在控制层的只有四类，且都不属于"智能体能力"：用户本机 GUI 与输入方式、**浏览器**、**通知**、连接引导所需的凭据。
2. **因此桌面壳的存在理由是"用户本机的 GUI 与本机资源"，不是智能体能力。** v1 的 ADR-011（Web 壳先行）仍成立，但需补一条职责划分——桌面壳不是"更完整的 Web 壳"，而是承担另一类职责的壳。
3. **v2 只需新增两条协议能力**：工作区文件/Git 结构化查询、PTY 字节流通道。两者 ZCode 都靠"桌面端即 agent 宿主"绕过了，ucode 分层后绕不过去。**浏览器与通知都已决定"不进协议"**——前者走既有的工具接入机制（桌面壳把浏览器包成本机工具提供者），后者由各控制层自理。因此 **v2 不需要"控制层能力调用"这一整个协议面，这是规模上最大的一处缩减**。
4. **ZCode 文档里一处未自洽之处现在有了答案**（见 §4.1）：远程工作区下「打开 localhost」指谁？答：浏览器属于桌面壳，所以指桌面端那台机器。语义自洽，不需要新协议面。
5. **"插件两者都要"带来一条新的安全规则**（见 §5.3）：来自市场的插件不得包含进程内代码。
6. **远程操作拆成两种形态，不照搬 ZCode 的"远程开发"**（见 §7）：**AI SSH**（目标机不装任何组件，AI 经 SSH 执行远端命令）与**远控**（桌面壳探测/安装/端口映射后接入远端核心层节点）。远控**不需要改动协议**——这是"控制层可以很薄"的直接证明。**Bot Channel 不做。**
7. **uhub 是一种附属能力：要用它提供的能力集就得登录**（见 [uhub 文档](uhub-服务端与B端私有部署.md)）。**登录的含义是「获得能力」而非「获得许可」**，所以组件与登录都是可选的，不登录时智能体完全按 v1 的模型运行。它提供的能力集是**开放的**：模型端点（免配置，安装 → 登录 → 可用）、企业知识库、内部数据服务，以后还会加。它同时是中继通路的提供者（异网远程控制），并可托管 Web 壳。**它引入第三种信任来源——远端权威的断言**，因此 04 的信任模型需要新增一类并定义合成规则。**扫码配对因此不做。**
8. **一条贯穿全文的架构原则：能力走工具层，协议 C 保持窄。** 已出现三个同类实例——桌面壳的浏览器、第三方 agent browser、uhub 的各类能力，**全部以「工具提供者 / MCP 服务」的形式接入，没有一个往协议 C 里加东西**。这条值得在 v2 里显式写下，因为它决定了后续每次加能力的成本。见 [uhub 文档 §2.5](uhub-服务端与B端私有部署.md)。

**一个反复出现的结构性收益**：AI SSH、远控、uhub 中继——**三次新增远程能力，协议 C 一行没改**。这是 v1 的分层（ADR-003：核心层不知道传输）在实际兑现。

## 一、判据

逐条问四个问题，第一个"是"决定归属：

| # | 问题 | 是 → 归属 |
|---|---|---|
| 1 | 是否需要**用户本机**的 GUI、显示、输入设备（拖拽、剪贴板、托盘、快捷键）？ | 控制层 |
| 2 | 是否需要**用户本机**的操作系统资源，而该资源无法从另一台机器取得（浏览器登录态、`~/.ssh/config`、OS 凭据存储、本机 Docker daemon）？ | 控制层（或控制层引导） |
| 3 | 是否需要与**代码所在环境**同处一台机器（工具执行、文件读写、PTY、语言服务）？ | 核心层 |
| 4 | 是否只是状态与逻辑（会话、调度、配置、扩展解析、统计）？ | 核心层 |

判据 2 是唯一会产生例外的：它是"用户的机器"与"代码的机器"第一次分离的地方。

## 三、需要新增的两条协议能力

这两条 ZCode 靠"桌面端即 agent 宿主"绕过了（终端、文件树全在本机），ucode 分层后必须显式定义。

### 1. 工作区文件/Git 结构化查询

控制层要渲染文件树、Git 图谱、变更筛选，但工作区在核心层那台机器上。现在协议 C 只有工具调用（`bash`、读写），没有结构化查询面。

**为什么不能用工具调用代替**：文件树需要增量刷新、Git 图谱需要分页加载（「加载更多提交」），用 `bash` 跑 `ls`/`git log` 来喂 UI 是把 UI 性能绑在命令解析上。

**这是 v1 的一个真实缺口**，也正好解释了 ZCode 的一个产品限制：Remote Control 里「手机能打开桌面端没开过的项目吗？不能」——因为没有这套查询面，控制层无法自己列出工作区。

### 2. PTY 字节流通道

终端仿真需要双向字节流 + 窗口尺寸变更 + 信号。不能塞进 JSON 消息面（base64 会毁掉交互式程序的体验）。

**归属**：PTY 在核心层（代码所在环境），控制层是终端仿真器。

---

**说明：原第 3 条「通知推送」已去掉。**

**决定：通知由各控制层自己实现。** 核心层不做通知的送达，也不因此新增协议能力。

但分工要写清，因为**通知的触发状态在核心层**：

| 职责 | 归属 |
|---|---|
| 把"有待决事项"作为**可查询的状态**暴露出来 | **核心层**（§5.6 的持久化待决交互） |
| 决定要不要通知、怎么通知（系统通知 / 移动端推送 / 浏览器通知） | **各控制层** |

**推论（各控制层必须自己解决的问题）**：控制层要能通知，就得保持某种形式的在场——断线期间核心层不会替它推送。所以"无人值守时把我叫醒"的实现方式是**控制层自己维持连接或周期性轮询**，而不是核心层主动找用户。

这条分工的收益：**核心层不需要知道用户在哪里、用什么设备**——与 v1 的"核心层不知道对端形态"（01 §3）一致，也与 ADR-003 一致。

## 四、三条例外

### 4.1 浏览器 —— 桌面端专属，不进协议

**决定：浏览器做成桌面端壳的专属能力。其他浏览器相关需求走第三方（agent browser 这类）。**

**这一决定消掉了 v2 最大的一处不确定性。** 原先列的方案 B/D 都要求新增"控制层能力调用"这一整个协议面（核心层反向调用控制层能力），那等于转向 ACP 的哲学（客户端持有环境），与 ucode 的选择相反。**现在不需要了。**

**做法：桌面壳把内置浏览器暴露成一个本机工具提供者**（MCP 服务器，或等价的本地工具接入方式），核心层把它当普通外部工具接入。

- **浏览器不进协议 C。** 它走的是 v1 已有的扩展机制（MCP / 工具接入）
- 于是"agent 驱动浏览器"不是一种新能力，而是一次普通的工具调用
- **其他浏览器方案**（网页抓取、多页自动化、更强的浏览器控制等）走**同一条路径**——替换成第三方 agent browser 即可，核心层不需要知道区别
- **内置浏览器是桌面端专属功能，其他控制端不考虑它**（已决）。所以它的边界不需要为"跨端一致"做裁剪，只由"桌面端需要什么"决定——**能力扩张交给第三方**
- 桌面壳因此只需做一件最小的事：一个用户能看见的浏览器面板，加一个把它包成工具提供者的适配层

**这顺手回答了 ZCode 没回答的问题。** ZCode 文档在此处不自洽：`remote-development` 页说进远程工作区后「文件读取、终端命令、Git 操作和 ZCode Agent 都在目标环境内执行」，而 `browser-use` 页说浏览器面板仅桌面端可用。那么远程工作区下「打开 localhost:3000」打开的是谁的 localhost？

ucode 的答案是：**浏览器属于桌面壳，所以 localhost 指桌面端那台机器。** 用户能听懂，不需要解释。若有人要访问远端节点上的服务，那是端口映射该做的事（§7.2）。

**它还让另一个遗留矛盾消失了**：登录态（Cookie/LocalStorage）天然在用户本机，而代码可能在别处——这个矛盾不需要靠新协议面解决，因为**浏览器不再声称自己代表"代码所在环境"**。它代表的是"你面前的这台机器"。语义自洽，代价是远程场景下浏览器测不到远端服务——这个代价用端口映射补。

**它同时是"核心层拥有环境"的例外，但例外被既有扩展点吸收掉了。** 见 §5.9 对 03 §1 措辞的修正。

### 4.2 用户本机 GUI 与输入方式

拖拽（从 Finder 拖入文件）、剪贴板（复制为 Markdown/CSV）、托盘、系统通知、快捷键录制、"用外部编辑器打开"、PDF 预览的翻页缩放。

这些**只能在控制层**，但它们都只是"把用户意图或本地资源转成协议输入"，协议已有的能力足够覆盖（附件、prompt 参数）。**不需要新协议面。**

**通知属于本类**，且已明确划归各控制层自己实现（§3 第 3 条）。系统通知、移动端推送、浏览器通知都是控制层宿主的事，核心层只暴露"有待决事项"这一状态。

**另外，浏览器也归入本类**（§4.1）——它由桌面壳持有，并通过已有的工具接入机制暴露给核心层，不进协议。

一个语义要明确：**"在资源管理器中打开"在远端场景下打开的是哪台机器？** 必须定为"控制层所在机器"（用户想看的是自己屏幕），而路径指的是核心层那台机器——两者不一致时应明确拒绝或给出提示，而不是静默打开一个错误的路径。

### 4.3 连接引导与本机凭据

建立到远端核心层的连接需要：读本机 `~/.ssh/config`、本机 OS 凭据存储、本机包管理能力。

ZCode 的答案是"这一步必须在桌面端完成"：「手机 Remote Control 不能新建或连接远程工作区」。**这是判据 2 的正确应用**——不是产品限制，是物理限制。ucode 的远控（§7.2）同样受此约束。

**但与 ZCode 有一个实质差别，且需要说清"关掉什么会失去什么"：**

- 若目标机端口可直接访问 → 引导完即无依赖，桌面壳可以关掉，其他控制层直连
- 若走**端口映射**（目标机端口未开放时的做法）→ **隧道本身就由桌面壳充当代理**。此时：

| 关掉什么 | 后果 |
|---|---|
| 关掉桌面壳 | **远端核心层继续跑**——会话、agent loop、无人值守任务都不受影响（这才是 §7.2 与 AI SSH 的本质区别） |
| 之后想重新接入 | **需要重建隧道**——原隧道随桌面壳一起消失 |

所以"引导完可以关掉引导方"这句话需要限定：**关掉的是运行依赖，不是接入依赖。** 远端节点的独立性体现在"它不因你离开而停止"，而不是"你可以从任何地方凭空连上它"。

ZCode 的处境更差一层：它的桌面端既是宿主又是隧道，所以关掉桌面壳等于**同时**失去运行与接入。ucode 只失去接入。

## 五、对 v1 基准的推论

以下每条都是 v2 变更集的候选内容。

### 5.1 临时会话（改 02 §2 的状态分类）

辅助对话「关闭标签页/主任务被删或归档/退出应用则无法恢复」「不进入任务列表，也不进入「最近关闭」」。v1 的会话全部持久且追加式，没有"故意不持久"这个类别。需要新增一类会话：存在但可丢弃、不进索引、不提供恢复。

### 5.2 逐轮文件改动集（改 02 §3）

ZCode 的"撤销文件改动"（全撤或全不撤）、"对话+文件重置"、"分叉不回滚磁盘文件"三条，说明**会话记录与工作区状态是两个独立的可回滚对象**。而且它承认终端命令造成的改动不可撤销——即**做不到完整覆盖，Git 是兜底**。

v1 的 02 §3 只描述记录的四条性质，完全没有记录与工作区状态的对应关系。这是需要新增的一节（或一条新不变量：**每轮的记录必须能对应该轮的文件改动集，且该对应关系在终端命令介入时明确失效**）。

### 5.3 插件"两者都要"带来一条新安全规则

清单式插件（JSON + Markdown + 子进程 hook）与进程内 TS 插件（pi extension）的能力不是同一套：

| | 清单式插件 | 进程内 TS 插件 |
|---|---|---|
| 能注册新工具 | 否 | **是**（`registerTool`） |
| 能注册模型供应商 | 否 | **是**（`registerProvider`） |
| 能订阅内部事件 | 仅子进程 hook 的 7 个事件 | pi 的 17 个事件 |
| 跨语言 | **是** | 否 |
| 能崩掉核心层 | 否（进程边界） | **是** |
| 能读核心层内存中的凭据 | 否 | **是** |

**能力分层**：清单式是分发默认形态（无代码，可跨语言，可兼容外部生态的 plugin/command/skill/hook 格式）；进程内 TS 是"需要注册新工具或供应商"时才用。

**新的安全规则**：ADR-007 的论证是"插件信任 = 文件系统所有权，隔离是假边界"——那个论证对**本地安装的清单式插件**成立（能写目录的人本就能改一切）。但**"来自市场的进程内 TS 插件"打破它**：插件作者不是那个能写你目录的人。所以需要一条新规则：

> **来自市场/远端的插件不得包含进程内代码。** 进程内 TS 插件只能来自本机显式安装或用户自建。

这条规则应写进 v2，并修订 ADR-006（从"插件即 pi extension"改为"清单式为主、进程内 TS 为可选高性能层"）。

### 5.4 自主级别是第二条权限轴（改 04 §2、§3）

v1 只有一条轴：信任级别由**绑定**决定。ZCode 的四档执行模式（变更前确认/自动编辑/计划模式/完全访问）+ 权限四选项（含「允许本会话」「始终允许本项目」）是另一条完全不同的轴：**agent 在本次会话里获得多少自主权**。

两者正交且都必须有。有效能力 = f(绑定信任, 会话自主级别, 逐工具规则)。

推论：v1 的"信任级别是绑定的属性"**仍然正确**，但 v2 需要新增第二条轴。两条轴的关系**不是能力取交集，而是一道门槛**——见 04 §三「低信任通路能驱动吗」：自主级别允许免批准执行时，只有"结构性等价于本机用户"或"已认证且有授权"的通路才能驱动该会话。

### 5.5 项目级作用域与第三个信任边界（改 02 §2、01 §4）

ZCode 的配置分用户级与工作区级，工作区级存在仓库里（`<项目>/.zcode/`，「跟着仓库走，不用单独复制」）。v1 的数据层是纯 host-local 单目录。

更要紧的是安全：ZCode 明说工作区 MCP **自动连接**，并警告「打开一个项目，就等于连上了它配置里写的所有 MCP 服务，而 MCP 服务能执行命令、读写你的文件、访问网络。所以打开来路不明的仓库之前，建议先看一眼它的 `.zcode/config.json`」。

它对此的处置是**把项目级 Hook 整体忽略**：「写在 `<workspace>/.zcode/config.json` 或 `<workspace>/zcode.json` 里的 hooks 配置在当前版本会被整体忽略（无论 `hooks.enabled` 是否为 true，日志中记为 `config_project_hooks_ignored`）」。但项目级 MCP 仍然自动连接——**同一份风险，两套处置**，这不一致。

v1 的两个信任边界都不覆盖这个情形：项目配置既不是"你自己的文件系统"（插件信任那条），也不是"网络可达性"（绑定信任那条）——它是**你刚 clone 的别人的代码**。需要第三条边界：**项目配置信任**。

#### 已决：项目级作用域不携带任何可执行内容

**项目配置只允许声明式内容，不允许携带可执行物**——Hook、命令、以及会自动连接的外部服务，一律不行。（Q-2）

这条让第三个信任边界**几乎不再需要设计**，因为：

| 项目配置能做的 | 风险 |
|---|---|
| **关**：关闭能力（如关闭知识库、关闭某个 MCP） | **无**。声明式的"关"不会执行任何东西 |
| **开**：携带 Hook / 命令 / 自动连接的外部服务 | **高**。它是"在你机器上执行、用你的凭据"，不是配置，是**以你的身份运行他人的代码** |

所以规则很简单：**项目级只减不增。** 它能关，不能开。

**与 ZCode 的差别**：它把项目级 Hook 禁掉、项目级 MCP 却自动连接；ucode 一刀切——**两者都不允许**。理由就是上表第二行：自动连接的外部服务同样是在你机器上跑、用你的凭据。代价是团队无法通过仓库共享一份"这个项目该连哪些 MCP"，改用组织级分发（uhub 能力或插件）解决。

### 5.6 无人值守运行（改 03 §6、04 §4，最大的一处）

闲时任务原文：「单次执行有时长上限，到点后任务会回到队列，下次接着原来的会话继续，不会从头再来。应用重启也不会丢」；「**权限确认不算接管**」（无人值守期间点批准/拒绝仍在免费通道内）。

这要求：会话在没有 attachment 的情况下持续运行数小时；一条权限请求可以被**延后应答**而不中断会话；核心层重启后能恢复。

v1 现在写的是"无 attachment 时按降级策略拒绝，绝不无限阻塞"。防死锁的理由没错，但它假设了"必然有个客户端在等"。**无人值守推翻了这个前提。**

正确的形态不是"等"，而是**持久化的待决交互**：

- 请求写入数据层，会话进入等待态并**释放运行资源**
- 任何人、任何设备、任何时间应答后恢复
- 重启后待决请求仍在

这与"绝不无限阻塞"**不矛盾**：不阻塞指的是不占着资源干等，而不是必须立刻拒绝。

连带：ZCode 的"提问超时 5 分钟自动继续"是同一机制的另一端——**超时后的策略应该是"降级为 agent 自决"而不是只有"拒绝"一种**。v1 的降级策略表需要重写。

### 5.7 节点注册表与多后端（新概念）

远控要求控制层能记住并接入**多个核心层节点**（本机、若干远端），每个节点有地址、认证凭据、显示名。

v1 里没有这个层次：attachment 是"挂到某个核心层实例的某个会话上"，而"有哪些核心层实例、怎么连"完全在协议之外。远控把这个缺失暴露出来了。

形态上这是 OpenHands Agent Canvas 的 backend switcher（显示名 + host URL + API key）那类做法。归属：**控制层侧的本地状态**（存在控制层的配置里，不是数据层的），因为它是"这台机器上的壳认识哪些节点"，而不是任何单个节点的数据。

### 5.8 节点身份认证（新要求）

远控的探测环节有一个安全问题：**探测到一个端口上有服务，怎么知道它是 ucode 核心层，而不是一个等着收凭据的假冒服务？**

必须先验证节点身份，再交出任何凭据。这要求核心层能以一种**可验证的方式自述身份**，而 v1 的握手（`hello`/`welcome` + `capabilities`）目前是"双方互报版本与能力"，没有身份验证。需要补充。

同时探测阶段本身需要一个**建立协议连接之前**的轻量端点（"这个端口上是什么服务、协议版本多少"），否则探测只能靠猜端口。

### 5.9 03 §1 措辞修正：内置工具 vs 通过 MCP 接入的工具（改 03 §1）

v1 的 03 §1 写的是「工具在**核心层所在主机上**实际执行」。浏览器决定（§4.1）让这句话的问题显形了：**通过 MCP 接入的工具本来就可以在别处执行**——这是 MCP 的常规用法（远程 HTTP/SSE 服务器），v1 也一直把 MCP 当作扩展点。

所以需要把这句话拆成两半：

- **核心层的内置工具**（读写编辑、bash、搜索）在核心层所在主机执行
- **通过 MCP 或等价机制接入的工具**在提供方所在处执行，核心层不假设其位置

这不是原则的破口，而是**原本就该有的区分**——只是浏览器把它变得显眼了。浏览器正是"由别处提供、在别处执行"的一个具体实例。

### 5.10 不需要改的

以下 v1 结论经功能面对照后**依然成立**：

- 三面划分（命令/事件/交互）——ZCode 的权限请求、提问、通知全部落在这三面里
- 依赖方向与包边界
- 数据层的七条不变量（逐轮文件改动集是在其上新增，不是修改）
- "不采用 pi 的 experimental 协议"
- 记录采用追加式树结构
- 两个版本独立演进

## 六、headless 核心层能做而 ZCode 做不到的

这一节是**选择 v1 架构的收益清单**，也是 v2 可以对外主张的差异点。

| 能力 | ZCode | ucode 的形态 |
|---|---|---|
| 手机接管时不依赖桌面端在线 | 「远控期间桌面端需要保持运行和联网」 | 核心层 headless 常驻，手机直连 |
| 多设备同时操作同一会话 | 「同一时间只支持一个手机页面连接」 | 多 attachment，无并发上限（受 owner 语义约束的是写，不是看） |
| 控制层可打开任意已登记项目 | 「手机能打开桌面端没开过的项目吗？不能」 | 核心层提供工作区查询面（§3.1），不再受"桌面端已打开"限制 |
| 定时任务不受"电脑唤醒"限制 | 「电脑必须唤醒…错过的一次性任务记为跳过而不是补跑」 | 核心层常驻即可，只要机器开机 |
| 控制层接入任意核心层节点 | 远端只是 runtime，桌面端每次转发 | 隧道建好后控制层用标准协议直连；**核心层不知道有隧道**（§7.2） |
| 换壳不换核心 | 无此概念 | 编辑器/移动/桌面/Web 都是同一核心层的壳 |
| 数据层可被外部工具读写 | 会话格式未文档化 | 协议 D 是公开规范 + 一致性测试套件 |
| 同机多实例隔离 | 无 | 多个核心层实例共享一个数据层，按 owner 语义分配会话 |
| 服务端部署（团队/CI 复用） | 无 headless，无 SDK | 核心层可独立安装运行 |

## 七、远程操作的形态：AI SSH 与远控

**本节替换原先照搬 ZCode"远程开发"的做法。**（设计由项目方给出，不是从 ZCode 文档归纳的）

两种形态的用户可见表现相似——"我坐在这台机器前，AI 在另一台机器上干活"——但数据层位置、凭据归属、离线可运行性**完全不同**，必须分开设计，不能合成一个功能。

### 7.1 AI SSH —— 一种能力

**形态**：已登记的 SSH 连接可以被引用。写完一个项目，说一句"部署到测试环境"，并 @ 选取一个已登记的连接，agent 就在那条连接上执行部署命令。

**关键约束：目标机器上不安装任何 ucode 组件。**

#### 定位：能力，不是模式

**AI SSH 是一种能力（以工具形式暴露），不是"执行后端"，也不是一种模式。**（项目方定位）

这个差别的实质在这里：

| | 当作"执行后端" | 当作"能力"（本项目定位） |
|---|---|---|
| 默认工具在哪执行 | 可能被整体切到远端 | **仍在核心层主机**（03 §1 不变） |
| 远端离线时的影响 | 该会话的工具全部失败 | **只有这一个能力不可用**，本机工具与会话照常 |
| 与逐轮文件改动集（§5.2）的关系 | 冲突面扩大到所有工具 | 冲突只限 AI SSH 自己发起的改动 |
| 与 §2.5 原则的关系 | 是个例外 | **是"能力走工具层"的又一个实例** |

pi 的 `ssh.ts` 扩展样例（"delegate all tools to a remote machine over SSH"）是把**所有**工具重定向到远端，属上表左列；ucode 取右列。

#### 两个必要的构件

1. **SSH 连接登记表** —— 命名的连接（名称、主机、端口、用户、凭据引用）。凭据不进数据层明文（用 OS 凭据存储，或数据层的凭据类别并标注不进同步）；登记表本身属数据层的"配置"类别。
2. **引用机制** —— 用户可 @ 选取一个已登记连接，把"用这个连接"作为本次请求的约束。**协议 C 的 `prompt` 因此需要一个引用参数**，可引用对象至少包括：文件/文件夹、会话、**已登记的连接**、技能/子智能体。（ZCode 的 @ 支持文件/文件夹/技能/智能体，ucode 多一个"连接"。）

#### 两条实现路径

| | (a) 每命令一个 SSH 连接 | (b) 常驻 PTY over SSH |
|---|---|---|
| 状态 | 无状态，每条命令独立 | 有状态，`cd`、环境变量、交互式程序可用 |
| 文件操作 | 需另走 SFTP（不能用 shell 往返） | 同样需 SFTP |
| 控制台视图 | 只能回显命令与输出 | **真终端** |
| 复用 | — | **复用 §3.2 的 PTY 通道** |

推荐 **(b)**。理由：需求里的"SSH 控制台"本身就是一个终端，而 §3.2 已经需要 PTY 通道——两者是**同一条通道的两个使用者**，不是两套机制。走 (b) 还顺带覆盖"AI 与用户在同一个远端 shell 里交替操作"这个场景。

#### 能力边界（必须写清，否则用户会误期待）

- **远端离线 → 只有这个能力不可用**，本机工具与会话照常（这是"能力"定位相对于"执行后端"的实质收益）
- **经 AI SSH 产生的远端改动不可撤销**——远端没有我们的改动记录，只能靠远端自己的 Git
- **不做远端配置同步**——远端没有 ucode 组件，没有配置要同步

### 7.2 远控

**形态**：**桌面端壳专属能力**。SSH 连上后**先探测目标机是否已安装 agent 核心服务**；没有则安装；然后**桌面壳直接接入那个服务**；端口未开放时用**端口映射**打通。

**为什么不叫"远程开发"**：ZCode 的叫法暗示"这不只是控制，还是开发环境"。这里的实质是**接入一个远程节点**，与"开发"无关。名字会误导用户对能力边界的预期。

**架构归属：远控不进协议。** 这是它最重要的性质：

> 探测、安装、端口映射**全部是控制层宿主的本地行为**——它们需要本机凭据、本机 ssh 客户端、本机包管理能力。隧道一旦建好，控制层就用**标准协议 C** 连上去。对核心层而言，这是一个普通的 WebSocket 或 unix socket 连接，**它不知道自己是本机还是穿过隧道的。**

这句话就是「**控制层可以很薄**」的直接证明，也是 v1 ADR-003（核心层不知道传输）的实际收益：**v2 不需要为远控改动协议。**

远控只要求两件 v1 没有的东西，两者都在控制层侧：**节点注册表**（§5.7）与**节点身份认证**（§5.8）。

**与 AI SSH 的本质区别——本机关掉之后会怎样**：

在远控下，会话记录在**远端的数据层**，模型调用在**远端**（凭据在远端），本机只是显示。**所以本机可以关掉，远端继续跑。** AI SSH 则相反：本机关掉，一切停止。

这个区别也是判定一个功能该归给哪种形态的依据。

**远端节点的凭据归属（已决）**：远端是**常驻的独立节点，自带数据层与凭据**。依据是"探测是否已安装"这个设计——否则不需要探测（每次都由桌面端启动它即可）。

这条推论消掉了 ZCode 的"远端配置同步"（同步 Skill/MCP/Plugin 到远端）：配置跟着数据层走，远端有自己的一套，没有东西要同步。

#### 隧道接入不需要额外认证（已决）

**项目方判断**：既然能直接 SSH 到那台远端，就已经具备它的最大权限（能装任何东西、读任何文件、改任何配置），没必要再对核心层做一次认证，**直接调用即可**。

这个判断可以落到 v1 **已有的判据**上，不需要新增机制：

**远控隧道的连接，在核心层看来就是「来自环回」——而"只监听 loopback 就等于结构性等价于本机用户"这条 v1 判据正好覆盖它。** 因为能建立那条 SSH 隧道的人，必须已经能在该机执行命令；这正是 `implicit` / `local` 这两档所依据的东西。

| | 远控通路 |
|---|---|
| 认证发生在哪 | **SSH 层**（SSH 登录本身） |
| 核心层要做什么 | **什么都不用做**——连接来自环回，按已有判据给权 |
| 前提 | 核心层**只监听环回**，隧道由 SSH 提供（不监听公网端口） |
| 需要新协议能力 | **无** |

**与 uhub 的认证闭环不冲突**：两条通路各用各的认证，且各自足够——远控靠 SSH，uhub 靠登录。区别在于 SSH 是一次点对点的、你已经拥有的凭据，而 uhub 是组织级的、需要网络可达的第三方。

**由此 §5.8「节点身份认证」的范围要收窄**：它只服务 **uhub 通路**（确认对端是哪个 uhub 及其身份载荷），**不服务远控**——远控不需要核心层做任何身份判断。

**其余接入方式**：需求里说"多种使用方式，一个是 SSH 连接后…"。WSL、Docker、或其他任何能建立隧道的方式都遵循同一模式（探测 → 必要时安装 → 端口映射 → 标准协议接入），差别只在"怎么打通那条隧道"。**这些都在控制层，核心层与协议对它们一无所知。**

### 7.3 两种形态对照

用于指导 UI 表述与文档措辞——用户必须能一眼看出当前处于哪种模式。

| | AI SSH | 远控 |
|---|---|---|
| 目标机安装 ucode 组件 | **否** | 是（探测到没有才装） |
| 核心层位置 | 本机 | 目标机 |
| 数据层位置 | 本机 | 目标机 |
| 模型凭据位置 | 本机 | 目标机 |
| **本机关闭后** | **全部停止** | **远端继续跑** |
| 目标机离线后 | 工具失败，会话仍在本机可用 | 连不上，会话在远端不动 |
| 归属层 | 核心层（**一种能力**，以工具形式暴露） | 控制层（桌面壳本地能力） |
| 受 v1 哪条约束 | "核心层拥有环境"的延伸（工具在别处执行） | 数据层 per-host 不变量（远端是独立 host） |
| 认证发生在哪 | 本机 SSH 凭据（AI SSH 每次连接都要） | **SSH 层；核心层不需要再认证一次**（§7.2） |
| 需要新协议能力 | PTY 通道（走 (b) 时，与 §3.2 同一条） | **无**（只需控制层侧的节点注册表） |

### 7.4 三种形态并存时的"套娃"

三种通路（AI SSH、远控、uhub 中继）都能把"另一台机器"变得可用，于是同一个核心层可能有多条接入路径。项目方指出这看起来像套娃——**不是错觉，但要区分三种情形，它们各需不同的规则。**

#### 情形一：同一核心层的多条接入路径

**先纠正一处先前写错的地方**：本节最初把"远控隧道"与"uhub 中继"列成两条**并列可选**的路，还建议"中继排最后（避免走第三方节点）"。**那是错的**，而且与 uhub §4.4 已经定下的结论自相矛盾——

> **uhub 的中继就是在远程操作服务层。web 能做什么，它就能做什么。** 它不是一条"次一等的、能不走就不走"的路径，**它就是远程操作的正常形态**。

远控与中继**不是并列关系，是先后关系**：远控是**纳管动作**，uhub 中继是**纳管之后的常态通路**（uhub §4.4）。机器一旦纳入组织，远程操作就经 uhub——不该再需要 SSH，也不该把经 uhub 当作需要回避的事。

**所以真正的"路径优先级"只剩两档，且都不是在取舍中继**：

| 情形 | 走哪条 | 理由 |
|---|---|---|
| 你就坐在这台机器前 | **环回 / stdio** | 根本不需要网络，与"回避中继"无关 |
| 你在同一局域网 | **局域网直连** | 少一次绕行，纯粹是省 |
| 你在别处 | **uhub 中继** | **这是远程操作的正常形态**；若组织没部署 uhub，则退回到远控隧道（那是唯一手段，见 uhub §4.4） |

**规则**：

- 核心层必须有**稳定身份（nodeId）**；控制层按身份去重，一个核心层在列表里只出现一次，**路径是它的属性而不是并列条目**
- 允许用户显式指定路径（诊断与排障），默认自动选最近的一档
- **不把"经 uhub"当作需要规避的状态**：它带来的额外一跳是远程操作的固有成本，不是缺陷

#### 情形二：uhub 部署在已纳管的节点自己身上

A 上跑 uhub，A 也跑核心层并登录这个 uhub。于是 A 的核心层出站连 A 上的 uhub，uhub 又把它转回 A 的核心层——环回。

技术上能工作，但很蠢（多一跳、零收益），而且会让信任判断出错（见下）。

**规则**：**本机到本机优先走环回，不经 uhub。**

#### 情形三：通路串联

远控隧道里套中继，或中继里套隧道。**这应当被禁止。**

**规则**：**每条连接只走一种通路，通路之间不串联。**

例外是核心层自己的**出站**网络路径——例如核心层所在的机器连不上 uhub，需要经跳板机出网。那是它自己的网络环境问题，对控制层不可见，不影响本规则。

#### 顺带修掉的一个判据（重要）

套娃现象牵出一个真实的安全问题：**"只监听 loopback 就等于本地可信"这条 v1 判据，在中继下不成立。**

若 uhub 与核心层同机，客户端经 uhub 中继到核心层的连接，在核心层看来就是一条**来自环回**的连接。按 v1 的判据它会被判为"本地"，而它实际上是远程用户的流量。

**规则**：**中继来的连接必须由 uhub 显式标记为"经中继"，不得靠地址推断。** 换句话说，信任判断不能只看"从哪来"，还要看"这一跳是否被中继过"。这是 [uhub 文档 §3.1](uhub-服务端与B端私有部署.md) 第三类来源在实现上的第一个具体落点。
