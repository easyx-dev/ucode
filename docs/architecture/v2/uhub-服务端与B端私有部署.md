# uhub · 服务端与 B 端私有部署

> **这是 v2 的输入材料，不是架构文档。** 它不改动 v1 的任何基准内容。本设计由项目方给出，不是从 ZCode 文档归纳的。
>
> 相关：[功能面归属分析](功能面归属分析.md)（含 AI SSH 与远控，见其 §7）

## 组件命名

**`uhub`**（中文「枢纽」）。由我们自己开发，不是第三方组件。

命名理由：与 `ucode` 同前缀，命名空间一致；"hub" 表达**汇聚**——核心层向它汇聚、壳从它接入、能力由它提供，这三件事都是汇聚，与它实际做的吻合；短、好念、能直接出现在配置项与命令行里（`uhub login`、`--uhub https://...`）。

**不采用的名字与原因**（记录以免反复讨论）：`urelay` 只描述了转发职能，而它同时提供能力与认证；`ugate` / `ugateway` 会把注意力引向"门禁"，而登录的定位是**获得能力**而非获得许可（§2.1）；`ucenter` / `ubase` 暗示集中存储，与"会话数据留在各 host"（§4.1）直接冲突。

> **编号约定**：本目录的文件不带编号。正文里的「02 §2」「04 §7」等一律指 **v1 章节**（`docs/architecture/v1/`），数字命名空间专属于 v1。

## 零、一句话

**uhub 是一种附属能力：要用它提供的接口能力，就得登录。** 登录不是使用智能体的前提，而是**获得 uhub 那组能力**的凭据。

它提供的第一个能力是**模型端点**——用户不必自己配。对普通用户而言，价值就是**安装 → 登录 → 直接可用**，不必理解什么是 API Key、Base URL 和模型列表。此后它的能力集是**开放的**：企业知识库接入、内部数据服务接口，以及以后新增的各种接口能力。

**不登录时，v1 的模型完全不变**：核心层只监听本机、自己配模型端点、各个壳直连。

## 一、它是什么：一个外挂的能力与通路来源

v1 有四层：控制层 / 绑定层 / 核心层 / 数据层。**uhub 不属于其中任何一层——它不是层，是外挂。**

准确地说，它对核心层提供**两类东西**，而区分这两类是理解它的关键：

| 角色 | 提供什么 | 接入方式 | 架构后果 |
|---|---|---|---|
| **能力提供者** | 模型端点、企业知识库、内部数据服务…… | **走既有的工具/能力接入机制**（§2.5） | **不需要新协议能力** |
| **通路提供者** | 中继（异网可达） | 又一种绑定（§2.3） | 不需要新协议能力，但需要新增信任与授权（§3.1） |

**所以"第五个组件"这个说法过重了。** 它更应该被看作**一类特殊的工具/能力提供者**，特殊之处只有三点：远端、需账号、且顺带提供中继。

| 层 | 有没有 agent loop | 有没有会话数据 | 面向谁 |
|---|---|---|---|
| 控制层 | 否 | 否 | 用户 |
| 绑定层 | 否 | 否 | （库，不是节点） |
| 核心层 | **有** | 经数据层读写 | 绑定 |
| 数据层 | 否 | **有** | 核心层 |
| **uhub** | 否 | **默认没有**（见 §4.1） | 核心层 + 控制层 + 管理员 |

按面看它长这样：

| 面 | 面向 | 职责 |
|---|---|---|
| **能力面** | 核心层 | 模型端点、知识库、数据服务等能力（§2.5 的接入原则） |
| **注册面** | 核心层 | 节点注册、身份签发、心跳、策略下发 |
| **接入面** | 控制层 | 登录、返回该用户可见的核心层与能力、（可选）托管 Web 壳 |
| **中继面** | 核心层 ↔ 控制层 | 数据面，转发流量 |
| **管理面** | 管理员 | 用户与席位、核心层准入、策略、用量 |

**控制面与数据面分开看**：身份、策略、能力在控制面（侧边）；中继流量在数据面（中间）。这个区分很重要，因为两者的可用性要求不同——控制面短时不可用时，已建立的中继不应立刻断掉。

## 二、登录后解锁的能力

### 2.1 登录（可选）与它解锁的能力集

**登录不是使用智能体的前提**，而是"要不要接入组织 uhub"的选择。

| 状态 | uhub 的能力集 | 中继（异网远程控制） |
|---|---|---|
| **未登录** | 全部不可用 | 不可用 |
| **已登录** | 按账号授权可用：模型端点、知识库、内部数据服务…… | 可用 |

**登录是"获得能力"，不是"获得许可"。** 这个区别在措辞上很小，在产品上很大：前者说的是"uhub 能给你什么"，后者说的是"uhub 允许你做什么"。可选登录的设计之所以成立，正是因为它按前者理解。

**这个设计消掉了一整类问题**：uhub 不再是使用前提，所以它的故障不会导致"组织内全部机器不可用"（见 §3.6）。**也消掉了"本机是否也要过门禁"这个问题**——没有门禁，只有开关；本机直连在任何情况下都可用。

**另一个容易被误读的点：不登录 ≠ 没有远程能力。** 不登录时仍然可以：

- **AI SSH**：经已登记的 SSH 连接执行远端命令，它是一种**能力**而非模式（01 §7.1）
- **远控**：桌面壳自己探测/安装/端口映射（01 §7.2）

这两条都不依赖 uhub，靠的是你自己的 SSH 与网络手段。**uhub 的价值在于"你没有 SSH 通路、但有一个组织账号"的场景**——它让你不需要任何网络配置就能跨网接入。

### 2.2 模型端点：可选由 uhub 提供

形态上这是标准做法：**uhub 暴露一个 OpenAI / Anthropic 兼容端点**；已登录时可以选择使用它，也可以继续用自己的端点。

**关键：权威性是逐模型的，不是全局的。** 这是原先"接管"说法需要修正的最重要一处：

| 模型来源 | 配置由谁权威 | 凭据在哪 |
|---|---|---|
| **uhub 提供的模型** | **uhub**（本地改动会在下次同步被覆盖） | uhub（不下发到本机） |
| **用户自配的模型** | **本地**（用户说了算） | 本地数据层 |

两者可以共存：一台核心层可以同时挂着 uhub 下发的模型和自己配置的模型。

**逐模型权威是必需的**，否则"未登录只能自配端点"这条不成立——如果登录后 uhub 把整份模型配置接管掉，用户自配的模型会被清掉。

**ZCode 有完全对应的先例**，而且它必须专门写一句话来解释，说明这是真实的用户困惑点：「编程套餐内置模型由 uhub 统一下发，本地改会在下次同步恢复官方值」，并明确提示「**这是有意设计，不是配置丢失**」。它的作用域也是逐模型的——「只有用 API Key 方式添加的模型才允许自己改」。ucode 在 uhub 提供的模型上会遇到同一个问题，需要同样的提示，否则用户会当 bug 报。

**这个能力的首要价值是免配置，不是企业治理。** 普通用户安装 → 登录 → 直接可用，不必理解 API Key、Base URL、模型列表这些概念。对 B 端而言第二位的价值才是**模型 key 只在 uhub，不下发到员工机器**。

这也是为什么模型端点是 uhub 的**第一个**能力：它把新用户旅程里最容易卡住的一步（配模型）变成了零步。

### 2.3 中继：流量经 uhub 转发

uhub 的中继职能一句话概括：**认证 → 转发**。经 uhub 转发的流量，uhub 在这条路径上，因此它**能看到、也能随时切断**。这两点后面会很省事。

#### 认证闭环

**不存在不过 uhub 认证的接入路径**——要经它转发，就得先过它的认证。

项目方强调的"认证闭环"，在**只有转发这一种形式**时是最强的形态：通路只有一条，而那条通路就是 uhub 本身，没有任何旁路可言。

#### 一个核心只绑定一个 uhub（已决）

好处是三处：

- 认证与授权**只有一个判定点**，不存在两个权威冲突时的仲裁问题
- 本机开关保持为**单一的二值开关**（若允许多个，开关就得变成列表，"关了没关干净"的判断也随之复杂化）
- 换组织的语义清晰：解绑旧的、绑定新的

代价是"一台机器不能同时服务两个组织"。**若确有这个需求**（例如外包人员同时接入甲方与乙方），v1 已经支持**多个核心层实例共享一个数据层**——起两个实例、分别绑定两个 uhub 即可，数据层仍是同一份，会话仍可互相看见。

#### 打洞已评估并放弃（已决）

**项目方决定：P2P 打洞不做，过于复杂，收益低。**

评估结论记录在此，以免将来重新讨论：

| 打洞能带来的 | 代价 |
|---|---|
| 延迟更低（少一跳） | 需要引入 UDP 系传输（TCP 打洞不可靠），等于给协议 C 再添一条传输 |
| uhub 不承载业务流量 | 需要地址观测、候选交换、一次性令牌、失败判定与回退——一整套 STUN/TURN/ICE 式的机制 |
| | 对**对称型 NAT** 无效；移动网络与多数企业网络经常失败。业界的常见量级是**一到两成连接仍需回退中继**——也就是说**这套机制只为一小部分连接服务** |
| | 打洞成功后 uhub **无法切断、无法审计**，撤销只能落到核心层侧自检（这是我们评估时发现的一处真实缺口） |

**关键判断：打洞是纯优化，不是功能。**

转发的唯一前提是"核心层能连上 uhub"——而这本来就是绑定的前提。所以去掉打洞**不丢失任何功能**，只是放弃了"少一跳"这个性能收益。为一小部分连接引入一整套机制加一条新传输，性价比不成立，这就是放弃它的理由。

**复评条件**（若出现下列情形，值得重新评估）：跨地域的托管部署叠加大量终端交互，使那一跳的延迟变得明显；或 uhub 的带宽成为瓶颈或成本项。

#### 端到端加密：暂不考虑，但保留一条设计约束

**项目方决定：端到端加密暂时不考虑。**

后果需要记明：uhub 在转发路径上，因此**它能看到全部会话内容**；被攻破时可读可改，而不只是阻断。这是当前设计已知并接受的暴露面。

**但有一条设计约束应当保留：uhub 只按「通道」转发不透明字节，不解析协议 C。**

理由：这条约束的成本几乎是零——uhub 本来只需要知道"这个客户端要连哪台核心层"，那是连接级元数据，不需要看协议内容。但它**保住了将来加端到端加密的可能性**。反过来，若 uhub 现在就开始解析协议 C（例如为了按会话或按消息做路由），那么以后要加端到端加密就不是"加一层加密"，而是重写 uhub。

**所以：加密暂不做，"不解析"这条留下。**

#### 转发面

| 转发对象 | 说明 |
|---|---|
| 已登录的核心层（服务层） | 控制层 ↔ 核心层的协议 C 流量。对核心层而言这就是一条普通连接 |
| **Web 壳** | uhub 托管的 Web 端（§2.4），浏览器打开 uhub 网址并登录即用 |

#### 与 v1 的关系：中继是一条新的绑定

协议 C 与传输无关（ADR-003），所以中继不需要改协议——它只是又一种"拿到一条到核心层的字节通道"的方式。这与远控的结论一致（01 §7.2）：**远控和中继都不改协议，都只是把远程连接变成一条本地连接。**

#### 中继必须覆盖全部通道

包括 01 §3 那两条新能力（工作区文件/Git 查询、PTY 字节流）。**通道类型从设计一开始就是一等概念**，不是"先转发 JSON 消息、字节流以后再补"——否则中继模式下终端与文件树会失效。已决，见 §4.3。

### 2.4 Web 壳托管（可选，但顺理成章）

「uhub 网址打开并登录后，也可以直接以 web 网页形式进行连接控制」——即 uhub 可以托管 `shells/web`。

**这对 v1 的 ADR-011（Web 壳先行）是个强支持**：Web 壳不只是协议验证载体，它还是 B 端部署的一个交付形态（浏览器打开即可用，无需装客户端）。**这条加强了我原先"Web 壳先做"的建议**，而且理由从"技术上便于验证协议"升级为"它是 B 端的一个产品形态"。

### 2.5 能力接入的统一原则：能力走工具层，协议 C 保持窄

**这是本文最重要的一条架构结论。**

uhub 的能力集是开放的（模型端点、知识库、内部数据服务、以后的新接口）。**如果每加一个能力就往协议 C 里加一种消息，协议会迅速膨胀，而且每次新增都要动核心层。**

正确做法是：**uhub 把能力以「工具提供者 / MCP 服务」的形式暴露，核心层按普通外部工具接入。**

| uhub 能力 | 接入形式 |
|---|---|
| 模型端点 | 模型供应商配置（**特例**，因为它是驱动 agent 的东西而不是 agent 用的工具，见 §2.2） |
| 企业知识库 | MCP 服务 / 工具提供者 |
| 内部数据服务接口 | MCP 服务 / 工具提供者 |
| 以后新增的接口能力 | 同上 |

**这条原则已经出现三个同类实例**，形状完全一样：

| 能力的来源 | 接入方式 |
|---|---|
| 桌面壳的内置浏览器（01 §4.1） | 桌面壳把它包成本机工具提供者 |
| 第三方 agent browser 等（01 §4.1） | MCP 服务 |
| **uhub 的各类能力** | **MCP 服务 / 工具提供者** |

**推论：协议 C 保持窄。** 它只承载会话、事件、交互，外加两条通道（工作区文件/Git 查询、PTY 字节流，见 01 §3）。**能力的扩张一律发生在工具层，不发生在协议层。** 这条值得在 v2 里显式写下，因为它决定了后续每一次加能力的成本——写下来之后，"加能力"这件事就默认不需要架构讨论。

**两个要处理的技术点**：

1. **凭据传递**：uhub 签发的账号凭据如何交给 MCP 客户端。远程类型（HTTP/SSE）本身有 OAuth 授权流程（ZCode 文档里有完整描述：`打开授权` 按钮、用系统浏览器授权、授权未完成时只把该服务标记为失败而不拖住整个会话）；本地 stdio 类型仍走环境变量。
2. **能力目录与开关**：登录后应能知道"这台 uhub 提供哪些能力""哪些对我可用"。这属于 uhub 与访问层，不进协议 C。

   **关闭的落点在项目级**（已决）：**可以在项目中显式关闭这些能力**——例如关闭知识库、关闭 MCP。这条同时说明项目级配置至少承担"**关**"这一职责，见 [待定总表](待定总表.md) Q-2。

**知识库 = MCP 服务**（已决）。所以它是"工具"形态：**模型自己决定何时检索**，不是每轮自动注入。

**这个决定的含义要记住**：将来若要做"问公司的事它就该知道、不该我去触发检索"那种体验，**那不是 MCP 能给的**，而是另一个机制（上下文注入）。届时需要单独设计，并处理上下文预算问题——ZCode 有同类先例可参考：技能元数据共享固定预算、超预算时降级为只保留名称（文档明确说"自动触发率会明显下降"），Memory 索引加载也有大小上限。**预算耗尽后的注入降级是静默的，用户只会觉得"它变笨了"**，所以真做的话降级行为必须显式设计。现在记为"不在 v2 范围"。

**一条隐私含义**：知识库若由 uhub 执行检索，uhub 会看到查询内容以及相关的代码上下文。私有部署下企业自己拥有 uhub，这不构成问题；托管部署下需要向用户说明。

## 三、与 v1 基准的冲突面

逐条列出，每条都是 v2 变更集的候选。

### 3.1 中继带来的真正变化：认证发生的位置变了（改 04 §2）

#### 与 SSH 的差别在哪里

"中继就像在远程一样"这个直觉是对的，但它同时暗示了一处不同——**认证发生在哪里**：

| | SSH | uhub 中继 |
|---|---|---|
| 认证在哪发生 | **在目标机上**（`authorized_keys` 在目标机） | **在 uhub 上** |
| 目标机要信谁 | **不用信任何人** | **必须信 uhub 的断言** |
| 凭据泄露的影响面 | 取决于那把钥匙被授权到哪些机器 | uhub 账号能到达哪些机器 |

所以差别不是"中继更不安全"，而是**信任链变长了**：目标机多了一个必须信任的第三方。

#### 因此：能力完全对等，不做降级

**本机 web 与桌面端能做的，透过 uhub 照样能做。没有分级。**（项目方定）

这不是"选择宽松"，而是两个理由的结论：

1. 对中继连接降级会得出荒谬结论——你从手机登录自己的账号访问自己的机器，权限低于一个未经认证的本地进程。对照 SSH 就很清楚。
2. **本机没有做二次限制的立足点。** 把机器注册到 uhub 这个动作**本身就是一次显式的授权声明**——"我同意这台机器由组织纳管"。授权发生在注册那一刻；之后在本机再加一道门，等于对同一个已做出的决定要求第二次同意。

#### 风险归位：uhub 必须自己承担的五件事

**uhub 被攻破是 uhub 的问题，不是本机权限模型的问题。** 因此它必须自己承担：

| # | 责任 | 说明 |
|---|---|---|
| 1 | **认证强度** | 账号、令牌、二次验证 |
| 2 | **密钥与凭据管理** | 断言签名密钥的存储与轮换 |
| 3 | **授权粒度** | 至少节点级；理想还要操作级（"能连这台机器但只能看"） |
| 4 | **审计** | 谁、从哪台设备、连了哪台机器、做了什么（§3.5） |
| 5 | **快速撤销** | 手机丢了、员工离职，必须立刻切断该身份的全部通路 |

**第 5 条在「通路与全权等价」的前提下尤其重要**：既然不再有本机的二次拦截，撤销就必须快且彻底。这是待定项 §2.3「绑定的生命周期」的实际内容，也是 uhub 值得优先设计的一块。

**注意责任 5 与本机开关的分工**：快速撤销是**已开启中继的机器**需要的；本机开关是**根本不想参与**的机器用的。两者不重叠——前者面向「已经接受依赖、但要能及时收回」，后者面向「不接受依赖」。

#### 本机的退出机制：关闭中继

机器的主人如果不想接受"信 uhub"这个依赖，有一个**本机开关：关闭「允许经 uhub 转发」**。关掉后那台机器彻底不经 uhub 可达。

**它不是缓解措施，是退出机制**——要么整套接受并给全权，要么不参与，没有"关一半"的中间状态。（权限降级的做法已否决，理由见 04 §三。）

**开关与"使用 uhub 的能力"是两件事，方向相反**：

| | 方向 | 开关 |
|---|---|---|
| 使用 uhub 提供的能力（模型端点、知识库……） | **出站**：核心层主动调用 uhub | 登录即有 |
| 允许经 uhub 被接入 | **入站**：uhub 把外部客户端流量转给你 | **独立开关** |

所以关闭中继**不影响**继续使用 uhub 的模型端点等能力。用户可以"只用 uhub 的模型与知识库，但不让 uhub 连进来"。

**默认值（建议）：默认关闭，由用户显式开启。** 理由是"开了就代表你愿意被中继"这句话只有在"开启是刻意动作"时才成立。代价是远程接入需要多一步。无论取哪个默认值，开关都要容易找到、状态显眼可查——不能让用户处于"不知道自己可以被远程接入"的状态。

#### 中继服务侧的策略（与本机开关互不干涉）

中继服务能做的事都在**它自己的策略**里，不触碰任何机器的开关：

| 中继服务能做的 | 效果 |
|---|---|
| 切断某条已建立的中继 | 断开那台机器当前的中继会话 |
| 不允许某个用户使用中继 | 该账号无法经中继接入任何节点 |
| 整体关闭中继功能 | 中继服务不再转发任何流量 |
| IP 白名单 | 限制可接入的来源地址 |

**这些都不是"强制某台机器开启中继"**——那件事中继服务做不到，也不需要做。本机只有开与关：**开了代表你愿意被中继，不开代表你不愿意，此时中继怎么都连不上。**

**机制上的保证**：核心层不对外开放入站端口，中继服务与它之间唯一可能的通路是**核心层自己发起的那条出站连接**。关闭中继即关掉这条连接上的中继用途——所以"连不上"不是拒绝的结果，而是**没有通道**。

**由此，本机开关与"使用 uhub 的能力"也是独立的**：前者是入站，后者是出站（见上表）。关闭中继的机器仍然可以正常使用 uhub 的模型端点与知识库。

**关闭后仍可能被远程接入**：AI SSH 与远控是别的通路，与 uhub 无关。要真正不被远程接入，还得管住那些通路。

#### v1 的信任矩阵继续管什么

它管**没有身份的通路**（stdio / unix socket / 本机 loopback，以及监听非环回的裸 HTTP/WS）。详见 04 §三——那里也写明了为什么"信任级别"这个名字容易误导：**它不是分级，是认证的替代品。**

**一处此前写错、现已撤销的要求**：本文档先前要求"连接必须显式标记是否经中继"。理由不成立——中继是**核心层自己发起的出站连接**，核心层天生知道那条通道是什么，不存在误判为本机用户的可能。判断依据只需要一个：**这条通路是否已完成身份认证。**

#### 通道即身份：核心层不需要判断"对端是不是 uhub"

**这是本节最省事的一处结论，它砍掉了一整套本来以为必需的机制。**

核心层与 uhub 之间的通道是**核心层自己发起的**：它 dial 到配置好的 uhub 地址，走 TLS，**证书校验就完成了"对端确实是 uhub"这件事**。这和浏览器访问一个 https 站点是同一件事，不需要第二套机制。

于是两个方向各归各法：

| 方向 | 谁认谁 | 靠什么 |
|---|---|---|
| uhub 认核心层 | uhub 认核心层 | 核心层提交**节点注册凭据**，uhub 校验——普通凭据校验 |
| **核心层认 uhub** | 核心层认 uhub | **"是我自己 dial 到配置地址 + TLS 证书校验"**——不需要任何额外机制 |
| 身份断言的传递 | —— | 在那条**已建立的 TLS 通道内**，因此**不需要签名** |

**核心层对断言所需的处理只有一件：记下"这条 attachment 属于谁"**，用于交互路由（04 §5）与审计。它不需要验证、不需要公钥、不需要轮换。

##### 为什么要砍掉"签名断言"

先前这里写的是"uhub 签发断言，核心层用 uhub 的公钥验签，还要处理公钥分发、密钥标识与双密钥轮换"。**那是错的**，两条理由：

1. **它防的是一个在这个拓扑里不存在的威胁**：断言在传递途中被第三方篡改。而这里传递途中没有第三方——就是核心层与 uhub 之间的 TLS。
2. **它对真正的威胁毫无用处**：uhub 被攻破或被内部人员作恶时，它签的断言就是它自己的谎话——**签名者就是 uhub，签名挡不住签名者**。

（顺带说明：真正能缓解那个风险的是端到端加密，而**签名从来不是**。见 §2.3。）

##### 一条可以复用的原则

> **核心层主动 dial 到配置地址 + TLS ⇒ 通道本身就是身份，不需要第二套信任机制。**

这条原则到今天已经砍掉三次多余的机制，值得单独记下，以后遇到"核心层怎么知道对端是某某"这类提议，先拿它对一遍：

1. **"是否经中继"标记** —— 通道是核心层自己开的，它天生知道那是什么（04 §三）
2. **打洞取消后"没有通道"的表述** —— 只有一条出站通路，无旁路可谈（§2.3）
3. **断言签名与公钥轮换** —— 通道即身份（本节）

#### 仍然要定义的两件事

1. **身份断言的形态** —— 连接级一次性给出，还是**按 attachment 逐条给出**？建议后者：v1 已有 attachment 概念（一次挂载 = 一台设备的一次接入），而交互路由现在按身份分，把身份绑到 attachment 上正好对上，且天然回答"哪个用户、哪台设备"。

   注意它现在只是**信息性载荷**，不涉及可验证性——上节已说明为什么不需要签名。

2. **审计要求** —— 经中继的每条连接至少要能回答"谁、从哪台设备、连了哪台机器、做了什么"。

   **这件事在砍掉签名之后反而更重要了**：身份的可信度完全来自"那条通道是核心层自己 dial 的"，没有任何密码学产物可供事后核对，所以**记录就是唯一的追溯手段**。建议两侧都记——uhub 记接入（谁连了谁），核心层记操作（在这台机器上做了什么），用 attachment id 做关联键。B 端几乎必然要求（§3.5），字段要在设计时就留。

### 3.2 认证与 TLS 从"推迟"变成"必做"（改 04 §7、07 不做清单）

v1 写的：
- 「无认证不得监听非 loopback」——即没有认证能力时只能监听本机
- 「v1 不做 TLS」，「远程场景依赖 TLS + 认证，打包在后续版本」

uhub 模式**就是**那个"后续版本"，而且它是远程认证本身。所以：

- 04 §7 的约束在 uhub 模式下由"uhub 承担认证"来满足
- **TLS 在 uhub 模式下是必需的**（控制层↔uhub、核心层↔uhub 两条链路）
- 07 的"不做 TLS 与远程认证"要移到 v2 的做

另外需要明确：**核心层与 uhub 之间是否也必须 TLS？** 在 B 端私有部署里，uhub 可能在内网、核心层在员工机器上——这条链路的暴露面取决于部署拓扑，建议默认加密。

### 3.3 凭据的分类要扩（改 02 §2、§8）

v1 的 02 §8 用一句话处理凭据：「凭据与其余状态同处数据层目录，因为是这台机器的智能体状态；但标注不进同步」。

登录引入后，凭据分成四类，归属与生命周期都不同：

| 类别 | 归属 | 已登录 | 未登录 |
|---|---|---|---|
| **自配模型凭据** | 数据层 | 保留（自配模型仍可用） | **必需** |
| **uhub 模型凭据** | **uhub** | 由 uhub 持有，不下发到本机 | 不适用 |
| **节点注册凭据** | 数据层 | **新增**。证明"这台核心层属于哪个组织" | 不适用 |
| **用户登录凭据** | 控制层 | 由各控制层自管（账号密码 / 令牌） | 不适用 |

**节点注册凭据是新增的一条**，其安全要求高于模型 key：模型 key 泄露是花钱，节点凭据泄露是"别人可以冒充一台核心层接进你的组织"。

### 3.4 多用户与授权（改 07 不做清单，但改动范围比原先设想的小得多）

07 写着"v1 不做：多租户 / 多用户——数据层是单用户目录模型，凭据是单用户凭据"。

登录引入账号，所以这一条被推翻。**但"登录可选"把推翻的范围限定住了**：

> **v1 的"数据层是单用户目录模型"依旧成立。** 新增的是**访问路径上的授权层**，不是多租户数据模型。

这个区别很实质：数据层不需要加 tenant 概念、不需要按用户隔离数据、02 几乎不用动。要新建的是"谁能在什么条件下连到哪台核心层"，它属于 uhub 与访问路径，与数据层正交。

仍然需要定义的东西（都在访问层）：

- **账号与身份**（属于 uhub）
- **核心层准入**（哪台机器可以注册进组织）
- **用户 → 核心层的授权映射**（谁能连哪台）
- **会话的可见性**：远程接入的用户 A 能看到 OS 用户 B 的多少东西？

最后一条仍然存在，但它**不是多租户问题**：一台核心层的数据层属于**那台机器的 OS 用户**，远程接入者是**访客**。所以问题是"访客能看到主人的哪些东西"，是**授权粒度**问题，而不是"数据属于谁"的问题。这比多租户好解得多。

### 3.5 审计与合规从"待业务输入"变成"当务之急"（07 §5 第 5 项）

07 的待业务输入里有一条"是否有合规/审计要求：审计日志、操作追溯、凭据轮换"。**B 端私有部署几乎必然要求这些**，而且现在它有了具体的落点：

- 谁在什么时候通过 uhub 连了哪台核心层
- 谁批准了哪次高权限操作
- 模型调用用量（B 端要计费/配额）
- 会话记录的可追溯性（员工离职后能否回收）

**最后一条是本节最重的一问**，见 §4.1。

### 3.6 可用性语义（比原先设想的小得多）

因为登录是可选的，uhub 不是使用前提，**"uhub 挂掉导致组织内全部机器不可用"这个风险不存在**——这是可选登录带来的最大好处。

#### 职权边界：uhub 关的是通道，不是 agent

这处需要写得很准，因为它决定了"账号被停"到底会发生什么。

**账号停了 = 中继中断，仅此而已。** 它关掉的是**远程操作的连接通道**，**不是 agent 服务**。

> **uhub 只能管自己的。它无法干涉用户的 agent 服务层。**

推论很干净：

| 发生了什么 | 后果 |
|---|---|
| 账号被停 / 凭据失效 | 中继通道关闭，**远程接入断开** |
| agent 正在跑的任务 | **不受影响，继续跑**。它的数据层在自己机器上，模型配置也在自己这里 |
| agent 用的是**自己配置的模型** | **完全没有影响** |
| agent 正在调用的是 **uhub 提供的能力**（模型端点、知识库、MCP） | 那些**调用会失败**——被 uhub 拒绝了 |

最后一行的性质要说清：**这不是"uhub 关掉了 agent"，而是"agent 调用某个外部服务时失败了"**——与调用任何外部服务失败没有区别。agent 不会因此进入什么"降级状态"，它只是遇到一次失败的调用。

**所以不需要设计"降级为未登录状态"这种东西**——agent 没有"登录状态"可言；有状态的只是那条中继通道。

#### 封禁 / 冻结 / 撤销：就是让通道不可用（已决）

**项目方定**：通道断了，**在中继时返回「通道已断开」这个错误即可**。用户封禁、用户冻结就是这种逻辑——**通道无法使用**；agent 调用经通道的模型会报错、调 MCP 也会报错。

这条把原先的待定项 Q-5 整个解掉了，因为它说明**不需要任何"通知机制"**：

| 我原先设想的三选一 | 为什么不需要 |
|---|---|
| 凭据带有效期、到期续期失败 | 不需要靠"到期"来发现——**用时就会失败** |
| uhub 主动推"你被撤销了" | 不需要推送——**没有需要同步的状态** |
| 核心层定期自检"我还在册吗" | 不需要自检——**它不需要"得知"，只需要"用不了"** |

**关键判断：通道不可用是一条普通的运行时错误，不是一次状态变更。**

这与 §3.6 上一节是同一个道理的两面：uhub 关的是通道、不是 agent；而 agent 也不需要"被告知"通道关了——它调用时自然会拿到错误。**准入与撤销因此是同一个动作的两面**：允许建立通道 / 让通道不可用。

**剩下的不是架构问题，是 uhub 侧的策略配置设计**：谁、能对哪些节点建立通道（那张准入表怎么配、怎么管）。这属于产品与 uhub 自身的实现，不再有架构上的未知。

#### 仍然要定义的一件事

**已建立的中继不应因控制面短时抖动而断开**（这是 §1 把控制面/数据面分开的理由）。以及一个更重要的推论：**已登录的机器不应因为控制面暂时不可达而拒绝本地使用**——否则一次网络抖动就让员工无法工作，而这是完全可避免的。

## 四、四个具体问题

### 4.1 会话数据留在各 host —— 已决

这一功能描述里只涉及**登录、模型端点、中继**三件事，**没有说会话数据集中**。所以按字面理解：

- 会话数据仍在各 host 的数据层（v1 的 per-host 不变量**保持不变**）
- uhub 只是让"跨网络访问别人的机器"变得可行
- 「用户 A 通过 uhub 连到机器 B，看到的是机器 B 上的会话」——数据没搬家

这个理解保持了 v1 最核心的一条不变量。**但 B 端客户很可能提出相反的要求**：

| B 端常见诉求 | 与 per-host 数据的冲突 |
|---|---|
| 会话集中存储、随时可查 | 冲突。需要会话同步到 uhub 或改用中心存储 |
| 员工离职后回收其机器上的会话 | 冲突。会话在员工机器上 |
| 审计所有操作内容（不只是"谁连了谁"） | 部分冲突。需要把内容也上报 |
| 换机即恢复全部历史 | 冲突，除非有同步 |

**这是 uhub 模式下最关键的一个决策**，因为选择"集中"会把数据层从 per-host 变成中心化，v1 的 02 几乎要重写（跨机共享数据层正是 07 明确列为 v1 不做的事）。

**已决（项目方）：会话数据留在各 host。**

这条决定的价值要写清，因为它保住了 v1 最核心的一条不变量：

- 数据层仍是 **per-host** 的，02 不需要为 uhub 重写
- 「用户 A 通过 uhub 连到机器 B，看到的是机器 B 上的会话」——数据没搬家
- §3.4 的"多用户影响限定在访问层"因此成立

上表那些 B 端诉求如果将来真的提出来，属于**独立的后续能力**，不要混进 v2——因为一旦选择集中，数据层就从 per-host 变成中心化，02 几乎要重写。

### 4.2 强制模式 —— 先不做，实现路径已明确

**项目方决定：强制模式可以有，但先不做，留说明。**

原先这一问源于"必须登录才能用"。改成**可选登录**后，没有门禁，只有开关：本机直连在任何情况下都可用。

#### 实现路径（项目方给出）

**强制模式不需要独立的策略开关，可以在模型配置那里实现**：开启该模式后，模型配置**只能使用 uhub 提供的模型**。

这个思路很省事，因为"不登录 → 没有可用模型 → 智能体实际不可用"这一条**自然就构成强制**，核心层不需要新增任何门禁逻辑。

需要注意它的性质：

- 这是**策略层面的强制，不是密码学强制**。本地有配置写权限的人能绕过——但如果本地配置由组织统一下发/管理，实际足够
- 一旦启用，§3.6 的可用性语义要重新审视：uhub 不可达时，未登录状态将意味着"没有模型"，即无法工作。**这个代价是启用该模式的客户自己选择的**，应写进部署文档
- 与 §2.2 的"权威性逐模型"配合：强制模式下，模型来源白名单里只剩 uhub 来源

**v2 的动作**：不实现，但在 02 §10（待业务输入）里记一条说明，避免将来重新推导。

#### 另需注意：管控口径随可选登录改变

B 端无法靠"强制登录"实现"员工必须走组织通道"。可选登录下这是预期的——要管控就用上面的强制模式，并且清楚它的代价。

### 4.3 中继覆盖全部通道 —— 已决

**已决（项目方）：中继覆盖全部通道。**

含义：**通道类型从设计一开始就是一等概念**，不是"先转发 JSON 消息、字节流以后再补"。否则中继模式下终端（PTY 字节流）与文件树（工作区文件/Git 查询）会失效——而这两条正是 01 §3 新增的协议能力。

这条要进实现规范：**中继的通道模型必须能承载 01 §3 的全部两条通道**，且新增通道时不需要重新设计中继。

### 4.4 uhub 与"远控"是什么关系

**原先的写法（"是否保留远控"）问错了问题。** 它们不是竞争关系，是**先后关系**。

#### 两者各自解决什么

| | 远控（01 §7.2） | uhub 中继 |
|---|---|---|
| 前提 | 你有那台机器的 SSH 凭据 | 你有 uhub 账号，且那台机器已注册 |
| 认证发生在哪 | **SSH 层；核心层不需要再认证一次**（01 §7.2） | **uhub 登录**（核心层只需记下身份，见 §3.1） |
| 需要在目标机装核心层 | 是 | 是（可由 uhub 分发安装包） |
| 网络要求 | SSH 可达；端口未开需端口映射 | **无**（核心层出站长连接） |
| 依赖组织设施 | **无** | 需要 uhub 存在 |
| 适用 | 这台机器归我管，但还没纳入组织 | 组织内统一纳管 |

#### 正确的关系：纳管动作 vs 常态通路

- **远控是"纳管动作"**：把一台还没纳入组织的机器变成"能连的"——探测、安装、打通网络
- **uhub 中继是"纳管之后的常态通路"**：机器已经在组织里了，之后连它不该再需要 SSH

所以两者都要有，且顺序固定：

```
一台新机器
  → 远控（或直接装上核心层）→ 纳入组织
  → 此后一律走 uhub 中继，不再需要 SSH
```

**这个先后关系必须写进用户文档**，否则会出现"我已经有 uhub 了，为什么还要 SSH"的困惑。

#### 推论：uhub 应当分发核心层的安装包

既然远控要做的是"探测 → 装 → 打通"，而 uhub 本来就要给核心层下发策略与模型配置，那么**由 uhub 提供安装包/脚本**是顺理成章的：省掉从本机向远端传输的过程，也保证版本一致。

ZCode 有现成做法可参考：远端资源下载有两条路径——「本地下载后上传」（经 SFTP 传到远端，远端全程无需联网）与「远端服务器下载」（远端需能访问 CDN，且具备 curl/wget、tar、sha256sum 等）。**ucode 可以只做后者**，因为远端通常能访问 uhub 本身。

#### 什么情况下仍然必须用远控

- 目标机还没纳入组织，且没有任何 uhub 通路
- 组织根本没有部署 uhub（此时远控是唯一的远程手段）
- 临时在一台机器上做事，不想把它纳入组织

## 五、三种远程形态的总对照

| | AI SSH | 远控 | uhub 中继 |
|---|---|---|---|
| 出处 | 01 §7.1 | 01 §7.2 | 本文 §2.3 |
| 目标机装 ucode | 否 | 是（探测后装） | 是（注册进组织） |
| 核心层位置 | 本机 | 目标机 | 目标机 |
| 数据层位置 | 本机 | 目标机 | **目标机（§4.1）** |
| 模型凭据位置 | 本机 | 目标机 | 目标机（自配）或 uhub（用其端点时） |
| 网络要求 | SSH 可达 | SSH 可达 + 端口或映射 | **无** |
| 身份来源 | 本机 SSH 凭据 | 本机 SSH 凭据 | **uhub 账号 + 节点注册凭据** |
| 可跨组织纳管 | 否 | 否 | **是** |
| 本机关闭后 | 停止 | 远端继续 | 远端继续 |
| 需要新协议能力 | PTY（复用 01 §3.2） | 无 | 无（中继是又一种绑定） |

**三者都不改协议。** 这是 v1 分层设计（ADR-003：核心层不知道传输）的实际收益——三次新增远程能力，协议 C 一行没动。

> **唯一在册的待定清单是 [待定总表](待定总表.md)——目前 0 条。** 本文件相关的三条（原 §3.1 身份载荷与审计、原 §2.3 绑定生命周期与准入撤销、原 §2.5 能力目录）均已关闭：身份载荷与审计降为实现级设计，准入与撤销已明确为「让通道不可用」，能力开关的落点在项目级。
