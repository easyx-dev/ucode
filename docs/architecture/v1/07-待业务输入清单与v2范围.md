# 07 · 待业务输入清单与 v2 范围

**这份文档是 v2 讨论的输入清单。** 左侧是 v1 已经定死的东西，右侧是需要业务决策才能填的东西。

## 一、v1 的边界

### v1 交付

| 层 | 交付物 |
|---|---|
| 数据层 | 协议 D 规范 + `store` 参考实现 + 一致性测试套件 |
| 核心层 | 协议 C 服务端 + pi agent loop + pi extension 运行时（从数据层加载插件与资源） |
| 绑定层 | `stdio` / `rpc`（unix socket）/ `http`+SSE / `ws` 四种绑定 + 信任矩阵 |
| 控制层 | **仅 Web 壳**，作为协议验证载体 |

### v1 明确不做

| 不做 | 理由 | 何时做 |
|---|---|---|
| 跨机共享数据层 | 数据层"唯一"是 **per-host 不变量**。跨机共享要把凭据抽出数据层、要解决网络 FS 上的锁（或改为服务端存储），是把整个拓扑复杂度提一个台阶 | 需业务证明有需求 |
| 多租户 / 多用户 | 数据层是单用户目录模型，凭据是单用户凭据 | 同上 |
| 插件隔离 | 插件信任 = 文件系统所有权，隔离是假边界（01 §4） | 需要"安装不受信任的第三方插件"时 |
| 插件市场 | pi packages 已经提供了分发机制（`pi install npm:...` / `git:...` / `./local`），自建市场是重复 | 需要审核/评级/商业化时 |
| TLS 与远程认证 | v1 只监听 loopback（04 §7）；非 loopback 且无认证配置则拒绝启动 | v2 的远程能力 |
| TUI / 桌面 / App 壳 | 只做 Web 壳验证协议。三种壳的交互模型差异大，在协议未验证前做它们是浪费 | 协议稳定后按需 |
| 复用 pi 的 experimental CBOR 协议 | 明确标注 experimental、source-only（不进 npm bundle）、协议层无认证、无重连重放、无兼容承诺（ADR-009） | 它稳定之后可重新评估 |
| 会话保留策略 | 属于业务策略（保留多久、是否自动清理） | §2 |

## 二、待定决策

> **P-1 ~ P-4 全部已关闭**，各自的结论见下。**唯一在册的待定清单在 [待定总表](../v2/待定总表.md)，目前 0 条**——待定项散在多处曾导致口径反复不一致，从该表起以它为准。
>
> **另有一类事未完成**：`06` 的 4 条技术假设待验证（缺的是事实，不是输入）。

### P-1 数据层格式是否做成 pi agent-dir 布局的超集

> **仍在册**，编号为 [待定总表](../v2/待定总表.md) 的 **Q-1**。

**当前倾向：是。** 附录 B 的目录布局参考已按此写（`settings.json` / `models.json` / `auth.json` / `AGENTS.md` / `SYSTEM.md` / `extensions/` / `skills/` / `prompts/` / `themes/` / `sessions/` 及会话文件的路径转义规则，全部沿用 pi 的 agent-dir 约定）。注意附录 B **属实现级**——直接改即可，但 02 §2 的状态分类本身不预设任何具体文件名，所以 P-1 的结论落地时不需要改基准。

**支持**：`PI_CODING_AGENT_DIR=~/.ucode` 就能让 pi CLI 与整个 pi 扩展/技能/package 生态直接读写 ucode 的数据层。这是"选 pi 作基座"能拿到的最大杠杆——用户的 pi 配置、插件、技能零成本迁移，ucode 也能直接消费 pi 生态的 5687 个包（数量为 pi.dev 包仓库自报）。

**代价**：继承 pi 会话格式的演进。pi 已经经历 v1 → v2 → v3 三次会话格式迁移（已验证事实），未来还会有。每次迁移我们都要跟。

**被否方案**：自有命名空间（数据层目录里用 `ucode/` 子目录）。换取格式自主权，代价是与 pi 生态完全隔离——用户要为 ucode 单独维护一套配置与插件。

**需要什么输入**：业务上是否允许"ucode 只是 pi 的一个宿主"这个定位。若 ucode 的产品定位需要与 pi 解耦（例如将来要支持别的 agent 内核），选自有命名空间。

---

### P-2 插件运行时：内嵌 pi extension 运行时 vs 自建

> **已关闭。** 结论：**两者都要**——清单式（JSON + Markdown，跨语言子进程 hook）为分发默认形态，进程内 TS 为可选高性能层。并由此新增一条安全规则：**来自市场/远端的插件不得包含进程内代码**（因为 ADR-007 的"插件信任 = 文件系统所有权"对"插件作者不是那个人"的情形不成立）。见 01 §5.3 与 [待定总表](../v2/待定总表.md)。

**当前倾向：内嵌。** 见 ADR-006。

**支持**：工作量是适配而非实现。pi 的扩展面已经覆盖了需要的一切（工具注册、命令注册、事件订阅、扩展间总线、jiti 免编译加载、packages 分发），且 `extensions/` `skills/` `prompts/` `themes/` 四类资源正好对应数据层布局。

**代价**：受 pi 的 API 稳定性约束；`[假设 #4]` 不成立则此路不通。

**被否方案**：自建插件运行时。可控、能自定义生命周期与将来的隔离，代价是从零实现加载/卸载/依赖/事件总线，且与 pi 生态不互通。

**需要什么输入**：`[假设 #4]` 的验证结论（技术输入，不是业务输入）。若验证通过则此决策可直接定案。

---

### P-3 凭据的位置

> **已关闭。** 其触发条件是"是否要做跨机共享数据层或目录同步"，该条件已答：**不做**（会话数据留在各 host，见 uhub §4.1）。所以凭据不必抽出数据层，v1 的"同处数据层目录、标注不进同步"维持原样。另注：凭据在 v2 细分成了四类（自配模型凭据 / uhub 模型凭据 / 节点注册凭据 / 用户登录凭据），见 uhub §3.3。

**当前状态**：凭据与其余状态同处数据层目录，但标注"不进同步"（02 §8）。

**待定内容**：v1 只需标注边界。但一旦要做跨机共享数据层或目录同步，凭据必须抽出——或者改用系统钥匙串（macOS Keychain 等）。

**需要什么输入**：是否要做跨机共享数据层（见 §1 的"不做"清单第一项）。

---

### P-4 无 attachment 时的降级策略是否可配

> **已关闭，且被 v2 的设计取代。** 无人值守已定为 v2 一等需求，但实现机制不是"把降级策略做成可配"，而是**持久化待决交互**：请求落进数据层、会话进入等待态并释放运行资源、任何人任何时间应答后恢复（01 §5.6）。另有"低信任通路能否驱动"的门槛约束自主级别（04 §三）。所以不再需要"预先授权的能力集合"这个概念。

**当前状态**：v1 默认策略 = 拒绝该操作并报告（04 §4）。

**待定内容**：是否允许用户配置成其他行为（例如"在 CI 场景下默认批准只读工具"）。

**被否方案**：默认放行、挂起等待、静默失败（三个都被否，理由见 04 §4）。

**需要什么输入**：是否有无人值守的运行场景（CI、定时任务）。若有，需要一个"预先授权的能力集合"概念——但这已经涉及安全模型，需要单独设计而不是加一个开关。

## 三、v2 允许增长的位置（扩展点）

**业务功能只在这些位置增长，不得新增层或改协议骨架。**

| 位置 | 能加什么 | 出处 |
|---|---|---|
| 数据层的插件目录 | 插件（pi extension），注册新工具、新命令、新事件处理 | 02 §2、03 §7 |
| 数据层的技能 / 提示词 / 主题目录 | 技能、提示词模板、主题 | 02 §2 |
| 配置与模型定义 | 新的配置键、新的模型供应商 schema | 02 §10 |
| 协议 C 命令面 | 新命令（**实现级**，可直接加） | 03 §4 |
| 协议 C 事件面 | 新事件类型（**实现级**） | 03 §5 |
| 协议 C 交互面 | 新方法（**实现级**，但交互面的两类划分属基准，不得合并） | 03 §6 |
| 绑定层 | 新绑定（**新增**一个包，不改既有绑定） | 04 §6 |
| 控制层 | 新壳子（**新增**一个包，不改核心层） | 05 §1 |
| 授予能力集合 | 新能力项、调整信任矩阵中的具体能力（矩阵的**存在性**属基准，具体能力项属实现级） | 04 §3 |

## 四、v2 改动基准级内容时要做的事

**注意：这一节不是"禁止改动"清单，而是"改动时需要记录"清单。** 业务需求压到基准级内容是 v2 的正常产出，不需要额外的正当性；需要的是留下记录，这样 v2 落地后能回答"变了哪里、为什么"（机制见 00 §v1 的冻结与变更追踪）。

改动下列内容时，进 v2 的「对 v1 的变更清单」（完整清单与出处见 00 §变更分级）：

- 四层的职责边界与"谁不知道谁存在"
- 两个信任边界正交（绑定信任 vs 插件信任）
- 数据层的形态、七条不变量、owner 语义、写入顺序
- 数据层文件兼作实例间的事件总线
- 两个版本独立演进、前向拒绝
- 协议 C 的三面划分与各面的语义不变量
- 信任级别是绑定的属性
- 交互承载能力按绑定声明、降级必须显式、路由按信任级别
- 无认证不得监听非 loopback
- 包边界与依赖方向

**反过来，附录 B 的全部内容**（具体文件名与格式、消息形状、命令清单、记录类型、分帧方式、包内文件划分、实施阶段）**属实现级**：直接改，不进变更集，也不构成对 v2 的约束。

**为什么要分这两类**：变更集是给人读的。把实现级改动混进去，真正重要的那些变动就会被淹没——**分级的主要作用不是给予自由，而是保持变更集的信噪比。**

## 五、v2 讨论需要的业务输入清单

按优先级排序，前两项决定 v2 的整体形态。

1. **核心使用场景是什么**：单人本地使用 / 团队协作 / 无人值守自动化？这决定是否需要多用户、是否需要跨机、决定 P-3 与 P-4。
2. **ucode 与 pi 的关系定位**：pi 的一个宿主（吃 pi 生态）还是独立的智能体产品（将来可能换内核）？这决定 P-1。
3. **壳子优先级**：v2 先做哪个壳（TUI 最省、桌面最重、App 需要远程能力）？这决定 v2 是否必须同时做 TLS + 认证。
4. **是否需要第三方开发者生态**：是否要对外开放 API、让第三方写插件或壳子？若是，协议 C 需要正式化（版本化文档、SDK、兼容承诺），这是 v1 里刻意没做的。
5. **是否有合规/审计要求**：审计日志、操作追溯、凭据轮换。当前设计里 `logs/` 有位置但没有规范。
6. **是否需要非 JS 实现**：若预期有 Go/Rust 的核心层实现，协议 D 的一致性测试套件需要提供多语言入口，协议 C 的 SDK 需要跨语言；这会显著增加 v1 的工作量，需要在 M1 之前决定。
