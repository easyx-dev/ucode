# 01 · 术语与分层边界

**级别：基准**（词汇表、两个信任边界正交的原则、四层职责边界；改动须记入变更集）

本章的词汇表属**基准**：后续所有讨论（包括 v2 的业务讨论）必须使用这里的词，不得引入同义词造成滑词。词汇表的改动要记入变更集——术语漂移是架构文档最难事后追溯的一类改动。

本章只定义**边界**，不定义实现。具体的消息形状、文件格式、命令清单等属附录 B（实现级）。

## 一、基准词汇表

| 术语 | 定义 |
|---|---|
| **数据层** | 一台机器上智能体全部持久状态的所在，形态是**一个目录**（默认 `~/.ucode`）。包含配置、模型定义、凭据、会话、插件与资源。一台机器一个。 |
| **核心层** | 智能体本体，**headless**。承担对话、agent loop、工具执行、插件运行时、人类交互中转。对外只暴露一套与传输无关的接口面。**核心层即服务层**——两者是同一件事，见下文说明。 |
| **绑定层** | 把核心层的接口面序列化到具体传输上的一层薄适配：分帧、寻址、流式。不含任何智能体逻辑。 |
| **控制层** | 绑定协议的具象化，即用户直接接触的壳子：TUI、桌面、Web、App。每个都是独立可安装的。 |
| **协议 D** | 数据层目录规范。面向任何核心层实现，可跨语言。 |
| **协议 C** | 核心层接口面。与传输无关。面向任何绑定层实现。 |
| **协议 B** | 各绑定自身的线格式。面向任何控制层实现。 |
| **attachment** | 一个控制层连接挂到某个会话上的那条挂载记录。一个会话可以有多个 attachment。 |
| **owner** | 某个会话当前的唯一写入者。一个会话同时只有一个 owner。 |
| **信任级别** | 某个绑定的对端可信程度。是**绑定的属性**，不是协议的属性。 |
| **授予能力** | 核心层按信任矩阵实际放行的能力集合（`grantedCapabilities`）。 |

### 关于"服务层"与"核心层"

两者指同一件事，本文档统一用**核心层**，因为"服务层"容易让人误以为它只是协议服务器，而实际上智能体的全部核心逻辑（对话、工具、插件）都在这里。早期讨论中使用过"服务层"，保留为别名以便检索。

**核心层是 headless 的**：它不渲染任何界面，也不假设对端是终端、浏览器还是桌面应用。

## 二、四层结构

```
控制层    TUI    Desktop    Web    App          ← 协议的具象化，各自独立可安装
─────────────────────────────────────────────
绑定层    stdio JSONL | JSON-RPC(uds/tcp) | HTTP+SSE | WebSocket
─────────────────────────────────────────────
核心层    对话 · agent loop · 工具执行 · skill · 插件(pi extension 运行时) · 人类交互中转
（服务层）  ↑ 对外只有一套与传输无关的接口面
─────────────────────────────────────────────
数据层    ~/.ucode 目录
```

三条必要的约束，是这套分层的全部意义所在：

1. **功能只在核心层**。绑定层和控制层不实现任何智能体逻辑。
2. **协议 C 定义一次**。绑定层只做序列化、传输、寻址。
3. **数据层可被独立实现**。协议 D 是规范，可跨语言实现，并有配套一致性测试套件。

## 三、谁不知道谁存在

这是本章最实用的一张表。实现时的每一个"要不要 import"的问题都由它回答。

| 组件 | **不知道**这些存在 | 原因 |
|---|---|---|
| 核心层 | 绑定层的任何一种传输（stdio、HTTP、WebSocket…） | 核心层只问"是否有可用的 UI 承载交互"（pi 的做法：`ctx.hasUI`），从不问"是哪种传输"。一旦核心层知道传输类型，新增一种绑定就要改核心。 |
| 核心层 | 控制层的任何形态 | 核心层不知道对端是终端还是浏览器。 |
| 绑定层 | 控制层的任何形态 | 绑定层只面对协议 C 的消息，不知道谁在另一端。 |
| 绑定层 | 其他绑定层 | 绑定之间不通信。跨绑定一致性由协议 C 的语义保证，不由绑定协商保证。 |
| 控制层 | 核心层的内部结构 | 控制层只面对协议 B。 |
| store | 核心层 | store 只实现协议 D，不 import 核心层。数据层可被任何实现消费。 |
| 核心层 | store 之外的任何持久化途径 | 核心层不得直接读写会话文件，一律经 store。 |

对应的依赖方向（详见 05）：

```
shells/*  →  client  →  bindings/*  →  core  →  store  →  data-layer-spec
```

严格单向。反向 import 由 `dependency-cruiser` 在 CI 中拦截。

## 四、两个正交的信任边界

**这是 v1 最容易搞错的一点。** ucode 里有两个完全不同的信任问题，机制不同、理由不同，不能混用一套方案。

### 边界一：绑定信任 —— 由网络可达性决定

- **性质**：临时。对端可能是攻击者。
- **机制**：认证 + 能力矩阵（见 04）。核心层强制执行。
- **为什么必要**：命令面里有 `bash` 和 `prompt`。`prompt` 会触发工具调用，也就是在服务主机上任意执行代码。所以任何可被非本机用户触达的绑定，都必须裁剪掉工具执行能力。

### 边界二：插件信任 —— 由文件系统所有权决定

- **性质**：持久。等价于登录用户身份。
- **机制**：**不需要机制**。
- **为什么**：插件放在数据层的插件目录里。能写这个目录的人本来就能改数据层里的一切——包括配置、模型定义、凭据，也包括直接改会话记录。在这种前提下做插件沙箱是**假边界**。

### 结论

两个边界正交，都要，但只有第一个需要设计。**v1 不做插件隔离**（ADR-007）。

推论：插件不需要权限提示，也不需要能力矩阵。绑定上的用户需要。

## 五、协议 D / C / B 的定位

| 协议 | 定义什么 | 面向谁实现 | 边界在哪 |
|---|---|---|---|
| **D** | 目录布局、文件格式、锁、原子写、版本规则 | 任何核心层实现（可跨语言） | 数据层目录的边界 |
| **C** | 命令面、事件面、交互面、握手、能力声明 | 任何绑定层实现 | 核心层进程的边界 |
| **B** | 分帧、寻址、流式、认证 | 任何控制层实现 | 每种绑定的对端边界 |

三者彼此独立演进：新增一种绑定不影响协议 D；数据层换实现不影响协议 C。这是 v1 能被 v2 定点增补的结构前提。

**为什么需要三个而不是一个**：如果把数据层格式混进核心层接口，数据层就无法被独立实现；如果把传输细节混进核心层接口，新增绑定就要改核心。pi 自己的实践印证了这条——它的核心只问 `ctx.hasUI`，而 stdio JSONL、SDK、实验性 CBOR 服务器是同一套核心的不同表面。

## 六、v1 的功能范围

| 层 | v1 交付 | 不在 v1 |
|---|---|---|
| 数据层 | 协议 D 规范 + 参考实现 + 一致性测试套件 | 跨机共享数据层 |
| 核心层 | 协议 C 服务端 + pi agent loop + pi extension 运行时（从数据层加载插件与资源） | 插件市场、插件隔离 |
| 绑定层 | stdio JSONL、JSON-RPC over unix socket、HTTP+SSE、WebSocket | 其他传输 |
| 控制层 | **仅 Web 壳**，作为协议验证载体 | TUI、桌面、App |

不做的完整清单与理由见 07。
