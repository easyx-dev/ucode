## ADR-001 数据层是一个目录，不是数据库

**决策**：数据层 = 一台机器上的一个目录（默认 `~/.ucode`），核心层以目录路径为入口参数。所有持久状态（配置、模型、凭据、会话、插件、资源）都在这个目录里。

**理由**：

1. **可被独立实现**。目录布局是规范，任何语言都能实现，并有配套一致性测试套件。用 SQLite 会把数据层锁死在 JS/SQL 生态。
2. **可检查**。可 grep、可备份、可人工审阅、可版本控制。事故排查成本远低于二进制文件。
3. **可移植**。整目录搬家即迁移，包含配置和插件，不需要导出/导入流程。
4. **业务扩展点天然**。`extensions/` `skills/` `prompts/` `themes/` 是目录，用户直接放文件即可，不需要数据库写入 API。

**被否方案：SQLite 作为数据层真相。**

否掉的原因不是"SQLite 不好"，而是它解决的正是我们愿意自己承担的问题：跨进程锁与跨进程 ID 分配。SQLite 的 `BEGIN IMMEDIATE` 事务可以优雅地同时解决这两件事（这也正是 pi 的 `pi-durable` 明确缺失的能力）。真正否掉它的理由是**前两条**——协议化与可检查性。一个二进制文件无法成为一份"任何语言都能实现的规范"。

**被否方案：每会话一个 JSONL 但目录结构自定。**

否掉的原因：与 pi agent-dir 布局不兼容，失去 P-1 的生态杠杆。见 ADR-010。

**代价（已知并接受）**：文件锁与一致性由我们实现；需要处理网络文件系统与云同步目录的失效情形（02 §4.5）；需要防范派生数据损坏（靠"派生数据必须可丢弃"这一设计把事故降级，02 §4.3）。

## ADR-002 划分三个协议 D / C / B

**决策**：数据层协议（D）、核心层接口面（C）、绑定线格式（B）三者独立定义、独立演进。

**理由**：三者面向不同的实现者，耦合任意两者都会导致其中一个无法被独立实现。

- 把数据层格式混进核心层接口 → 数据层无法被独立实现（违背 ADR-001 的理由 1）
- 把传输细节混进核心层接口 → 新增绑定就要改核心（违背 ADR-003）

**被否方案：单一协议（一套 RPC 覆盖全部）。**

否掉的原因：这是最直觉的方案，但它在交互面上必然崩掉——核心层需要向控制层发起请求（权限确认），方向与请求-应答相反。见 ADR-005 与 03 §2。

**被否方案：两个协议（数据层 + 一个统一的对外协议）。**

这个方案能工作，但代价是绑定层与核心层的边界模糊——实现时很容易把传输逻辑放进核心。三面划分是把这个边界**写进文档**的手段。

## ADR-003 核心层与绑定层分离，核心不知道传输

**决策**：核心层只对外暴露一套与传输无关的接口面。绑定层只做序列化、传输、寻址。

**理由**：

1. **新增绑定不改核心**。这是"暴露多种操作协议"（stdio / RPC / HTTP …）这个需求的前提。
2. **核心层可 headless 运行**，不假设对端是终端、浏览器还是桌面应用。
3. **有先例**。pi 的核心只问 `ctx.hasUI`（是否有 UI 可以承载交互），从不问是哪种传输，并用 `ctx.mode === "tui"` 守卫 TUI 专用代码（已验证事实）。

**被否方案：核心层内建 stdio 支持，其他传输作为附加。**

否掉的原因：这正是 `pi --mode rpc` 的形态——一个长驻子进程、JSONL over stdio、单客户端。它在"从命令行驱动"场景下很好用，但撑不起多客户端与远程壳子（ADR-004、ADR-011 都需要绑定层的存在）。可以作为 v1 的一种绑定实现，但不能作为架构。

## ADR-004 信任级别是绑定的属性

**决策**：`trustLevel` 由绑定声明，能力由核心层按信任矩阵授予。同一命令在不同绑定上可能被授予或拒绝。

**理由**：命令面里有 `bash` 和 `prompt`。`prompt` 会触发工具调用，也就是**在服务主机上任意执行代码**。若信任是协议级属性（"协议 C 允许 `bash`"），那么一条暴露到公网的 WebSocket 就等于把主机交给任何能连上的人。

这是"壳子直连异地服务"能否安全实现的唯一保障。

**被否方案：认证即全权（认证通过就授予全部能力）。**

否掉的原因：把"身份"与"权限"合并，会导致无法实现"远程壳子可以看和说，但不能在主机上执行命令"这个很常见的需求。而且认证是二值的，权限需要是集合。

**被否方案：由控制层自报信任级别。**

否掉的原因：对端声称自己可信，等于没有信任模型。

## ADR-005 交互请求路由给信任级别最高的 attachment

**决策**：同一会话多条 attachment 时，核心层发起的交互请求（权限确认等）只发给 `trustLevel` 最高的那条，同级取最早连接者。低信任 attachment 收到完整对话事件但无权应答。

**理由**：

1. **避免重复弹出**。若广播给所有 attachment，同一个权限请求会弹在多个壳子上，任一个应答后其他的变得无效。
2. **避免落到无权限的壳子**。远程 Web 壳不应能批准本地工具执行——否则绕过 ADR-004 的裁剪。
3. **可预测性**。"先到先得"比"按信任级别"更简单，但在多绑定共存时会把交互路由到错误的入口。

**被否方案：广播给所有 attachment，先应答者生效。**

否掉的原因：多个壳子同时弹窗，用户在终端应答后浏览器里还挂着一个待处理请求；而且实现上"先应答者生效"需要一个跨 attachment 的竞态仲裁，复杂度不比按信任级别路由低。

**被否方案：由客户端在 attach 时声明自己是否愿意处理交互。**

否掉的原因：这就是"对端声称自己可信"。信任级别必须由绑定声明（可验证的属性），不能由客户端选。

## ADR-006 插件即 pi extension，不自建插件系统

**决策**：核心层内嵌 pi 的 extension 运行时，从数据层的 `extensions/` 加载 `.ts` 插件。工具注册、命令注册、事件订阅、扩展间通信都用 pi 的既有 API。分发复用 pi packages。

**理由**：

1. **工作量是适配而非实现**。pi 的扩展面已覆盖需要的一切：`registerTool` / `registerCommand` / `registerShortcut` / `registerFlag` / `registerProvider` / `on()` / `pi.events`，jiti 加载免编译，宿主包以 `peerDependencies: "*"` 提供（均为已验证事实）。
2. **资源目录天然对齐**。pi 的 `extensions/` `skills/` `prompts/` `themes/` 正好是数据层需要的四类资源。
3. **生态互通**。用户已有的 pi 插件与技能零成本迁移；ucode 也能消费 pi 生态的包。

**被否方案：自建插件运行时。**

否掉的原因：可控性和将来的隔离能力是真实的好处，但从零实现加载/卸载/依赖/事件总线是显著工作量，且与 pi 生态完全隔离。若 `[假设 #4]` 不成立（运行时无法嵌入），这个方案会被重新启用——届时需要回到 07 重新评估基座选择。

## ADR-007 v1 不做插件隔离

**决策**：v1 不对插件做沙箱、权限提示或能力限制。

**理由**：**插件信任 = 文件系统所有权。** 能写数据层插件目录的人本来就能改这个目录里的一切——改配置、把模型定义指向自己的端点、读走凭据，也包括直接编辑会话记录。在这种前提下做插件沙箱是**假边界**：沙箱拦住的是插件，拦不住那个能写目录的人。

**这个决策不是"暂时不做"，而是"在当前信任模型下没有意义"。** 它只有在信任模型改变时才需要重新考虑：即当出现"安装来自不受信任来源的插件"这个需求时（此时 `extensions/` 目录的所有权不再等价于可信）。

**被否方案：给插件加权限声明与提示。**

否掉的原因同上——提示的对象是本来就有完全控制权的人。

**参考**：pi 有 `sandbox` 与 `gondolin`（micro-VM 路由）两个扩展样例。若将来需要卸载不可信插件，这些是起点。

## ADR-008 数据层文件兼作核心实例间的事件总线

**决策**：owner 实例往会话文件追加记录，其他核心层实例通过**跟随该文件的追加流**获得实时进展。**不实现 core↔core 通道。**

**理由**：消除一整类复杂度。若要让多个实例实时共享同一会话的进展，走显式通道需要：实例间服务发现、连接建立、认证、双向协议、断线重连、事件去重。而数据层文件天然是广播介质——owner 本来就要写它，其他实例本来就有读权限。

**代价与前提**：

- 依赖 `[假设 #1]`（会话文件严格追加，02 §3）。若不成立，跟随方案失效，本 ADR 作废。
- 跟随机制的具体实现有若干坑（变更通知不可靠、部分读取、文件被整体替换），见附录 B。这些是**实现问题，不影响本决策**。
- 非 owner 实例**不参与交互应答**（04 §5）——这条是 v1 的范围边界。

**被否方案：SQLite + 变更通知。**

否掉的原因：见 ADR-001。

**被否方案：owner 通过 IPC/网络广播给其他实例。**

否掉的原因：需要实现上列出的全部机制，而这些机制的存在只为了让非 owner 看到进展——用文件跟随几乎免费地达到同样效果。

## ADR-009 不采用 pi 的 experimental server/client/protocol

**决策**：不复用 pi 的 `@earendil-works/pi-server` / `pi-client` / `pi-protocol` / coordinator 作为服务层基座。

**理由**：它**在形态上几乎就是本架构**（多服务实例注册到 coordinator、一个 host 一个 server 目录、会话可有多个 presentation attachment、CBOR + unix socket 传输），但当前的成熟度不足以作为地基：

- 明确标注 experimental，**无兼容性承诺**
- source-only（v0.85.1 起 server/client 命令不进 npm bundle）
- **协议层无认证**——而认证是"异地壳子"的前提（ADR-004 的信任模型需要它）
- client **不自动重连、不重放**
- 依赖 unix socket；跨机需要经由 coordinator 的 TCP 管道，而那部分同样是 experimental

**被否方案：直接采用它，省掉协议设计。**

否掉的原因：节省的是设计工作，付出的是把地基押在一个随时可能变的、无认证的实验性协议上。而我们的协议设计并不是从零开始——命令面照搬 pi 的 rpc 命令清单，交互面照搬它的 `extension_ui_request` 语义（见 ADR-010、03 §4/§6），所以"自己设计"的实际增量不大。

**重新评估的时机**：若 pi 的该层去掉 experimental 标记、补上认证、进入 npm bundle，本 ADR 值得重开——届时可能改为"用它的协议作为协议 B 的一种绑定"。

**注意**：本 ADR 否掉的是**复用它作为地基**，不是知识上的无视。它的命名（`serverId` / `sessionId` / `attachmentId`）与概念（attachment、多实例注册）被我们沿用，以便将来迁移。

## ADR-010 会话采用追加式树结构

**决策**：会话存储为**追加式记录流**，记录之间通过**父指针**构成树而非线性列表。对既有内容的修改（压缩、编辑历史、打标）以追加新记录的方式表达，不改写旧记录。

**级别**：基准（上述结构性质；改动进变更集）。具体的记录格式——字段名、记录类型集合、文件命名——**属实现级**，见附录 B；若决定采用 pi 兼容格式则关联待定项 P-1。

**理由**：

1. **父指针是对的分支模型**。分支（分叉/克隆）不需要复制历史，只需要指向更早的记录。
2. **追加式表达修改**是这套结构的关键，它同时带来三个好处：多实例可跟随（ADR-008）、崩溃后只需处置尾部（02 §4.4）、写入无需原子性（02 §4.2）。
3. **省掉一轮设计**。无论是否采用 pi 的具体格式，"带父指针的追加式记录流"这个结构都会收敛到相似形状——pi 已经为它设计了完整的记录类型集合，包括如何用追加表达压缩、编辑、打标。

**被否方案：线性消息列表 + 原地修改。**

否掉的原因：分支要复制历史；原地修改破坏追加式，连带作废 ADR-008、02 §4.2、02 §4.4 三条设计。

**被否方案：采用关系型模型（消息表 + 分支表）。**

否掉的原因：见 ADR-001。且关系模型要表达"追加式修改"需要额外的版本列，复杂度不低于树结构。

## ADR-011 v1 只做 Web 壳

**决策**：v1 的控制层只交付 Web 壳，不做 TUI、桌面、App。

**理由**：Web 壳是**验证协议的最佳载体**——它天然是"另一个进程、另一套交互模型、可能远程"，能暴露协议设计的问题；而 TUI 与核心层同机、交互模型接近，会掩盖问题（例如交互面的方向反转在 TUI 下不容易暴露，因为 TUI 与核心层同在终端里）。

**被否方案：TUI 优先（复用 pi 的 `@earendil-works/pi-tui`，最快看到效果）。**

否掉的原因：`pi-tui` 确实现成（差分渲染，已验证事实），但 TUI 的交互模型会掩盖协议设计缺陷，且难以验证多客户端挂载与远程场景。TUI 是 v2 的事。

**被否方案：桌面壳（Electron/Tauri）。**

否掉的原因：打包与跨平台分发成本高，在协议未稳定前做它是浪费。

## ADR-012 协议版本双向校验、从不静默降级

**决策**：握手时双方都必须校验对方版本，不支持则**显式拒绝**。版本或能力不匹配必须是显式错误，不允许"尽量兼容"。新增可选能力走能力协商，**不升版本号**；只有改变既有消息语义才升版本号。

**级别**：基准（上述不变量；改动进变更集）。版本号取整数形式、以及能力协商的具体字段，属实现级（附录 B）。

**理由**：

1. **"从不静默降级"是防事故规则**。尽力而为地解析未知格式，是数据损坏类事故的经典成因——一方按旧语义解释新格式，静默产生错误结果。pi 的 experimental 协议反过来做（明确声明"无兼容性承诺"）也说明了这个问题的真实存在。
2. **能力协商与版本号分离**，是为了让"新增一个可选能力"不需要双方同步升级。
3. **能力声明与能力授予分离**（ADR-004 的配套），是为了让"操作被拒"可诊断——区分"绑定承载不了"与"信任不足被拒"。

**被否方案：语义化版本（semver）。**

否掉的原因：协议版本需要的是"是否兼容"这一个比特，semver 的三个数字带来的主要是沟通成本。整数加一次校验更直接。（此为**实现层面**的取舍，不构成架构约束。）

**被否方案：只做向后兼容（新客户端能连旧核心层）。**

否掉的原因：实践中"向后兼容"通常意味着静默降级，与理由 1 冲突。
