# 00 · 定位与版本策略

## 这份文档是什么

ucode 的**基准架构 v1**。它定义业务无关的底座：分层、协议、信任模型、数据层不变量、依赖规则。

它不定义业务功能——那些属于 v2。

## v1 的作用：一个可被 diff 的参照点

**这是理解本文档全部约定的前提。**

v2 会在业务需求的压力下改动架构。这是**预期的、正常的**，不是异常，也不是失败——v1 是在没有业务输入的情况下写出来的，它必然会在业务面前暴露不足。v2 是 v1 的补全与变种升级，目标是更贴合业务。

那么 v1 为什么要保持不变？**因为它的价值在于成为一份未被污染的参照点。**

如果 v1 随着讨论被反复就地修改，那么"v2 到底改了什么"就只能靠记忆回答，而记忆会失效：改动会在讨论中被逐步吸收，半年后没人能说清哪些是第一版的设计、哪些是业务压出来的调整、哪些是被悄悄放弃的假设。这是架构文档最常见的退化方式——它不会变错，它会变成所有人都以为记得、但没人能复述的样子。

所以 v1 的定位是：**冻结的快照，供 v2 做对照。** 它不需要正确，只需要如实记录 v1 时刻的想法，并保持可被 diff。

### 由此推出的三条结论

1. **改动是 v2 的正常产出，不是需要审批的例外。** v1 里没有任何内容"不许改"。
2. **但基准级的改动必须被记录。** 见下面的变更分级与变更追踪。
3. **v1 冻结后不再就地编辑。** 修订写在 v2 里，v1 保持原样。

## 基准与实现参考

本文档的内容分两级，判别标准是一条：

> **换一种做法，架构结论会变吗？** 会 → 基准。不会 → 实现。

| | **基准**（01–08） | **实现参考**（附录 B） |
|---|---|---|
| 内容 | 分层、边界、不变量、信任模型、依赖方向、决策理由 | 具体文件名、消息形状、命令清单、分帧方式、包内划分 |
| 性质 | 约束。改动必须记入变更集 | 建议。可自由替换，不产生架构后果，不必记录 |
| v2 改动它时 | 必须显式记录：改了什么、为什么 | 直接改，不进清单 |

**为什么必须分开**：把实现细节写进基准，会让 v2 的业务讨论撞上一堆它在架构上本不该关心的约束。举例——"会话 ID 采用什么格式"在业务层面完全无关紧要，但如果它被当作基准，那么讨论"会话要不要支持跨机同步"时就会莫名其妙地被它挡住。这类约束是**假约束**：它们不保护任何东西，只制造摩擦，而且它们会淹没真正需要被追踪的那些改动。

同理，"命令面有哪些命令"不属于基准：业务会带来新命令，把它当基准意味着每次加功能都要记一条变更，清单很快会失去信号。

## 读者与验收标准

**实现者**：读 01–05 掌握全部约束，读附录 B 得到一份可直接照做的参考方案。

**业务方**：读 07 就知道功能该加在哪里、哪些改动需要记录。v2 的讨论以 07 的清单为输入。

四条验收标准（本文档自身的合格条件）：

1. 实现者读完 01–05 掌握全部约束，配合附录 B 可直接开工，无需再问架构问题
2. 07 中每条待定项都写明了"需要什么输入才能定"，没有悬空 TODO
3. 06 中每条假设都写明了"若不成立会推翻本文档哪一节"
4. 每条标记为**基准**的内容，v2 改动它时都能被识别出来（即：基准与实现的分界是可判定的）

## 内容分类铁律

每一段内容属于且只属于以下四类之一。写作时必须能明确归类，禁止混写。

| 类别 | 含义 | 标记方式 |
|---|---|---|
| **已验证事实** | pi.dev 的能力，经实际抓取官网/仓库/文档确认 | 正文陈述，出处见附录 A |
| **未验证假设** | 我们推断成立但**没有验证**的 pi 行为 | 集中在 06，正文引用处标注 `[假设 #n]` |
| **我们的决策** | 我们的设计选择，附理由与被否方案 | 正文陈述 + 08 中有对应 ADR |
| **待业务输入** | 需业务或验证才能定的问题 | 集中在 07，带推荐方案 |

**铁律一：不得把未验证的推断写成事实。**

本文档有两条架构卖点完全建立在未验证的假设上——"数据层文件兼作核心实例间的事件总线"依赖 `[假设 #1]`，"插件复用 pi extension 运行时"依赖 `[假设 #4]`。把它们写成既定事实，会让 v2 在未核实的地基上继续加层。

**铁律二：不得把实现选择写进基准。**

判别方法见上节。写的时候要能回答："换一种做法，架构结论会变吗？"

## 变更分级

**级别决定 v2 改动它时要做什么，不决定它能不能被改。**

### 基准 — 改动必须记入变更集

| 基准内容 | 出处 |
|---|---|
| 四层的职责边界与"谁不知道谁存在" | 01 §2、§3 |
| 两个信任边界正交（绑定信任 vs 插件信任） | 01 §4 |
| 数据层的形态、七条不变量、owner 语义、写入顺序 | 02 §3–§6 |
| 数据层文件兼作实例间事件总线 | 02 §7 |
| 两个版本独立演进、前向拒绝 | 02 §9 |
| 协议 C 的三面划分与各面的语义不变量 | 03 §2、§3、§5、§6 |
| 信任级别是绑定的属性 | 04 §2 规则 2 |
| 交互承载能力按绑定声明、降级必须显式、路由按信任级别 | 04 §2 规则 3、§4、§5 |
| 无认证不得监听非 loopback | 04 §7 |
| 包边界与依赖方向 | 05 §1、§2 |

改动这些**不需要审批**，但需要在 v2 里留下记录（格式见下节）。业务需求足以构成改动的理由——不需要额外的正当性。

### 实现 — 改动无需记录

附录 B 的全部内容，以及在 01–08 中被标注为"属实现"的内容。直接改，不进变更集。

**理由**：变更集是给人读的。把不重要的改动混进去，重要的那些就会被淹没。所以"实现级"这个分级的主要作用不是给予自由，而是**保持变更集的信噪比**。

### 待定 — 需输入才能定

集中在两章：06（技术未知）与 07（业务未知）。每条都写明了缺什么输入。

## v1 的冻结与变更追踪

### 冻结时刻

v1 现在是**工作文档**：06 的假设验证结论（M0 产出）可以就地回写进 01–05，把它从"假设"升格为"已验证事实"或触发修订。这一步应当在 v2 动笔之前完成——带着未核实的地基进入业务讨论，代价会随层数放大。

**v2 开始编写时，v1 冻结。** 此后 v1 的目录不再编辑，任何修订都写在 v2 里。

### 变更集的形态

v2 中应有一节「对 v1 的变更清单」，每条五行：

| v1 的哪一节 | v1 说的是什么 | v2 改成什么 | 驱动它的是哪条业务需求 | 影响面 |
|---|---|---|---|---|

只记录**基准级**条目。实现级改动不进清单。

v2 若引入新的对外接口面（例如面向第三方开发者的开放 API），新建 `docs/architecture/v2/` 而非覆盖 v1——v1 保持可追溯。

### 机械保证

**变更清单靠人写，会漏；靠 git 不会。** 所以：

1. v1 定稿时打一个 tag（例如 `arch-v1`）
2. v2 在同一条历史线上演进，不重写历史
3. 于是 `git diff arch-v1..HEAD -- docs/architecture` 就是一份机械保证的完整变更集，可与人工清单交叉核对
4. **两者都要**：diff 保证不漏，人工清单解释"为什么"——而"为什么"正是 v2 最需要留下的东西（它记录的是业务如何反过来改造了架构）

这条机制是 v1 保持不变的**实际用途**。如果 v1 被就地修改，历史线就断了，diff 也就失去意义。

## 如何演进到 v2

1. **先跑 M0**（06 的四条假设），结论回写 v1（此时 v1 尚未冻结）
2. **冻结 v1** 并打 tag
3. **讨论业务**，以 07 §5 的输入清单为起点
4. 业务功能落在 07 §3 列出的扩展点上，不新增层、不改协议骨架
5. 业务确实压到基准级内容时，按 §变更分级记录进变更集——**这是 v2 的正常产出**
6. 附录 B 的内容不构成对 v2 的约束，v2 讨论时不要把它们当作前提
7. v2 完成后，用 §变更追踪的机制交叉核对

## 术语速查

01 有完整定义，最短版本：

- **数据层** — 一个目录，`~/.ucode`。一台机器一个。
- **核心层**（= 服务层）— headless 的智能体本体。对话、agent loop、工具执行、插件、人类交互中转。
- **绑定层** — 把核心层的接口面序列化到具体传输上。
- **控制层** — 绑定协议的具象化，即各种壳子。
- **协议 D / C / B** — 分别对应数据层 / 核心层接口面 / 绑定线格式。
