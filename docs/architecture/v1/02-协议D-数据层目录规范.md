# 02 · 协议 D：数据层

**级别：基准**（数据层的形态、不变量、owner 语义；改动须记入变更集。具体文件命名与格式属实现级，见附录 B）

## 一、定位

数据层是**一台机器上的一个目录**，默认 `~/.ucode`。核心层以这个目录路径为入口参数启动：

```
agent-service start --data-dir ~/.ucode
```

这是核心层唯一的持久化入口。

**"数据层唯一共享"的含义**：一台机器可以有多个核心层实例，它们指向同一个目录。这是 per-host 不变量——不跨机。

协议 D 是这份目录规范的**协议**而非某个库的用法，因此它必须①可被任何语言实现，②附一份一致性测试套件（见 §7）。

## 二、数据层持有的状态分类

协议 D 只规定**有哪几类状态、谁可以写、能否丢弃**。具体的文件名与格式属**实现级**（附录 B 给了一份参考）。

> **已决**：数据层格式做成 **pi agent-dir 布局的超集**（原待定项 P-1 / Q-1）。所以附录 B 里的具体命名不是「参考之一」，而是定下来的方向——收益是 `PI_CODING_AGENT_DIR=~/.ucode` 即可让 pi 生态直接读写数据层；代价是继承 pi 的会话格式演进。

| 类别 | 内容 | 写入者 | 能否丢弃 |
|---|---|---|---|
| **配置** | 用户偏好、模型与供应商定义 | 用户；核心层受限写 | 否 |
| **凭据** | API key、OAuth token | 用户；核心层 | 否，且**不进同步**（§8） |
| **上下文** | 全局提示词与项目上下文 | 用户 | 否 |
| **插件与资源** | 插件、技能、提示词模板、主题 | 用户 | 否 |
| **会话** | 对话历史与由此派生的全部状态 | **仅 owner**（§5） | 否 |
| **派生数据** | 索引、缓存等一切可从上面几类重建的东西 | 任何核心层实例 | **是，且必须随时可丢**（§4） |
| **锁与日志** | 协调用的锁、运行日志 | 任何核心层实例 | 锁是暂时的，日志视需要 |

### 两条必须记住的推论

**插件与资源是业务扩展点。** v2 的业务功能主要通过"往这几个目录里放东西"接入，而不是通过改核心层代码。这是数据层采用目录形态的一个直接后果，也是它相对数据库方案的具体收益。

**凭据与会话同处一个目录，但命运不同。** 见 §8。

## 三、会话的存储性质

协议 D 不规定会话文件的字节格式（那是实现），但规定它的四条**性质**。这四条是数据层能被多实例共享、能被 tail 跟随、能被重放的基础：

1. **追加式**。对既有内容的修改表现为追加新记录，而不是改写旧记录。压缩、编辑历史、打标等操作都遵循这一条。
2. **带父指针的树**。会话不是线性列表，每条记录指向它的父记录。分支不需要复制历史。
3. **单调游标**。每条记录可导出一个单调递增的序号，用于客户端重放与断线续传（03 §5）。
4. **每会话独立**。游标、树、追加序列都以单个会话为作用域，不跨会话。

第 1 条是另外三条的前提，也是 §6 的多实例方案的前提。它是 `[假设 #1]`。

## 四、不变量

以下每条都是"必须如此"，不规定"如何做到"（怎么做属于实现）。

### 1. 归属与权限

数据层目录只对本人可读写。凭据的权限比目录更严。**权限不满足时拒绝启动**，不静默修正。

### 2. 非追加写必须原子

除追加以外的任何写，要么完整生效、要么完全不生效，不存在中间态。

**追加写是例外**：追加不需要原子性保证，因为它不修改既有内容（这是 §3 第 1 条的收益之一）。

### 3. 派生数据必须可丢弃

派生数据目录内的任何东西，都必须能被随时删除并在下次启动时重建。真相永远是扫描数据层本身的结果，派生数据只是加速。

**推论：派生数据损坏不是数据事故。** 启动时以数据层为准做一次对账即可修复。

这条规则的价值在实践中极高：它把"多进程写同一份索引导致损坏"从一个数据事故降级为一次性能损失。

### 4. 崩溃后可恢复

崩溃可能留下不完整的尾部。**接管者必须能识别并丢弃不完整的尾部**，不得把损坏内容当作数据。

### 5. 危险的文件系统上拒绝运行

数据层目录位于**网络文件系统**（NFS/SMB）或被**云同步**（iCloud Drive / Dropbox / OneDrive）时，**拒绝启动**。

原因：这两种环境下文件锁与文件变更通知都不可靠，并发写入会撕裂会话。这不是保守——静默的数据损坏不会立即暴露。

### 6. 版本前向拒绝

读取者遇到**高于自身**的数据层版本，必须**拒绝启动或转为只读**，禁止"尽力而为"地解析。

"尽力而为"是这类系统的经典事故源：旧实例按旧语义解释新格式，静默损坏数据。

### 7. 路径安全

由会话标识或项目路径派生的文件路径必须经过校验，不得逃逸出数据层目录。

## 五、owner 语义

**一个会话同时只有一个 writer，即它的 owner。** 其他核心层实例对该会话只读。

- owner 通过竞争产生，不由配置指定
- owner 定期声明存活
- 声明超时后，其他实例可判定原 owner 已死并**抢占**；抢占时执行 §4.4 的尾部处置
- 优雅退出时主动释放

**为什么需要 owner**：多个实例同时往一个会话追加会撕裂它。owner 是让"数据层唯一共享"与"多实例"这两件事共存的最小机制。

具体的竞争与存活声明机制属于实现（附录 B）。

## 六、写入顺序不变量：先落盘，再广播

核心层产生的每条会话记录，必须**先写入数据层，再向控制层广播对应事件**。

顺序不能反。反过来的话，发生在两次操作之间的崩溃会让用户看到未持久化的内容——而用户会以为自己看到的东西已经保存了。

这条不变量在单实例和多实例下都成立。

## 七、多实例：数据层文件兼作事件总线

owner 实例往会话文件追加记录，其他实例通过**监听文件变更 + 按位置跟随**获得实时进展。**不需要实例间的专用通道。**

这是本架构里最省事的一处设计，它消掉了一整类复杂度：不用实现实例间的服务发现、连接、认证、双向协议、断线重连。数据层文件天然充当广播介质——owner 本来就要写它，其他实例本来就有读权限。

依赖：`[假设 #1]`。若不成立，本节方案作废，多实例协作需改为显式通道或定期全量重读。实现注意（部分读取、变更通知不可靠、文件被整体替换）见附录 B。

**v1 的范围边界**：非 owner 实例**不参与交互应答**。交互请求只发给 owner 实例上信任级别最高的 attachment（04 §5）。否则同一权限请求会在多个实例上重复弹出，或落到一个没有权限的壳子上无人应答。

## 八、凭据的边界

凭据与其余状态同处数据层目录，因为它属于"这台机器的智能体状态"，且核心层需要读它。

**但它是唯一标注"不进同步"的一类。** 一旦数据层目录被同步或跨机共享，凭据会跟着走，而用户通常不会预期"配置同步"等同于"凭据外泄"。

v1 的动作仅限于标注这个边界。若将来要做跨机共享数据层，凭据必须抽出（待定项 P-3）。

## 九、版本演进不变量

数据层里存在**两个独立的版本概念**，实现时不要混淆，也不要把它们合并：

| 概念 | 含义 | 演进责任 |
|---|---|---|
| **数据层协议版本** | 协议 D 本身的版本 | 我们 |
| **会话记录格式版本** | 会话文件内部格式的版本 | **由 pi 演进**（已决：采用 pi 兼容格式，见 §2） |

**必须独立演进。** 合并的话，"我们升了一次协议版本"就会变成"必须重写所有会话文件"，而重写会作废所有客户端的游标（§3 第 3 条），也会与 §3 第 1 条冲突。

演进规则：**严格 additive**——新版本只能增加，不得改变既有语义；低版本读到高版本按 §4.6 处置。

具体的版本标记方式属于实现（附录 B）。

## 十、待业务输入

- **配置里有哪些键**：v1 只规定这类状态存在及其写入规则，不规定键。键是业务的，v2 填。
- **模型与供应商的定义 schema**：同上。
- **会话保留策略**：是否自动清理、保留多久。业务策略。
- **日志与审计**：v1 只规定日志目录存在。是否需要审计日志、格式、留存期属于业务（07 §5）。
