# 05 · 包结构与依赖规则

**级别：基准**（包边界与依赖方向；改动须记入变更集。包内划分与测试细节属实现级，见附录 B）

## 一、包边界

```
data-layer-spec/     协议 D 的规范与一致性测试套件
store/               协议 D 的参考实现
core/                核心层（协议 C 的服务端实现）
bindings/*           绑定层，每种传输一个包
client/              控制层共用 SDK
shells/*             控制层，每个壳一个包
cli/                 核心层与壳子的启动入口
```

**包边界是架构，包内文件划分不是。** 划这个边界的唯一目的，是让三条需求在结构上成立：

| 需求 | 由什么结构保证 |
|---|---|
| 服务层可脱离控制层单独安装 | `core` 不依赖任何 `shells/*` |
| 数据层可被独立实现 | `data-layer-spec` 不依赖任何内部包 |
| 新增绑定（或新增壳）不需改核心层 | `bindings/*` 与 `shells/*` 都是叶子方向的加法 |

## 二、依赖方向

```
shells/*  →  client  →  bindings/*  →  core  →  store  →  data-layer-spec
```

**严格单向。** 反向依赖一律禁止。

### 具体禁令（每条对应一条架构不变量）

| 禁止 | 对应 |
|---|---|
| `core` 依赖任何 `bindings/*` | 核心层不知道传输（01 §3、ADR-003） |
| `bindings/*` 依赖任何 `shells/*` | 绑定层不知道对端形态（01 §3） |
| `bindings/*` 之间互相依赖 | 绑定之间不通信；跨绑定一致性由协议 C 语义保证（04 §8） |
| `store` 依赖 `core` | 数据层可被任何实现消费（ADR-001） |
| `core` 绕过 `store` 直接读写会话文件 | 绕过 owner 语义与写入不变量（02 §5、§6） |
| `data-layer-spec` 依赖任何内部包 | 它必须能被外部独立实现者使用 |

### 强制手段

用依赖检查工具（`dependency-cruiser` 或等价物）做成 CI 门禁，违反即构建失败。规则写成**允许列表**而非禁止列表——显式列出每个包允许依赖什么。理由是新增包时禁止列表会静默漏掉，而允许列表会直接报错。

## 三、"服务层可脱离控制层单独安装"的验收形式

这是需求里最具体的一条，必须可验证而不是靠约定。

**交付形态**：`core` 是可独立安装的包，其依赖里不出现任何 `shells/*`。`cli` 提供两个入口——启动核心层（+指定绑定）的入口，与启动某个壳的入口。**后者不需要核心层的代码，只需要连到一个端点。**

**CI 验收**：

1. 在一个空目录里只装 `core` 与一个绑定包（**不装任何壳**）
2. 启动核心层，指向一个临时数据层目录
3. 用一个**纯协议测试客户端**（不依赖 `client` 包，直接按协议收发消息）完成：握手 → 新建会话 → 发起对话 → 收到完整事件流 → 取回历史校验
4. 断言退出码为 0

这一个任务同时验证三件事：核心层不依赖壳、协议 C 可被独立实现、数据层可被独立实现。

**反向验收**：再跑一个只装 `shells/web` 的任务，断言它的依赖树里**不出现 `core`**。

## 四、数据层的独立实现验证

`data-layer-spec` 导出一致性测试套件，形态是"接收一个实现工厂函数"：任何实现（我们的 `store`、将来某个其他语言的实现、某个实验性的另一种存储后端）传入自己的工厂函数，跑完整套，通过即符合协议 D。

**必测范围**（对应 02 的不变量，具体测例属实现）：

| 覆盖 | 对应 |
|---|---|
| 并发竞争 owner：恰好一方成功 | 02 §5 |
| owner 崩溃后能被接管，且尾部得到处置 | 02 §4.4、§5 |
| 派生数据被删除或损坏后可重建 | 02 §4.3 |
| 非追加写的原子性（中途崩溃不产生中间态） | 02 §4.2 |
| 权限不满足时拒绝启动 | 02 §4.1 |
| 版本高于自身时拒绝启动 | 02 §4.6 |
| 危险文件系统上拒绝启动 | 02 §4.5 |
| 路径逃逸被拒 | 02 §4.7 |

没有这份套件，协议 D 只是一份约定而不是协议——它是"数据层可被独立实现"这条需求的实际交付物。

## 五、测试分层

**层次划分是基准，具体测例属实现。**

| 层 | 必须覆盖什么 |
|---|---|
| 数据层 | 上述一致性套件；任何实现都要跑 |
| 绑定层 | 线格式往返；**跨绑定一致性**（04 §8） |
| 核心层 | 用假模型供应商的录制式测试（对话 → 事件 → 落盘）；交互超时与降级；信任矩阵约束 |
| 控制层 | 端到端：起真核心层 + 无头浏览器，验证挂载、权限弹窗、断线续传 |

**假模型供应商是必要设施**：核心层的测试不能让结果依赖真实模型调用。pi 的 `ai` 包支持注册自定义 provider（已验证事实），注册一个回显用的即可。

## 六、待业务输入

- 是否发布到公共包仓库（影响命名与版本策略）
- 是否预期非 JS 的核心层实现（若是，协议 D 的测试套件需提供多语言入口，协议 C 需要跨语言 SDK——**这会显著影响工作量，宜早定**）
- 壳的分发方式（包管理器 / 安装包 / 容器）
