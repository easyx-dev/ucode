# 06 · 待验证假设与 spike 计划

**每条假设都写明了：内容、为什么重要、怎么验证、若不成立会推翻哪一节。**

本文档中有两条架构卖点完全建立在未验证的假设上。在验证完成之前，01–05 中相应结论应被理解为**待验证的设计**，不是既定事实。

**验证完成后的动作**：结论回写进 01–05 的正文（升格为"已验证事实"或触发修订），并在本章记录验证日期与结论。不要只在本章更新。

## 假设总览

| # | 假设 | 影响的架构卖点 | 影响面 |
|---|---|---|---|
| 1 | pi 的 session JSONL 严格只追加 | 数据层文件即核心实例间的事件总线 | 02 §3、§7，多实例方案 |
| 2 | `sessionManager` 可覆写 / `PI_CODING_AGENT_DIR` 可指向数据层 | 数据层是唯一真相 | 02 §4.3、§6，store 定位 |
| 3 | pi 容忍 `sessions/` 下的非 `.jsonl` 文件 | 锁与派生数据可与会话同层 | 02 §2 的状态分类 |
| 4 | pi extension 运行时（jiti + `registerTool` + `pi.events`）可嵌入非 pi 宿主 | 插件复用而非自建 | 03 §7，工作量级差异 |

## [假设 #1] pi 的 session JSONL 严格只追加

**假设内容**：pi 写会话文件时只追加，从不重写或截断已有字节。压缩、历史编辑、打标等操作都表现为追加新 entry，而非原地修改。

**依据**：pi 的 entry 模型里有 `compaction`、`context_edit`、`label` 这些 entry 类型（已验证事实：类型清单见 pi 文档）。它们**看起来**是为"追加式表达修改"而设计的——`compaction` 携带 summary 与 firstKeptEntryId 而不是删掉旧内容，`context_edit` 携带 targetId 与 replacement 而不是改写目标。但这是从类型设计推断出的**意图**，不是验证过的**行为**。

**为什么重要**：02 §7 的整个多实例方案建立在此之上。owner 实例追加写记录，其他实例靠**跟随同一文件的追加流**获得实时进展。若 pi 会重写已有字节，跟随就失效。

**验证做法**：

1. 准备一个测试仓库与一段会话脚本，覆盖：普通对话、工具调用（读文件）、**触发压缩**（把上下文撑到阈值以上）、手动 `compact`、`context_edit`、`label`
2. 全程在每一步之后计算文件的**内容哈希与长度**，记录 `(timestamp, size, sha256)`
3. 断言：**任一步的哈希必须是上一步哈希的前缀延伸**——即 `newContent.startsWith(oldContent)`。长度必须单调不减
4. 额外检查 inode 是否变化（若 pi 用"写临时文件再 rename"重写，inode 会变，长度可能不变）

**若不成立**：02 §7 作废。多实例协作需改为：显式的 core↔core 通道（引入服务发现、连接、认证、重连——即我们刻意避开的那一整类复杂度），或退化为"非 owner 实例定期全量重读"（实时性差但简单）。

**注意**：即便假设成立，也有一个次生风险需要一并验证——pi 是否会在**加载**会话时自动迁移格式并**立即写回**（pi 的 session header 有版本号且会从 v1/v2 迁移到 v3，这是已验证事实）。若是，则"只追加"在某些会话上不成立。测试时要用一个**旧版本格式**的会话文件加载一次，观察是否被改写。

## [假设 #2] `sessionManager` 可覆写 / `PI_CODING_AGENT_DIR` 可指向数据层

**假设内容**：能把 pi 的持久化重定向到我们指定的数据层目录（理想情况是让 pi 直接读写 `~/.ucode` 的 `sessions/`），或能用 `sessionManager` 完全接管持久化。

**依据**：pi 的 SDK 工厂函数接受 `sessionManager` 覆写参数，环境变量里有 `PI_CODING_AGENT_DIR` 用于指定 agent-dir，会话目录还可用 `sessionDir` 设置 / `--session-dir` / `PI_CODING_AGENT_SESSION_DIR` / SDK `sessionDir` 覆盖（**以上均为已验证事实**）。但"参数存在"不等于"能达成我们想要的语义"——尤其不确定的是：覆写 `sessionManager` 后 pi 是否仍会在旁路写一份自己的 JSONL。

**为什么重要**：决定 store 的定位是**唯一真相**还是**镜像 + 索引**。

- 若可行 → 数据层就是唯一真相，`~/.ucode/sessions/` 里的文件由我们控制，02 的全部规则按设计生效
- 若不可行 → 数据层降级为"pi 格式的镜像 + 索引"，存在两个真相源，必须在 02 §6 重新论证"先落盘再广播"的顺序保证，并明确"若 pi 的写入失败而我们的镜像成功"这类不一致如何处置

**验证做法**：

1. 用 `createAgentSession()` 显式传入自定义 `sessionManager`，跑一轮 prompt，然后**检查 `~/.pi/agent/sessions/` 下是否出现了新文件**。出现即说明没有被接管
2. 设 `PI_CODING_AGENT_DIR=$TMP/ucode-test`，跑一轮 prompt，检查会话文件是否落在 `$TMP/ucode-test/sessions/`。若落在默认 `~/.pi/agent`，说明该变量不控制会话路径
3. 设 `sessionDir`（三种设法规各试一次）指向我们的目录，观察 pi 是否**只**写那里
4. 分别测试"SDK 嵌入"与"CLI 子进程"两种宿主方式，因为两者可能行为不同

**若不成立**：01 §1 对数据层的定义（"全部持久状态的所在"）与 02 §4.3、§6 需要修订——数据层降级为"持有权威副本"，pi 的存储成为派生。需在 02 新增一节说明两个真相源的不一致如何处置。**这是四项假设里影响面最大的一项。**

## [假设 #3] pi 容忍 `sessions/` 下的非 `.jsonl` 文件

**假设内容**：pi 在 `sessions/` 目录下遇到非 `.jsonl` 文件（例如我们的锁目录、索引文件）时不会报错，也不会尝试解析。

**依据**：无直接依据。02 的布局把锁放在 `locks/`（已避开），但**索引**原计划放在 `cache/`（也已避开）；真正需要同目录的是**每个会话的锁文件**（若有）与 pi 自己可能产生的辅助文件。此假设严格来说是为布局灵活性留的余地。

**为什么重要**：若 pi 会对会话目录下的未知文件报错或误解析，则锁与派生数据必须放到会话所在的层级之外，02 §2 的状态分类需调整——而且锁的位置会影响 owner 竞争的原子性设计。

**验证做法**：

1. 在 `~/.pi/agent/sessions/<bucket>/` 下放一个非 `.jsonl` 文件（一个目录、一个 `.json`、一个 `.lock`）
2. 分别验证 pi 的**会话列表**（列出该 bucket 下的会话）与**按 id 加载会话**两个路径
3. 观察是否有错误、警告，或该文件被当作会话尝试解析

**若不成立**：把锁与辅助文件全部移出会话所在目录（例如集中在单独的锁目录），02 §2 的状态分类更新。**影响面小，但必须在 M1 之前确定**，因为锁的位置影响 owner 竞争的原子性实现。

## [假设 #4] pi extension 运行时可嵌入非 pi 宿主

**假设内容**：在我们自己的进程里，用 pi 的 extension 运行时加载用户放在 `~/.ucode/extensions/` 下的 `.ts` 插件，并且 `registerTool` / `registerCommand` / `on()` / `pi.events` 都正常工作。

**依据**：pi 的扩展机制本身是已验证事实（工厂式入口、jiti 免编译加载、事件名与注册 API 清单、`@earendil-works/pi-coding-agent` 导出 `./experimental/plugin` 子路径）。但"在 pi CLI 里能用"与"在第三方宿主里能用"是两件事——`ExtensionAPI` 的实现在哪个包里、它的初始化是否依赖 CLI 的上下文（`ctx.ui`、`ctx.mode` 从哪来）、`pi.events` 的事件总线是谁持有的，这些都不清楚。

**为什么重要**：决定插件是**嵌入运行时**还是**自建运行时**。前者工作量是适配，后者是从零实现加载、卸载、依赖、事件总线、工具注册。这是四项假设里**工作量差异最大的一项**。

**验证做法**：

1. 写一个最小宿主进程，`import` pi 的 extension 加载入口，指向一个测试插件目录
2. 测试插件内容：`export default function (pi) { pi.registerTool({...}); pi.on('tool_call', ...); pi.events.emit(...) }`
3. 断言：插件被加载（工厂被调用）、工具注册成功、事件订阅收到回调、`pi.events` 可跨插件通信
4. 重点观察：**是否有隐含依赖 CLI 上下文**。期望 `ctx.hasUI === false`（因为我们是 headless 宿主）而不是抛错
5. 再测 `customTools` / `InlineExtension` 路径能否注册工具，并被 agent 真实调用（这一条同时验证 03 §7 的加载路径）

**若不成立**：03 §7 改为自建插件运行时，`extensions/` 的契约需自行定义（入口形状、注册 API、事件名、生命周期），并且**与 pi 的扩展生态无法互通**——这会显著削弱"选 pi 作基座"的理由，需要回到 07 重新评估基座选择。

## 执行顺序与产出物

**假设 #1 与 #2 优先**，因为它们决定数据层能否成立；#3 和 #4 可以并行。

| 顺序 | 假设 | 产出 | 阻塞什么 |
|---|---|---|---|
| 1 | #2 | 结论 + 一份"pi 实际写到哪里"的路径清单 | store 定位；M1 的写入路径设计 |
| 2 | #1 | 含哈希序列的测量脚本 + 结论 | 02 §7 多实例方案 |
| 3 | #3 | 结论（是否报错/误解析） | 02 §2 状态分类定稿 |
| 4 | #4 | 最小宿主 + 测试插件 + 结论 | 03 §7 插件工作量的量级 |

**产出物形态**：每个假设一个独立可重跑的脚本，放在实现仓库的 `spike/` 目录下（本仓库当前只有文档）。脚本要能重跑——pi 升级后需要复验，尤其是 #1 与 #2，因为它们依赖的是 pi 的**实现细节**而不是**文档承诺**。

## 关于验证的姿态

这四条假设验证的是 pi 的**实现行为**，不是它的**文档承诺**。两者会不一致，而且升级可能改变行为。#1 和 #2 在 pi 每次小版本升级后都值得复验一次——它们是这个架构与 pi 之间耦合最紧的两个点。

如果 #1 或 #2 不成立，本架构仍然可行，但代价是重新设计数据层方案，而不是打补丁。这就是把它们放在 06 单列而不是散落在正文里的原因：**它们是可以推翻架构的输入，不是实现细节。**
