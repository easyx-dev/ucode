# 04 · 协议 B：绑定层与信任模型

**级别：基准**（信任模型、三条硬规则、路由与降级规则；改动须记入变更集。具体分帧与认证机制属实现级，见附录 B）

## 一、绑定层的职责

绑定层是核心层接口面到具体传输的适配。**只做三件事**：

1. **序列化** — 协议 C 的消息 ↔ 线格式
2. **寻址** — 连接、会话、attachment 的标识与路由
3. **流式** — 把事件面推给对端

**绑定层里不得出现**：会话逻辑、状态机、重试语义、业务规则、能力判断的实现（能力判断由核心层执行，绑定只**声明**自己的信任级别与承载能力）。

## 二、三条硬规则

### 规则 1：协议 C 定义一次，绑定只做映射

同一个命令序列，经任何绑定，**结果必须一致**。绑定的差异只允许体现在**承载能力**与**信任级别**上，不允许体现在语义上。

反面例子：让某个绑定自己实现"模型忙时排队"——这就把语义放进了绑定，换一个绑定行为就不同了。

### 规则 2：信任级别是绑定的属性，不是协议的属性

同一个命令在不同绑定上被授予与否不同。协议 C 对此毫不知情——它只收到绑定的信任级别并查表。

**为什么这条必须写成规则**：命令面里有"直接执行工具"这一类，而"发起一轮对话"会触发工具调用，也就是**在服务主机上任意执行代码**。如果信任级别是协议级属性（即"协议 C 允许执行工具"），那么一条暴露到公网的连接就等于把主机交给任何能连上的人。

这是"控制层直连异地服务"这个目标能否安全实现的**唯一**保障。

### 规则 3：交互承载能力按绑定声明，核心层必须能降级

交互面是**服务端发起**的（03 §6）。不是所有传输都能承载：

- **双向传输**（stdio、unix socket、WebSocket）原生支持
- **纯请求-应答传输**（HTTP）必须**配对**：下行推请求，上行提交应答，按标识配对

绑定声明自己是否支持交互。声明不支持的绑定，核心层**不得发出**交互请求，而是走降级策略（§4）。

## 三、信任矩阵

| 绑定 | 对端信任来源 | 信任级别 | 默认授予能力 |
|---|---|---|---|
| **stdio** | 由父进程 spawn，隐式可信（能 spawn 它的人已经能执行任意代码） | `implicit` | 全部 |
| **unix socket** | 本地文件系统权限（目录与 socket 的归属与权限） | `local` | 全部；高危操作需交互确认 |
| **HTTP + SSE** | **无**（网络可达性不等于身份） | `untrusted` | 只读 + 对话；**工具直调关闭，且不具备工具执行的批准权**（见 §5 交互路由） |
| **WebSocket** | **无**，必须认证后才能提升 | `untrusted` | 认证前仅握手；认证后按策略授予，同样不具备批准权 |

### 信任级别不是"分级"，它是"认证的替代品"

这个概念的表述一直容易误导，先纠正命名：**它听起来像在给用户或通路打分（一级、二级、三级），其实它回答的是另一个问题——这条通路需不需要身份认证。**

v1 最早没有认证能力（「v1 不做 TLS 与认证」，只监听 loopback）。在那个阶段，唯一能用的判断依据是**通路来历**：谁创建的它、文件权限是什么、地址是什么。信任矩阵就是那个阶段的产物。

**有了认证能力之后，这个替代品对已认证的通路就不再需要。** 于是判断依据是两条**互斥**的分支，而不是可以叠加的三级：

```
连接到达
├── 这条路是否已完成身份认证？
│    ├── 是 → 按「身份 + 授权」判断（与 SSH 同构，不分级）
│    └── 否 → 按「通路来历」判断（下面的信任矩阵）
└── 不需要认证的通路 = 结构性等价于「本机用户本人」
```

**关键在于互斥而非叠加。** 用"已认证但来历是远端"去取交集会得出荒谬结论——比如"你从手机登录自己的账号访问自己的机器，权限低于一个未经认证的本地进程"。对照 SSH 就很清楚：从手机 SSH 进自己的机器，你就是你自己的完整权限，没有人会因为"你是从手机来的"而降权。

#### 信任矩阵仍然管什么

它管**没有身份的通路**：

| 通路 | 它证明了什么 | 给什么 |
|---|---|---|
| stdio（父进程 spawn） | 对端**本来就是这台机器的主人**——能 spawn 核心层的人已经能执行任意代码，所以"它能连上我"没有泄露任何新权限 | 全部 |
| unix socket（受文件权限约束） | 对端是**同一个 OS 用户**的进程，同用户进程本来就能读写你的文件、改你的配置 | 全部，高危操作确认 |
| HTTP/WS 只监听 loopback | 同上（只有本机进程能连） | 同上 |
| HTTP/WS 监听非环回 | **什么都证明不了** | 只读 + 对话；不具批准权（§5），且**不能驱动免批准执行的会话**（见下） |

最后一行的 `untrusted` 不是"比较不可信"，而是**"没有身份，因此不能给它自主权"**——这才是它和另外两行的真正区别。

#### 权威被攻破怎么办：那是权威的问题

一个自然的反应是"那就对中继来的连接保守一些"。**不应当这么做**，有两个理由。

**理由一：会得出荒谬结论。** 从手机登录自己的账号访问自己的机器，权限不能低于一个未经认证的本地进程。对照 SSH 就很清楚——没有人会因为"你是从手机来的"而降权。

**理由二：本机没有做二次限制的立足点。** 把一台机器注册到权威服务，这个动作**本身就是一次显式的授权声明**——"我同意这台机器由组织纳管"。授权发生在注册那一刻；之后在本机再加一道门，等于对同一个已经做出的决定要求第二次同意。

**所以本机 web 与桌面端能做的，经权威的已认证通路照样能做，没有分级。**

| 通路 | 能力 |
|---|---|
| 本机（stdio / loopback） | 全部 |
| **经权威的已认证通路** | **同样全部** |
| 未认证通路（监听非环回的裸 HTTP/WS） | 只读 + 对话（见上一节表格最后一行） |

##### 风险归位：权威必须自己承担的五件事

权威被攻破的风险属于**权威这个组件的安全责任**，不是本机权限模型的输入。因此它必须自己承担：

1. **认证强度** —— 账号、令牌、二次验证
2. **密钥与凭据管理** —— 断言的签名密钥怎么存、怎么轮换
3. **授权粒度** —— 至少节点级，理想还要操作级（"能连这台机器但只能看"）
4. **审计** —— 谁、从哪台设备、连了哪台机器、做了什么
5. **快速撤销** —— 手机丢了、员工离职，必须能立刻切断该身份的全部通路

第 5 条在"通路与全权等价"的前提下尤其重要：**既然不再有本机的二次拦截，撤销就必须快且彻底。** 这是权威服务的待定项「绑定的生命周期」的实际内容。

##### 本机的退出机制：关闭中继

机器的主人如果不想接受这个依赖，有一个**本机开关：关闭「允许经权威转发」**。关掉之后，那台机器彻底不经权威可达。

**这个开关的性质要说清：它不是缓解措施，是退出机制。**

| | 权限降级（已否决） | 关闭中继（本项目定） |
|---|---|---|
| 结果 | 可达但被削弱 | **完全不可达** |
| 权限模型 | 需要第二套规则 | **不增加任何规则** |
| 语义 | 含糊（"能连但不能批准"） | 清晰（"连不上"） |

**不要试图用"关一半"的方式解决问题。** 要么接受权威的整套安全模型并给全权，要么不参与——中间状态既解释不清也测不干净。

**开关与"使用权威的能力"是两件事，因为方向相反**：

| | 方向 | 开关 |
|---|---|---|
| 使用权威提供的能力（模型端点、知识库……） | **出站**：核心层主动调用权威 | 登录即有 |
| 允许经权威被接入 | **入站**：权威把外部客户端的流量转给你 | **独立开关** |

所以关闭中继**不影响**继续使用权威的模型端点等能力——两者本就独立。用户可以"只用你的模型与知识库，但不让你连进来"。

**默认值与告知**：建议默认开启（登录权威的主要动机之一就是远程接入），但**必须在登录/注册流程里明示**，开关要容易找到、状态要显眼可查。不能让用户处于"不知道自己可以被远程接入"的状态。

**关闭后仍可能被远程接入**——AI SSH 与远控是别的通路，与权威无关（见 04 §二的三种形态对照）。要真正不被远程接入，还得管住那些通路。

**本机开关不被任何外部策略覆盖。** 关闭之后，中继服务**没有任何路径**能连上这台机器：核心层不**监听**公网端口，也不接受任何入站连接；它与中继服务之间唯一可能的通路，是**核心层自己发起的那条出站连接**。关闭中继即关掉这条连接上的中继用途。**这不是"拒绝"，是"没有通道"。**

**中继服务侧的策略管的是别的事**：切断某条已建立的中继、不允许某个用户使用中继、整体关闭中继功能、IP 白名单。这些只影响"哪些客户端能经中继到达哪些已开启中继的节点"，**影响不到某台机器开不开**。两侧职责不交叉，也不存在"组织强制开启"这件事。

**默认值（建议）：默认关闭，由用户显式开启。** 理由是"开了就代表你愿意被中继"这句话，只有在"开启是刻意动作"时才成立。代价是远程接入——登录权威的常见动机之一——需要多一步操作。

##### 一处此前写错的地方（已撤销）

本文档先前要求"连接必须显式标记是否经中继，不得靠地址推断"，理由是"权威服务与核心层同机时，中继流量看起来来自环回"。**这个理由不成立**——中继是**核心层自己发起的出站连接**，核心层天生知道那条通道是什么，不存在把它误判为本机用户的可能。

**该要求撤销。** 判断依据只需要一个：**这条通路是否已完成身份认证。** "是否经中继"最多作为诊断与审计的元数据保留，不是权限输入。

#### 低信任通路能驱动吗：与自主级别的一道门槛

§4 的降级策略处理了"无人应答"的情形，但有一个更容易被忽略的漏洞：

**若会话的自主级别是"完全访问"，agent 不会请求任何批准——那么"不具备批准权"就完全不起作用了。** 一个 `untrusted` 通路的客户端只要发一句话，agent 就会照做，等于间接拿到了执行权。

所以两条轴的关系**不是能力取交集，而是一道门槛**：

> **自主级别允许免批准执行时，只有「结构性等价于本机用户」的通路，或「已认证且有授权」的通路，才能驱动该会话。**

| 会话的自主级别 | 谁能驱动它 |
|---|---|
| 变更前确认（默认） | **任何通路**都可以。未认证通路也能发消息，因为危险操作要人批准，而批准权在可信通路手上（§5） |
| 自动编辑 / 完全访问 | **只有本机等价通路，或已认证且有授权的通路** |

这样表述的好处：它把"谁来驱动"与"要不要批准"的依赖关系说清楚了，而不是含糊地给每种通路各列一份能力清单——后者正是前面几版一直在犯的错。

### 三条轴（第四条已取消）

| 轴 | 谁定的 | 决定什么 |
|---|---|---|
| **通路来历** | 通路的创建方式（绑定属性） | **未认证通路**能获得多少自主权 |
| **身份与授权** | 认证结果 + 授权策略 | **已认证通路**能用哪些节点、哪些能力 |
| **自主级别** | 会话配置（人设定的执行模式） | **agent 自己决定多少事、多少事要问人** |

**曾经有过的第四条已被取消**：先前把"信任级别"与"外部权威的断言"当成两条可叠加的轴并建议取交集。那是错的——第一条轴的定义就是"**没有身份时**的判断依据"，有身份时它不适用，谈不上相乘。

举例区分后两条：身份与授权说"你能连 test-server 但不能连 prod"；自主级别说"在这个会话里 agent 改文件前要不要问"。

**顺带一条归类**：同一账号在不同设备上能力不同（手机只读、借来的电脑只读）这类诉求，全都属于**身份与授权**轴，不属于通路来历。

### 为什么 unix socket 是 `local` 而不是 `implicit`

`implicit` 的信任来自"父进程能 spawn 我"，这在 stdio 下是结构性保证。unix socket 的信任来自文件系统权限——**同一个用户的其他进程能连上，而且这个 socket 的生命周期长于启动它的那个 shell**。所以是"本地可信"而不是"隐式可信"，高危操作仍需确认。

**诚实说明**：这是本矩阵里最弱的一处区分。它更多是 UX 差异（要不要多点一次"允许"）而非安全边界——两者的对端其实是同一类主体（同用户进程）。**若认为这个区分不值得，`implicit` 与 `local` 可以合并成两级**，代价是 stdio 的免确认也会对 unix socket 生效。

### 关于 HTTP 的默认裁剪

默认关闭工具执行，意味着经 HTTP 的壳子可以看会话、发消息、切模型，但**agent 在服务主机上执行工具时不会被这个壳子批准**。

这带来一个需要显式处置的情形：HTTP attachment 与 stdio attachment 同时挂在一个会话上，agent 需要批准一次工具执行——答案是 §5 的路由，请求发给 stdio 那条，HTTP 只旁观。**若该会话上只有 HTTP attachment**，则没有可承载交互的对端，按 §4 降级。

## 四、降级策略（必须显式定义）

当无可承载交互的 attachment 时，核心层的行为必须由策略明确指定，**不能是"等着"**。

v1 默认策略：**拒绝该操作并向所有 attachment 报告。**

被否方案与原因：

| 被否方案 | 否掉的原因 |
|---|---|
| 默认放行 | 把"没有人在看"当成"用户同意"，等于远程无人值守时自动提权 |
| 挂起等待 | 死锁：没有对端能应答，等待永远不会结束。这是这类系统最常见的死锁来源 |
| 静默失败 | 用户看到 agent 卡住，没有任何线索 |

策略是否可配属于业务（待定项 P-4）。

## 五、交互请求路由规则

**先按身份分，再按来历分。**

1. **已认证的 attachment**：**广播——所有 attachment 都显示，首个应答生效，其余同步关闭**（已决）
2. **未认证的 attachment**：按通路来历排序（`implicit` > `local` > `untrusted`）；`untrusted` 不具应答权
3. **若会话上有已认证的 attachment，优先路由给它**；只有在没有已认证 attachment 时，才用第 2 条的来历排序

### 为什么已认证时是广播而不是择一

**因为多个 attachment 不是多个上下文，而是同一个会话的多个视图。**

手机与桌面连的是**同一个服务层、同一个数据层**——它们的状态本来就是同步的。既然会话状态同步，交互请求没有理由不同步：一端显示而另一端不显示，等于人为制造不一致。

由此推出的两条：

- **不做"把请求发给某台设备"这种路由**。先前设想的"择一"是实现复杂度的自找，它要为"哪个 attachment 更该收到"引入一套规则，而收益只是少弹一个窗
- **"哪台设备"不参与路由**。它可以记进审计（"是手机批准的"），但不用于决定请求发给谁。见 04 §三"低信任通路能驱动吗"——那一条按**是否已认证**分，与设备无关

**去重仍然必需**：广播意味着多处同时可答，必须保证同一个请求不会被重复应答而导致状态错乱（首个应答生效、其余收到同步关闭，后续应答被忽略）。

## 六、绑定的开放集合

绑定是**开放集合**：v1 交付一组（stdio、unix socket、HTTP+SSE、WebSocket），新增绑定是**加一个包**而不是改核心层（01 §3）。

具体分帧方式、认证机制属于实现（附录 B），不属于基准——它们随传输与环境变化，且不影响任何架构决策。

**唯一需要在基准里固定的分帧相关约束**：采用行分隔 JSON 的绑定**必须按字节切分，禁止使用语言内置的行读取器**。原因是 JSON 字符串里可以合法包含 `U+2028` / `U+2029`，而部分运行时的行读取器会把它们当作换行。这一条不是风格建议，它会导致消息被静默截断。

## 七、认证与暴露面

- **stdio 与 unix socket 绑定**：信任来自进程关系与文件权限，不需要认证
- **HTTP 与 WebSocket 绑定**：**v1 仅监听 loopback**

最后一条是硬约束：监听非 loopback 时，若无认证配置则**拒绝启动**。v1 不支持远程，但也不允许出现"无意间暴露了一个无认证的端口"。要么显式配置认证（v2 的能力），要么只监听本机。

**v1 不做 TLS。** 远程场景依赖 TLS + 认证，打包在后续版本（待定项见 07）。

握手里已经预留了认证字段（03 §3 的能力协商机制），v1 恒为空。这是**置位不实现**——目的是让 v2 加远程能力时不必改协议结构。

## 八、跨绑定一致性要求

同一个命令序列经不同绑定必须产生一致的会话状态变化。这是规则 1 的可验证形式，也是测试要求：对同一组命令，分别经不同绑定执行，断言产出的会话内容与事件顺序一致。

允许的差异只有三条：能力集合、交互请求的承载方式、分帧与寻址细节。**不允许**出现在会话状态、记录内容、事件顺序上。
