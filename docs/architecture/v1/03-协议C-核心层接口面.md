# 03 · 协议 C：核心层接口面

**级别：基准**（三面划分与各面的语义不变量；改动须记入变更集。具体命令、消息形状、事件类型属实现级，见附录 B）

## 一、核心层职责

核心层是 headless 的智能体本体。它承担：

| 职责 | 说明 |
|---|---|
| 会话生命周期 | 创建、加载、切换、分支、克隆、重命名 |
| agent loop | 驱动模型调用与工具循环 |
| 工具执行 | 工具在**核心层所在主机上**实际执行 |
| 资源与插件 | 从数据层加载技能、提示词、主题、插件（§7） |
| 人类交互中转 | 把"需要人回答的问题"转成交互请求发给控制层，等待应答（§6） |
| 持久化 | 一切经数据层写入，核心层不绕过数据层直接读写会话文件 |

核心层**不渲染界面**，**不知道对端是什么传输**（01 §3）。

## 二、为什么必须分三个面

最直觉的做法是只定义一套"客户端发请求、服务端回响应"。这个做法在第三个面上必然崩掉，所以协议 C 从一开始就分三面：

| 面 | 方向 | 语义 | 为什么不能与其他面合并 |
|---|---|---|---|
| **命令面** | 控制层 → 核心层 | 请求-应答 | 基础能力，但表达不了流式输出 |
| **事件面** | 核心层 → 控制层 | 单向、有序、可重放 | 模型输出是流式的，token 逐个产生；用轮询模拟流式会引入延迟与竞态 |
| **交互面** | **核心层发起** → 控制层应答 | 阻塞式 | **最容易被漏掉的一面。** 工具执行需要人类批准时，是**服务端需要问客户端**，方向与命令面相反。硬塞进请求-应答模型会导致死锁或需要额外通道 |

三面划分属**基准**。新增绑定、新增命令都不影响它。若有人提议"用一套统一 RPC 简化一下"，那是在提议放弃交互面——代价见 04 §4。

## 三、握手：三条语义不变量

连接建立后先握手。握手的消息形状属于实现（附录 B），但它必须满足三条：

### 1. 能力声明与能力授予必须分离

控制层声明自己**能承载什么**，核心层回告自己**实际授予什么**。两者分开。

**理由是可诊断性**：当一个操作被拒绝时，必须能区分两种原因——"这个绑定承载不了"（配置/设计问题）与"能承载但信任不足"（策略问题）。只有一个能力列表时，这两种情况在错误信息里长得一样，排查会非常痛苦。

### 2. 版本双向校验

双方都必须校验对方版本，不支持则**显式拒绝**。

### 3. 从不静默降级

版本或能力不匹配必须是显式错误，不允许"尽量兼容"。

"尽力而为地解析未知格式"是数据损坏类事故的经典成因：一方按旧语义解释新格式，静默产生错误结果。pi 的 experimental 协议反过来（明确声明"无兼容性承诺"）也说明了这个问题的真实存在。

新增可选能力走能力协商，**不升版本号**；只有改变既有消息语义才升版本号。

## 四、命令面：覆盖范围

命令面必须覆盖四类操作。**具体命令清单与参数形状属于实现（附录 B），不属于基准**——业务会带来新命令，把清单写进基准意味着每次加功能都在改架构。

| 类别 | 必须覆盖 |
|---|---|
| 会话生命周期 | 新建、列出、取状态、取历史、取分支结构、分叉、克隆、重命名 |
| 驱动 | 发起一轮对话、运行中介入、排队后续消息、中止、清空队列 |
| 配置 | 切换模型、切换思考层级、手动压缩上下文 |
| 工具直调 | 直接执行工具（**受信任矩阵约束**，见 04 §3） |

三类响应形态不变量：成功、失败（带可诊断的错误标识）、以及**解析失败**——解析失败的响应必须能被识别，且不能假设请求里可用来关联的信息一定可用。

**关于照搬 pi 的命令清单**：v1 的实现建议直接采用 pi 的 rpc 命令集（附录 B 列出），理由是那份清单是实际使用中收敛出来的而非设计出来的。但这是**实现建议**，不是基准——若业务需要不同的命令划分，直接改。

## 五、事件面：三条不变量

事件面是单向、有序、可重放的流。事件类型属于实现（附录 B）。三条不变量：

### 1. 流式增量不是权威，落盘才是权威

流式内容增量**仅用于展示**，可能合并、可能乱序、可能丢失。权威信号是"这条内容已经落盘"。

**推论**：控制层在收到权威信号之前，不得把累积的增量标记为"已保存"。

把流式增量当作权威会导致客户端渲染出未落盘的内容，崩溃后用户看到的与磁盘不一致。这条与 02 §6 的顺序不变量是同一件事的两面。

### 2. "一轮结束"不等于"完成"

一轮对话结束之后**可能还有后续自动工作**（agent 触发了新的工具链等）。真正的完成信号是"不再有任何自动工作待办"。

控制层不得在一轮结束时解除"运行中"状态。

### 3. 必须支持中途挂载与断线续传

- **中途挂载**：一个新连上的控制层必须能渲染当前状态，因此必须有"取状态快照 + 取历史"的能力，不能只有事件流
- **断线续传**：控制层重连时带上次收到的位置，核心层补齐缺失部分

这两条依赖 §四的会话游标（02 §3 第 3 条）。

**游标失效必须有显式信号**：若发生了会导致游标失效的事件（例如格式迁移重写了会话文件），核心层必须主动通知所有 attachment 重新全量同步，而不是让控制层带着失效的游标继续。

## 六、交互面

**方向与命令面相反：核心层发起，控制层应答。**

交互请求分两类：

| 类 | 语义 | 例子 |
|---|---|---|
| **阻塞式** | 需要应答，请求与应答按标识配对 | 选项、确认、单行输入、多行编辑 |
| **通知式** | 不需应答，发完即忘 | 提示、状态、进度、标题 |

**为什么阻塞式与通知式要分开**：它们的可靠性要求完全不同。通知可以丢（丢一条状态更新无伤），阻塞式不能丢也不能重复应答（丢一次权限确认会让 agent 永久挂起）。混成一套会导致要么通知被过度保障，要么确认被轻率处理。

### 核心层的义务：绝不无限阻塞

核心层发出阻塞式交互请求后等待应答，**必须有超时，且超时后的行为必须由策略显式定义**。

- 超时或无法投递时，按策略处置，**默认是拒绝该操作并报告**，而不是放行
- 若当前没有可承载交互的 attachment，请求不应发出，直接走降级

这条看起来是常识，但它是这类系统最常见的死锁来源。完整策略与被否方案见 04 §4。

## 七、插件与资源

核心层从数据层加载四类资源：**插件、技能、提示词模板、主题**。

**插件即 pi extension**（ADR-006）。核心层内嵌 pi 的 extension 运行时，而不是自建插件系统。理由：pi 的扩展面已覆盖需要的一切（工具注册、命令注册、事件订阅、扩展间通信、免编译加载、包分发），且它的资源目录分类正好与数据层的四类资源对应。工作量因此是**适配而非实现**。

可行性依赖 `[假设 #4]`。

**加载失败不得致命**：单个插件加载失败不应导致核心层启动失败——记录错误、跳过该插件、上报给控制层即可。理由是插件是用户可随意增删的第三方代码，一个坏插件不该让整个智能体不可用。

**v1 不做插件隔离**，理由见 01 §4：插件信任 = 文件系统所有权，隔离是假边界。

## 八、attachment 模型

一条 attachment = 一个控制层连接挂到某个会话上的挂载记录。

- 一个会话可以有**多条** attachment（多个壳子同时看同一个会话）
- 每条 attachment 携带绑定的信任级别与核心层授予的能力
- 交互请求按**信任级别**路由（04 §5）
- **attachment 是内存态，不写入数据层**。核心层崩溃后 attachment 消失，控制层重连后重建。持久化 attachment 只会带来"陈旧 attachment"的清理问题而没有收益
- 同一连接重复挂载同一会话是幂等的
