# 00 · 实现设计

本文是 ucode 的**工程实现设计**：仓库与目录组织、包划分与职责、调用与运行方式、构建与测试、以及实现步骤。

它**不改架构**——架构见 [../spec/01-架构.md](../spec/01-架构.md)（基线 `spec-baseline`）。本文只回答"代码怎么摆、包怎么分、怎么跑、按什么顺序做"。涉及对 spec 的**细化**处会显式标出。

标记沿用 spec：**【已决】**（已确认）/ **【实现级】**（可直接替换）。

## 一、仓库组织

pnpm workspaces 单仓多包。

```
ucode/
├── package.json            私有根，只放脚本与 devDeps
├── pnpm-workspace.yaml     workspaces + catalog（统一依赖版本）
├── tsconfig.base.json      共享编译选项
├── biome.json              lint + format
├── .npmrc
├── .gitignore
├── README.md
├── docs/
│   ├── spec/               定稿架构（spec-baseline）
│   └── impl/               本设计
├── spike/                  承重假设验证脚本（dev-only，可弃）
├── packages/               库与共享代码（被依赖，无独立部署）
│   ├── protocol/           @ucode/protocol        协议 C/B 的消息类型（叶子）
│   ├── branding/           @ucode/branding        品牌配置与资源（叶子，构建期注入）
│   ├── data-layer-spec/    @ucode/data-layer-spec 协议 D 规范 + 一致性套件（叶子）
│   ├── store/              @ucode/store           协议 D 参考实现
│   ├── core/               @ucode/core            协议 C 服务端
│   ├── bindings/{stdio,rpc,http,ws}/
│   ├── sdk/                @ucode/sdk            headless 控制层 SDK
│   └── ui/                 @ucode/ui              React 组件与视图模型
├── apps/                   可部署产物（有入口）
│   ├── cli/                @ucode/cli             bin: ucode（内置 web/tui）
│   ├── web/                @ucode/web
│   ├── desktop/            @ucode/desktop   Electron
│   └── tui/                @ucode/tui       Ink
└── hub/                    @ucode/hub             单独部署的服务（可缺省，删之不影响主产品）
```

`pnpm-workspace.yaml`：

```yaml
packages:
  - "packages/*"
  - "packages/bindings/*"
  - "apps/*"
  - "hub"

catalog:
  typescript: "^7.0.2"
  zod: "^4.6.5"
  react: "^19.0.0"
  # …其余共用依赖统一在此声明，包内以 "catalog:" 引用

# 依赖的构建脚本逐个显式表态（pnpm 12 起默认全部拦截）：
# 只有 esbuild 需要平台二进制；pi 依赖树里的 @google/genai 与 protobufjs 不需要。
allowBuilds:
  esbuild: true
  "@google/genai": false
  protobufjs: false
```

**【实现级】** 命名一律 `@ucode/*`（B-7 暂不发布，先私有 scope）。`hub/` 在顶层但纳入同一 workspace，可用 `workspace:*` 复用 `protocol`/`branding`。包 scope 与 bin 名是**编译期标识**（写在 `package.json` 里）；源码里则不得出现产品名与数据层目录名——两者不同，后者由品牌门禁强制（§五）。

## 二、包划分与职责

| 包 | 职责 | 内部依赖 | 对外导出 | 备注 |
|---|---|---|---|---|
| **protocol** | 协议 C 的命令/事件/交互消息类型，协议 B 的线格式类型；用 **Zod** 定义 | 无 | 类型 + Zod schema + 解析器 | **细化 spec §7.2**：新增此叶子包，使 bindings 不依赖 core |
| **branding** | 品牌配置（productName / dataDirName / appId / vendor / theme）与资源（logo/图标/主题） | 无 | `getBrand()` + `brand.json` | **构建期单品牌**；B 端换配置重打包（见 §五） |
| **data-layer-spec** | 协议 D 的类型；一致性套件工厂 | 无 | `createConformanceSuite(factory)` | 任何实现传入工厂即跑全套 |
| **store** | 协议 D 参考实现（layout / session-repo / owner / index-cache / migration / atomic / guards） | data-layer-spec | `openStore({ dataDir })` → `Store` | 唯一写会话文件者 |
| **core** | 协议 C 服务端：握手、attachment、session-runtime（包住 pi）、commands、events、ui-broker、resources、tools | store, protocol, pi | `createCore({ dataDir, modelRuntime? })` → `Core` | 不含任何传输 |
| **bindings/\*** | 传输适配：序列化、寻址、流式；每个传输一个包 | protocol | `createBinding(core)` → 传输句柄 | **不依赖 core**；绑定之间不互相依赖 |
| **sdk** | headless SDK：按绑定建连、命令封装、事件折叠、断线续传 | bindings/*, protocol | `connect({ endpoint })` → `AgentSdk` | 不含 DOM |
| **ui** | React 组件 + 视图模型（状态来自 sdk） | sdk, protocol | React 组件与 hooks | 只被 web/desktop 复用 |
| **apps/web** | 浏览器宿主 | ui | Vite 应用 | `@ucode/web` |
| **apps/desktop** | Electron 主进程（托盘/通知/OS 凭据）+ 渲染进程复用 ui；spawn 核心层 | ui | Electron 应用 | `@ucode/desktop` |
| **apps/tui** | Ink 终端宿主 | **sdk**（不复用 ui） | bin | `@ucode/tui` |
| **apps/cli** | 启动入口：**内置 web 与 tui**，启动核心层 | core, bindings/*, apps/web, apps/tui | bin `ucode` | 单独部署的 uhub/desktop 不含在内 |
| **uhub** | 服务端：登录、准入、审计、中继、能力目录 | protocol | 服务 + 长连接中继进程 | **顶层、单独部署**，可缺省 |

**【实现级】包内文件划分**见 spec §7.1；各包内部按职责分文件，不在本文重复。

## 三、依赖图与边界

```
apps/web, apps/desktop ──▶ ui ──▶ sdk ──▶ bindings/* ──▶ protocol
apps/tui ───────────────────────▶ sdk
core ──▶ store ──▶ data-layer-spec
core ──▶ protocol
uhub ──▶ protocol
apps/cli ──▶ core, bindings/*, apps/web, apps/tui
branding ──▶（叶子；core、apps/cli、apps/web、apps/desktop、apps/tui、ui、uhub 读取）
```

**严格单向**，由 `tools/check-boundaries.ts` 的**允许列表**在 CI 拦截（策略数据在 `tools/boundaries.json`：每个包允许依赖什么，而不是禁止什么）。两条必须守住的边界：

1. **bindings 不依赖 core**（细化 spec §7.2）。原因：spec §7.3 要求"只装 `apps/web` 时依赖树里不出现 `core`"。若 bindings→core，则该验收必然失败。于是把协议 C 类型下沉到叶子包 `protocol`，core 与 bindings 都只依赖它。
2. **sdk 保持 headless**：不 import ui、不假设 DOM；TUI 因此能只复用 sdk。

**【实现级】为什么不用 dependency-cruiser**：它依赖 TypeScript 编译器的 JS API，而本项目用 TS 7（原生编译器，尚未发布 JS API）——在 TS 源码上它会巡游 0 个模块，**门禁会静默失效**（已实测）。门禁因此自建，用 Oxc 的解析器（`oxc-parser`）取导入说明符，与 TS 版本解耦；顺带把"声明了却没导入""导入了却没声明""相对导入穿墙"一并纳入检查。若将来 dependency-cruiser 支持 TS 7，可把它接回来当第二道校验——允许列表数据保持单一来源。

## 四、调用与运行方式

### 4.1 CLI 子命令

```
ucode core start --data-dir ~/.ucode --binding stdio
ucode core start --data-dir ~/.ucode --binding rpc --socket ~/.ucode/run/core.sock
ucode core start --data-dir ~/.ucode --binding http --port 0        # 非 loopback 且无认证则拒绝启动
ucode web --port 3000        # 启动内置 Web 壳（核心层 + HTTP/SSE + 静态资源，同一端口）
ucode tui                    # 启动内置 TUI 壳（默认自己拉起一个核心层）
ucode provider add --base-url <OpenAI 兼容端点> --model <模型名> --api-key <密钥>
ucode provider list          # 列出当前可用模型
```

**【实现级】`provider` 子命令**是落地时补的：首次可用必须有个把模型端点写进数据层的地方（F-5.3）。
它写的就是数据层的 `models.json`（本地权威，与基座约定一致），所以 `PI_CODING_AGENT_DIR=<数据层>`
时 pi 生态看到的是同一份定义；密钥只落文件、不入库。

`uhub` 与 `desktop` 各有独立入口，**不由 `ucode` 启动**：uhub 单独部署；桌面壳是 Electron 应用（内含 spawn 核心层）。

### 4.2 核心层启动流程

```
解析参数
 → openStore(dataDir)        权限/危险文件系统/版本前向拒绝
 → 争 owner                   心跳与抢占见 spec §3.5/§3.12
 → createCore(...)            构造协议 C 服务端（不绑传输）
 → binding = createBinding(core)   按 --binding 选一个传输
 → binding.listen()           就绪
```

### 4.3 壳连接方式

| 壳 | 连接方式 |
|---|---|
| desktop | Electron 主进程 **spawn 核心层子进程 + stdio**（默认）；也支持连已运行的 unix socket |
| web | HTTP+SSE 或 WebSocket 连核心层（loopback） |
| tui | unix socket 或 stdio |
| 测试 | 进程内 `createCore` + `connect`，或 spawn + 纯协议客户端 |

### 4.4 编程接口（测试与嵌入用）

- `createCore({ dataDir, modelRuntime? })` → `Core`（协议 C 服务端，传输无关）
- `createBinding(core, options)` → 传输句柄
- `connect({ endpoint })` → `AgentSdk`
- `openStore({ dataDir })` → `Store`
- `createConformanceSuite(storeFactory)` → 一致性测试

## 五、品牌与产品标识（brand profile）

**产品名、logo、数据层目录名、appId 等属"运行期品牌"，是构建期注入的单一事实来源，不在代码里硬编码。**

- 载体：`packages/branding/`（`@ucode/branding`）——`brand.json` + `assets/`（logo/图标/主题 token）+ 类型化读取器 `getBrand()`。
- 字段：

```jsonc
{
  "productName": "ucode",
  "dataDirName": ".ucode",
  "appId": "com.earendil.ucode",
  "vendor": "Earendil",
  "urlScheme": "ucode",
  "theme": "default"
}
```

- 消费点：

| 消费方 | 读什么 |
|---|---|
| 核心层 | 数据层**默认**目录 `~/${dataDirName}`（仍可被 `--data-dir` / 环境变量覆盖） |
| CLI | `--help` / `--version` 的 `productName` |
| Web / 桌面壳 | 标题、logo、favicon、主题；桌面另取 Electron `appId` / 产品名 |
| 打包 | electron-builder 的 `appId` / `productName`；Web 的 `<title>` / favicon |
| uhub | 登录页与文档的 `productName` / logo |

- **粒度：构建期单品牌**——brand profile 在构建期注入；B 端定制 = **换一份 `branding/`（配置 + 资源）、重新构建**，代码与协议不动。
- **包 scope**（`@ucode/*`）属编译期标识，B 端 fork 时机械替换即可（与改名同类操作，零架构影响）。
- **协议 D 不受影响**：它只规定"目录以内"的布局；"目录叫什么"是品牌参数。

**步骤 0 的项**：建 `branding` 包与默认 profile；核心层/CLI 的默认目录从它读，**禁止再出现字面量 `.ucode`**。

## 六、构建、测试与 CI

| 项 | 做法 |
|---|---|
| 语言/模块 | TypeScript 7（ESM）；dev 期**不构建**——`exports` 指向 `src/*.ts`，由 Node 原生类型剥离直跑源码 |
| 构建 | 库包用 `tsc`（emit 推迟到需要产物的步骤，见 D-3）；`apps/web` 用 Vite；`apps/desktop` 用 electron-builder；`hub` 用 TanStack Start |
| 测试 | Vitest（各包）；`data-layer-spec` 套件由 `store` 测试驱动 |
| Lint/格式 | Biome |
| 依赖边界 | `tools/check-boundaries.ts`（允许列表，Oxc 解析器，不依赖 TS 编译器 API） |
| 品牌门禁 | `tools/check-brand-literals.ts`（源码里禁止产品名 / 数据层目录名等品牌字面量） |
| 假模型供应商 | 核心层测试用录制式假 provider（见 spec §7.4），不依赖真实模型 |

**CI 必跑的两个验收任务**（spec §7.3）：

1. **核心独立安装**：空目录只装 `core` + 一个绑定包 → 启动 → 纯协议客户端完成握手/对话/取历史 → 退出码 0。
2. **反向验收**：只装 `apps/web` → 断言依赖树里**不含 `core`**。

## 七、实现步骤

按 spec §7.5 的 M1–M6，展开为可执行任务。**每步都有可判定的验收**。

### 步骤 0 · 工程脚手架（M1 前置）——**已落地**

- 仓库骨架：根 `package.json`、`pnpm-workspace.yaml`（含 catalog 与 allowBuilds）、`tsconfig.base.json`、`biome.json`、`.npmrc`、`.gitignore`、`vitest.config.ts`。
- 15 个包/应用的 `package.json` + `tsconfig.json` + 占位入口，依赖按 §三 的图声明（内部依赖一次声明齐，外部工具链随各自步骤引入）。
- `branding`（`brand.json` + 类型化读取器）与 `cli`（最小 `ucode --help`，文案全部由品牌派生）。
- 门禁：`tools/check-boundaries.ts`（允许列表）+ `tools/check-brand-literals.ts`（品牌字面量），并配自测 `tests/gates.spec.ts`——**注入违规必须被拦、合法态必须通过**，避免"配置存在"式自证。
- 验收（已跑通）：`pnpm install`、`pnpm -r typecheck`、`biome check`、两个门禁、`pnpm test`、`ucode --help`；反向验收：只装 `@ucode/web` 时依赖树里不含 `core`（允许列表的 `forbiddenTransitive` 规则 + `pnpm --filter @ucode/web list --depth Infinity` 人工复核）。

### 步骤 1 · 数据层（M1）——**已落地**

- `data-layer-spec`：协议 D 类型 + `createConformanceSuite` 骨架。
- `store`：`layout`（路径与转义）→ `atomic`（临时文件+rename）→ `guards`（权限/危险FS/路径安全/版本前向拒绝）→ `session-repo`（追加式树、游标=行号）→ `owner`（目录锁+心跳 mtime+抢占）→ `index-cache`（派生数据对账）→ `migration`（**迁移须按 spec §3.11/§3.12：原地重写、通知重同步**）。
- 验收：一致性套件全绿；两进程抢 owner 恰好一方成功；kill 持锁进程后可接管。

### 步骤 2 · 核心层 + stdio 绑定（M2）——**已落地**

- `protocol`：握手 + 命令面 + 事件面 + 交互面的消息 schema（【实现级】清单见 spec §4）。
- `core`：`handshake`（能力声明/授予分离、版本双校验、身份载荷）→ `session-runtime`（包住 pi，订阅→转译→**先落盘再广播**）→ `attachment` → `commands/*` → `ui-broker`（超时与降级）。
- `binding-stdio`：JSONL，**按字节切分**（禁用 readline）。
- 验收：纯协议客户端完成握手 → 新建会话 → 对话 → 完整事件流 → 取回历史（即 CI 验收 1）。

### 步骤 3 · 交互面 + 多 attachment + 跟随（M3）——**已落地**

- `ui-broker`：阻塞式/通知式、超时与降级策略、广播路由与去重。
- `core`：多 attachment 注册表；非 owner 跟随（`fs.watch` + **轮询兜底**，见 spec §3.12、V-10）。
- 验收：第二个控制层挂载收到全量重放 + 增量且不获应答权；高信任 attachment 断开后路由正确移交。

### 步骤 4 · 其余绑定 + 信任矩阵（M4）——**已落地**

- `binding-rpc`（长度前缀）/ `binding-http`（SSE+POST）/ `binding-ws`。
- 信任矩阵生效、能力声明与授予分离、非 loopback 无认证拒绝启动。
- 验收：HTTP 上工具执行被拒并给出可诊断原因；无法承载的交互请求走降级而非挂起。

### 步骤 5 · Web 壳 + TUI 壳 + 桌面壳（M5）——**已落地**

- `sdk`：连接、reducer、resume。
- `ui` + `apps/web`（Vite）：UI 以 ZCode 为蓝本。
- `apps/desktop`（Electron，复用 ui）：主进程 spawn 核心层 + 托盘/通知/OS 凭据。
- 验收：杀掉核心层再拉起，壳自动重连并用游标补齐，UI 不丢不重。

### 落地记录：实现时才暴露出来的约束

这一节记的是"读设计时看不出来、写下去才发现"的东西。它们都属【实现级】，但踩过一次就该留痕。

| # | 约束 | 影响 |
|---|---|---|
| I-1 | **Node 的原生类型剥离不支持 JSX** | 被 Node 直接执行的包（`core` / `bindings/*` / `sdk` / `apps/cli` / `apps/tui`）只用 `.ts` + `createElement`；只有经打包器处理的 `apps/web` 用 `.tsx`。 |
| I-2 | **基座的 `entry_appended` 在正常对话路径不触发**（只覆盖扩展追加、上下文编辑等少量路径，实测确认） | `session-runtime` 改为**按差异落盘**：每次事件后比对内存态管理器的记录，把新增的追加进数据层，成功后才广播。副作用是"先落盘再广播"由我们自己的顺序保证，比依赖基座事件更硬。 |
| I-3 | **索引是派生数据，而写它的是别的实例** | `listSessions` 必须与磁盘 mtime 对账，否则跨实例会一直读到旧索引（真实运行里表现为"侧栏条目数不动"）。 |
| I-4 | **SSE 是长连接** | 优雅退出时 `server.close()` 会一直等连接自己结束；必须 `closeAllConnections()` 强制断连，否则 SIGTERM 之后进程不退出。 |
| I-5 | **前端选择器不能返回新建的数组/对象** | 否则快照恒变、React 无限重渲（表现为整页白屏）。派生数据在组件里用 `useMemo` 算。 |
| I-6 | **壳子只依赖 `sdk`** | 传输工厂做成 sdk 的子路径（`@ucode/sdk/http`、`@ucode/sdk/stdio` …）：浏览器只 import 自己那一份，`node:net`/`node:child_process` 不会进打包结果；同时保住 `apps/* → sdk` 这条依赖边，不新增 `apps/* → bindings/*`。 |
| I-7 | **Electron 的主进程与 preload 不能有 TS 语法** | 它们不经打包器直接加载：主进程用 `.mjs`（类型剥离不适用，只能纯 JS），preload 必须是 **CommonJS**（沙箱里的 `require` 只认 electron 与少数内置模块，`node:fs` 都不可用——品牌配置因此由主进程读，经 IPC 递给渲染进程）。 |
| I-8 | **Electron 二进制的下载** | 默认源可能拉不动；`ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node apps/desktop/node_modules/electron/install.js` 可手动补。 |

**进程级验收**（`tests/e2e.test.ts`）：起真实核心层进程 + **纯协议客户端**（不依赖 sdk）跑通
握手 → 建会话 → 对话 → 完整事件流 → 取回历史，stdio 与 HTTP 各一遍；
`tests/http-binding.test.ts` 覆盖线格式、交互配对与"非环回拒绝启动"；
`tests/sdk-http.test.ts` 覆盖 sdk 的请求-应答配对与带游标续传。

### 步骤 6 · 多实例 + 远程（M6，后续）

- 多实例指向同一数据层、writer/reader 角色正确。
- WebSocket 绑定启用认证 + TLS；节点注册表、远控、AI SSH、uhub 中继。
- 验收：同机两实例共享数据层；远程通路不改协议即可接入。

> **`V-8` 的落点**：步骤 6 之前需补"持久化待决交互"的核心层状态机（释放运行资源、应答后恢复），否则 M6 的无人值守不成立。可作为步骤 5.5 单列。
