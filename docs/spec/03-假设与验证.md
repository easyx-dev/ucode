# 03 · 假设与验证

本文是 ucode 的**技术假设验证台账**，并记录**已确认的业务输入**。标记含义见 [00 §标记说明](00-需求与功能.md)。

- **技术假设 `V-n`** —— 缺的是**事实**（外部组件的实现行为、技术可行性）。验证结论会决定 [01 架构](01-架构.md) 的具体章节是否成立。
- **业务输入 `B-n`** —— 已由业务方确认（见 §二），是确定项，不改变架构骨架。

**为什么不散落在各章**：多份清单 = 没有清单。所有未验证事项以本文台账为准，正文只做内联标记。

---

## 一、技术假设

这些假设验证的是外部组件的**实现行为**，不是它的**文档承诺**。两者会不一致，且升级可能改变行为；`V-1`/`V-2` 在基座每次小版本升级后都值得复验——它们是架构与基座耦合最紧的两个点。

### V-1 会话文件严格只追加

**假设内容**：基座写会话文件时只追加，从不重写或截断已有字节。压缩、历史编辑、打标等操作都表现为追加新记录。

**为何重要**：[01 §3.3](01-架构.md) 的四条会话性质与 [01 §3.7](01-架构.md) 的整个多实例方案建立在此之上。owner 追加写记录，其他实例靠**跟随同一文件的追加流**获得实时进展。若会重写已有字节，跟随失效。

**验证做法**：

1. 准备测试仓库与一段会话脚本，覆盖：普通对话、工具调用（读文件）、**触发压缩**、手动压缩、历史编辑、打标；
2. 每步之后计算文件的内容哈希与长度，记录三元组；
3. 断言：任一步的哈希必须是上一步哈希的**前缀延伸**（`newContent.startsWith(oldContent)`），长度单调不减；
4. 额外检查 inode 是否变化（若用"写临时文件再 rename"重写，inode 会变，长度可能不变）。

**若不成立**：[01 §3.7](01-架构.md) 作废，多实例需改为显式实例间通道（引入服务发现、连接、认证、重连），或退化为非 owner 实例定期全量重读。

**验证结论（2026-09-26，pi 0.87.1）：成立（限 v3 会话）。** 两轮对话与全部"修改类" entry（自定义消息、会话信息、自定义数据、模型切换、思考层级、用量、打标、历史编辑、压缩）均为前缀延伸、大小单调、inode 不变。证据见 `spike/README.md` 与 `spike/results/v1.json`。

### V-2 pi 持久化可被接管

**假设内容**：能把基座的持久化重定向到指定数据层目录（理想情况是让它直接读写 `~/.ucode` 的会话目录），或用会话管理器完全接管持久化。

**为何重要**：决定 `store` 的定位是**唯一真相**还是**镜像 + 索引**。若可行，数据层就是唯一真相，[01 §3](01-架构.md) 全部规则按设计生效；若不可行，数据层降级为"镜像 + 索引"，存在两个真相源，必须在 [01 §3.6](01-架构.md) 重新论证"先落盘再广播"的顺序保证。**这是影响面最大的一项。**

**验证做法**：

1. 显式传入自定义会话管理器，跑一轮对话，检查默认目录下是否出现新会话文件（出现即说明没被接管）；
2. 设目录覆盖环境变量，跑一轮，检查会话文件是否落在指定目录；
3. 分别用会话目录覆盖的三种设法各试一次，观察是否**只**写指定目录；
4. 分别测试"进程内嵌入"与"子进程 CLI"两种宿主方式，因为两者行为可能不同。

**若不成立**：[01 §3.1](01-架构.md) 对数据层的定义需要修订——数据层降级为"持有权威副本"；需新增一节说明两个真相源的不一致如何处置。

**验证结论（2026-09-26，pi 0.87.1）：成立。** `PI_CODING_AGENT_DIR` 生效（配置与会话一起重定向）；SDK 用 `SessionManager.create(cwd, sessionDir)` 可显式接管会话目录；`inMemory()` 不落盘；**无旁路双写**。宿主差异：`PI_CODING_AGENT_SESSION_DIR` 仅在 CLI 宿主生效，SDK 宿主需显式传 manager。证据见 `spike/results/v2.json`。

### V-3 pi 容忍会话目录下的非会话文件

**假设内容**：基座在会话目录下遇到非 `.jsonl` 文件（锁、索引、辅助文件）时不报错、不误解析。

**为何重要**：决定锁与派生数据能否与会话同层；锁的位置影响 owner 竞争的原子性设计。

**验证做法**：在会话分桶目录下分别放一个目录、一个 `.json`、一个 `.lock`，验证"列出会话"与"按 id 加载会话"两条路径是否有错误、警告或被误当会话解析。

**若不成立**：把锁与辅助文件全部移出会话目录，[01 §3.2](01-架构.md) 的状态分类更新。**影响面小，但必需在 M1 前确定。**

**验证结论（2026-09-26，pi 0.87.1）：成立。** 会话桶内放子目录、`index.json`、`x.lock` 与非法 `bad.jsonl`，`list` 均忽略它们，`open` 与 `findById` 正常。证据见 `spike/results/v3.json`。

### V-4 进程内 TS 插件运行时可以嵌入非本基座宿主

**假设内容**：在我们自己的进程里加载用户放在数据层插件目录下的 `.ts` 插件，并让工具注册、命令注册、事件订阅、扩展间通信都正常工作。

**为何重要**：决定插件是**嵌入运行时**（工作量是适配）还是**自建运行时**（从零实现加载、卸载、依赖、事件总线、工具注册，工作量最大）。这是四项中工作量差异最大的一项。

**验证做法**：

1. 写一个最小宿主进程，指向一个测试插件目录；
2. 测试插件内容覆盖：注册工具、订阅事件、扩展间通信；
3. 断言：插件被加载（工厂被调用）、工具注册成功、事件订阅收到回调、扩展间可通信；
4. 重点观察是否有隐含宿主上下文依赖。期望"没有 UI"这一状态为假而非抛错；
5. 再测"通过自定义工具注入"路径能否注册工具并被 agent 真实调用。

**若不成立**：[01 §4.9](01-架构.md) 的进程内层改为自建运行时，插件契约需自行定义，且与基座生态无法互通，会削弱"选它作基座"的理由。

### V-5 会话格式迁移不在加载时自动写回

**假设内容**：基座加载旧版本格式的会话文件时，不会立即迁移并写回。

**为何重要**：若会写回，则"只追加"在某些会话上不成立，游标（行序号）可能变化，[01 §3.3](01-架构.md) 与 §3.12 的游标实现受影响。

**验证做法**：用一个旧版本格式的会话文件加载一次，观察文件是否被改写（哈希、长度、inode）。

**若不成立**：迁移必须被当作显式的、需通知全体 attachment 重新全量同步的事件（[01 §4.5](01-架构.md)），并在 [01 §3.12](01-架构.md) 补充迁移写回的处置。

**验证结论（2026-09-26，pi 0.87.1）：推翻。** 把会话 header 版本改回 v2 / v1 后加载，文件被**原地重写**为 v3：前缀断裂、**inode 不变**、大小仅变 1 字节。→ 迁移**必须**作为显式重同步事件（[01 §4.5](01-架构.md) 已如此规定）；且跟随者**不能只靠 inode 变化**检测整体替换（见 [01 §3.12](01-架构.md)）。证据见 `spike/results/v5.json`。

### V-6 工作区文件/Git 结构化查询的实现载体

**假设内容**：能实现 [01 §4.7](01-架构.md) 的工作区结构化查询通道（文件树增量刷新、Git 图谱分页加载、变更筛选）。

**为何重要**：控制层渲染文件树与 Git 图谱需要它；没有它，控制层无法自己列出工作区。**不能用工具调用（跑 `ls`/`git log`）代替**——那会把 UI 性能绑在命令解析上。

**验证做法**：确认基座是否已提供等价的查询能力；若无，验证自建该通道（在核心层实现、经协议 C 暴露）的可行性，并确认其在各绑定与中继上的承载方式。

**若不成立**：需自建并纳入实现范围，工作量增加；受影响的后续功能包括文件树、Git 图谱、变更筛选。

### V-7 PTY 字节流通道的实现与承载

**假设内容**：能实现 [01 §4.7](01-架构.md) 的 PTY 字节流通道（双向字节流 + 窗口尺寸变更 + 信号），并在各绑定与 uhub 中继上正确承载。

**为何重要**：终端面板与 AI SSH 控制台共用这条通道；[ADR-016](02-决策记录.md) 要求中继覆盖它。

**验证做法**：验证通道在 stdio / unix socket / WebSocket / HTTP+SSE 各绑定上的实现方式（HTTP 需配对或独立流），以及经中继转发时的透明字节承载。

**若不成立**：终端面板与 AI SSH 控制台改用进程内伪终端 + 消息封装（体验下降）；或该能力延后。

### V-8 持久化待决交互在基座上的介入点

**假设内容**：能在基座的 agent loop 上实现"会话进入等待态并释放运行资源、应答后恢复、重启后待决请求仍在"（[01 §4.11](01-架构.md)）。

**为何重要**：[ADR-020](02-决策记录.md) 的无人值守是后续版本的一等需求。

**验证做法**：确认 agent loop 是否提供可介入的挂起/恢复点，或是否需要在核心层用自己的状态机包住它；验证会话状态可被完整序列化与恢复。

**若不成立**：无人值守需自建会话状态机与调度，工作量增加；定时/闲时任务受影响。

### V-9 清单式子进程 hook 的可行性与事件覆盖

**假设内容**：能实现 [01 §4.9](01-架构.md) 的清单式插件（JSON + Markdown + 子进程 hook），且 hook 事件覆盖所需。

**为何重要**：清单式是插件的分发默认形态。

**验证做法**：定义子进程协议（stdin 一行 JSON、stdout JSON + 退出码、matcher、超时、聚合 deny/ask/allow），验证可覆盖所需事件集。

**若不成立**：插件默认形态需调整，或事件覆盖需缩窄。

### V-10 多实例文件跟随在目标平台的可靠性

**假设内容**：在目标平台上，"监听文件变更 + 按位置跟随"能可靠地让非 owner 实例实时获得进展，配合轮询兜底后不丢进展。

**为何重要**：它是 [ADR-008](02-决策记录.md) 的实现基础；若可靠性不足，会退化为"定期全量重读"。

**验证做法**：在目标平台验证文件变更通知的漏事件率与轮询兜底效果；覆盖部分读取、文件被整体替换、迁移后游标三类情形。

**若不成立**：改为定期全量重读（实时性差但简单），或引入显式通道。

## 二、业务输入（已确认）

由业务方拍板，全部取推荐方案。

| 编号 | 结论 | 它决定什么 |
|---|---|---|

| B-7 | **暂不发布**到公共包仓库 | 命名与版本策略 |

| B-9 | **沿用 pi 配置键 + 少量新增** | [01 §3.2](01-架构.md) 配置类 |
| B-10 | **节点级准入**（与"通路与全权等价"一致） | [01 §6.3](01-架构.md) 可用性语义 |

## 三、风险登记

| 风险 | 说明 | 处置 |
|---|---|---|
| **技术假设未坐实** | `V-1`/`V-2` 若不成立会推翻数据层方案，而非打补丁 | M0 先跑，结论回写 [01](01-架构.md)；不通则重新选基座，不带不确定性前进 |
| **对基座实现细节的耦合** | `V-1`/`V-2` 依赖的是实现行为，升级可能改变 | 每次基座小版本升级后复验；M0 产出为可重跑脚本 |
| **中继可见会话内容** | 端到端加密暂不做，uhub 在被转发路径上能看到全部内容，被攻破时可读可改 | 已知并接受；保留"uhub 只按通道转发不透明字节、不解析协议 C"这条约束，保住将来加它的可能性（[ADR-013](02-决策记录.md)、[01 §6.3](01-架构.md)） |
| **B 端集中诉求与 per-host 冲突** | 客户可能要求会话集中、离职回收、内容审计 | 已决"会话留在各 host"（[ADR-017](02-决策记录.md)）；这些诉求列为独立的后续能力，不混进首发 |
| **无回调的远程能力后补** | 远程能力若事后补会被迫重设计协议 | 首发即在协议 C 预留认证字段、在信任矩阵预留未认证行（[01 §5.3](01-架构.md)） |

### 执行顺序

`V-2` 优先（决定数据层是唯一真相还是权威副本），随后 `V-1`（决定多实例方案），`V-3` 必须在 M1 前确定；`V-4` 与 `V-5`~`V-10` 可并行。每个假设产出一个**独立可重跑**的脚本，便于基座升级后复验。

**已完成（2026-09-26，pi 0.87.1）：`V-2`、`V-1`、`V-3` 已确认；`V-5` 已推翻。** 脚本在 `spike/`，可用 `node v2-persistence.ts` / `v1-append-only.ts` / `v3-tolerance.ts` 重跑。剩余：`V-4`、`V-6`~`V-10`。
