## ADR-001 数据层是一个目录，不是数据库

**决策**：数据层 = 一台机器上的一个目录（默认 `~/.ucode`），核心层以目录路径为入口参数。所有持久状态（配置、模型、凭据、会话、插件、资源）都在这个目录里。

**理由**：

1. **可被独立实现**。目录布局是规范，任何语言都能实现，并有配套一致性测试套件。
2. **可检查**。可 grep、可备份、可人工审阅、可版本控制，事故排查成本远低于二进制文件。
3. **可移植**。整目录搬家即迁移，包含配置与插件，不需要导出/导入流程。
4. **业务扩展点天然**。资源目录就是目录，用户直接放文件即可，不需要数据库写入 API。

**被否方案：SQLite 作为数据层真相。**
否掉的原因不是"SQLite 不好"，而是它解决的正是我们愿意自己承担的问题（跨进程锁与跨进程 ID 分配），真正否掉它的是前两条——协议化与可检查性。一个二进制文件无法成为"任何语言都能实现的规范"。

**被否方案：每会话一个 JSONL 但目录结构自定。**
否掉的原因：与 pi agent-dir 布局不兼容，失去"数据层即 pi 超集"的生态杠杆。

**代价（已知并接受）**：文件锁与一致性由我们实现；需处理网络文件系统与云同步目录的失效情形；需防范派生数据损坏（靠"派生数据必须可丢弃"把事故降级）。

## ADR-002 划分三个协议 D / C / B

**决策**：数据层协议（D）、核心层接口面（C）、绑定线格式（B）三者独立定义、独立演进。

**理由**：三者面向不同的实现者，耦合任意两者都会导致其中一个无法被独立实现。
- 把数据层格式混进核心接口 → 数据层无法被独立实现；
- 把传输细节混进核心接口 → 新增绑定就要改核心。

**被否方案：单一协议（一套 RPC 覆盖全部）。**
否掉的原因：它在交互面上必然崩掉——核心层需要向控制层发起请求（权限确认），方向与请求-应答相反。

**被否方案：两个协议（数据层 + 一个统一对外协议）。**
能工作，但代价是绑定层与核心层的边界模糊，实现时容易把传输逻辑放进核心。三面划分是把边界写进文档的手段。

## ADR-003 核心层与绑定层分离，核心不知道传输

**决策**：核心层只对外暴露一套与传输无关的接口面；绑定层只做序列化、传输、寻址。

**理由**：

1. **新增绑定不改核心**。这是"暴露多种操作协议"这个需求的前提。
2. **核心层可 headless 运行**，不假设对端是终端、浏览器还是桌面应用。
3. **有先例**。pi 的核心只问 `ctx.hasUI`，从不问是哪种传输。

**被否方案：核心层内建 stdio 支持，其他传输作为附加。**
否掉的原因：那是长驻子进程、JSONL over stdio、单客户端的形态，撑不起多客户端与远程壳子。它可以作为一种绑定实现，但不能作为架构。

## ADR-004 信任级别是绑定的属性

**决策**：信任级别由绑定声明，能力由核心层按信任矩阵授予。同一命令在不同绑定上可能被授予或拒绝。

**理由**：命令面里有 `bash` 与 `prompt`，`prompt` 会触发工具调用，即在服务主机上任意执行代码。若信任是协议级属性，那么一条暴露到公网的 WebSocket 就等于把主机交给任何能连上的人。这是"壳子直连异地服务"能否安全实现的唯一保障。

**被否方案：认证即全权（认证通过就授予全部能力）。**
否掉的原因：把"身份"与"权限"合并，无法实现"远程壳子可以看和说，但不能在主机上执行命令"这个常见需求；而且认证是二值的，权限需要是集合。

**被否方案：由控制层自报信任级别。**
否掉的原因：对端声称自己可信，等于没有信任模型。

## ADR-005 交互请求在已认证 attachment 上广播

**决策**：同一会话多条 attachment 时，已认证的通路**广播**交互请求——所有 attachment 都显示，首个应答生效，其余同步关闭；未认证通路按来历排序，`untrusted` 不具应答权。路由**先按身份分，再按来历分**。

**理由**：

1. **多个 attachment 是同一个会话的多个视图**，不是多个上下文。它们连的是同一个核心层、同一份数据层，状态本就同步；交互请求没有理由不同步。
2. **不做"发给某台设备"的路由**。"哪台设备更该收到"要引入一套规则，而收益只是少弹一个窗。
3. **去重仍然必需**：首个应答生效，其余同步关闭，后续应答忽略。

**被否方案：只发给信任级别最高的 attachment。**
否掉的原因：与"多 attachment 是同一会话的多个视图"矛盾，等于人为制造两端不一致；且"哪台设备"不参与路由是本架构的既定原则。

**被否方案：由客户端在 attach 时声明自己是否愿意处理交互。**
否掉的原因：这是"对端声称自己可信"。信任级别必须由绑定声明，不能由客户端选。

## ADR-006 插件分层：清单式为主 + 进程内 TS 可选

**决策**：插件分两层。**清单式**（声明式，无代码，可跨语言，进程外）为分发默认形态；**进程内 TS**（可注册工具与模型供应商）为可选高性能层，复用 pi 的 extension 运行时，只能来自本机显式安装或用户自建。**来自市场/远端的插件不得包含进程内代码。**

**理由**：

1. 两层能力不同：进程内能注册工具/供应商、能订阅完整事件、但也能崩掉核心层、能读内存中的凭据。
2. 清单式无代码、可跨语言、可兼容外部生态，适合作为分发默认形态。
3. 新安全规则的必要性：本地安装插件的信任等于文件系统所有权，但"来自市场的进程内插件"其作者不是那个能写你目录的人——原论证在此不成立。

**被否方案：只做进程内 TS（自建或复用 pi extension）。**
否掉的原因：与跨语言、与"分发不带代码"的能力目标冲突，且把市场插件的安全模型暴露在本机。

**被否方案：只做清单式。**
否掉的原因：无法注册新工具与新模型供应商，扩展面过窄。

## ADR-007 不做插件隔离

**决策**：对本地安装的插件不做沙箱、权限提示或能力限制。

**理由**：**插件信任 = 文件系统所有权。** 能写数据层插件目录的人本来就能改这个目录里的一切——改配置、把模型定义指向自己的端点、读走凭据，也包括直接编辑会话记录。在这种前提下做插件沙箱是**假边界**：沙箱拦的是插件，拦不住那个能写目录的人。提示的对象也是本来就有完全控制权的人。

**这个决策不是"暂时不做"，而是"在当前信任模型下没有意义"。** 它在信任模型改变时才需重开，即出现"安装来自不受信任来源的进程内插件"时——这已由 ADR-006 的安全规则处置。

## ADR-008 数据层文件兼作实例间事件总线

**决策**：owner 实例往会话文件追加记录，其他核心层实例通过**跟随该文件的追加流**获得实时进展，**不实现实例间专用通道**。

**理由**：消除一整类复杂度。走显式通道需要：服务发现、连接建立、认证、双向协议、断线重连、事件去重。而数据层文件天然是广播介质——owner 本来就要写它，其他实例本来就有读权限。

**代价与前提**：依赖"会话文件严格追加"（[03 V-1](03-假设与验证.md)）；跟随机制有若干实现坑（变更通知不可靠、部分读取、文件被整体替换）；非 owner 实例不参与交互应答。

**被否方案：owner 通过 IPC/网络广播给其他实例。**
否掉的原因：需要实现上述全部机制，而这些机制只为让非 owner 看到进展——用文件跟随几乎免费地达到同样效果。

## ADR-009 不复用 pi 的实验性 server/client/protocol

**决策**：不复用 pi 的实验性服务器/客户端/协议作为服务层基座。

**理由**：它在形态上几乎就是本架构（多实例注册、会话可有多个 attachment、CBOR + unix socket），但成熟度不足以作地基：明确标注 experimental 且无兼容承诺、source-only、**协议层无认证**、client 不自动重连与重放、依赖 unix socket。

**被否方案：直接采用它，省掉协议设计。**
否掉的原因：省的是设计工作，押上的是把地基放在一个随时可能变的、无认证的实验性协议上；而我们的协议设计并非从零开始（命令面与交互面语义沿用了它的形状），"自己设计"的实际增量不大。

**重新评估的时机**：若该层去掉 experimental 标记、补上认证、进入正式分发，值得重开——届时可能改为"用它的协议作为协议 B 的一种绑定"。

## ADR-010 会话采用追加式树结构

**决策**：会话存储为**追加式记录流**，记录之间通过**父指针**构成树而非线性列表。对既有内容的修改（压缩、编辑历史、打标）以追加新记录的方式表达。

**理由**：

1. **父指针是对的分支模型**。分支（分叉/克隆）不需要复制历史，只需指向更早的记录。
2. **追加式表达修改**同时带来三个好处：多实例可跟随（ADR-008）、崩溃后只需处置尾部、写入无需原子性。
3. **省掉一轮设计**。无论是否采用具体格式，"带父指针的追加式记录流"都会收敛到相似形状。

**被否方案：线性消息列表 + 原地修改。**
否掉的原因：分支要复制历史；原地修改破坏追加式，连带作废 ADR-008 与数据层的两条不变量。

**被否方案：关系型模型（消息表 + 分支表）。**
否掉的原因：见 ADR-001；且关系模型要表达"追加式修改"需要额外的版本列。

## ADR-011 首发控制层 = Web + 桌面

**决策**：控制层首发送代 **Web 壳与桌面壳**（共享 React 组件层；桌面含托盘、通知、OS 凭据等廉价本机能力）；TUI 与移动端属后续。桌面用 Electron，经 **spawn + stdio** 连核心层。

**理由**：

1. **Web 与桌面共享组件与全库 TS，一起做的边际成本远低于分开做**——桌面壳在 Web 壳之上只多一层宿主集成（本身也有 ADR-022 支撑）。
2. 桌面承接本机能力（托盘、通知、OS 凭据），是后续远控与内置浏览器落地的前提。
3. Web 壳仍是**验证协议的最佳载体**——它天然是"另一个进程、另一套交互模型、可能远程"，能暴露协议设计的问题。

**被否方案：首发只做 Web 壳，桌面后续。**
否掉的原因：桌面用 Electron + React 与 Web 共享组件，拆开做等于把同一套 UI 维护两遍、把宿主集成推迟；一起做的成本更低。

**被否方案：TUI 优先。**
否掉的原因：TUI 与核心层同机、交互模型接近，会掩盖协议设计缺陷（如交互面的方向反转在 TUI 下不容易暴露），且难以验证多客户端挂载与远程场景。TUI 属后续。

## ADR-012 协议版本双向校验、从不静默降级

**决策**：握手时双方都必须校验对方版本，不支持则**显式拒绝**。新增可选能力走能力协商，**不升版本号**；只有改变既有消息语义才升版本号。

**理由**：

1. **"从不静默降级"是防事故规则**。尽力而为地解析未知格式，是数据损坏类事故的经典成因——一方按旧语义解释新格式，静默产生错误结果。
2. **能力协商与版本号分离**，让"新增一个可选能力"不需要双方同步升级。
3. **能力声明与能力授予分离**，让"操作被拒"可诊断——区分"承载不了"与"信任不足被拒"。

**被否方案：语义化版本（semver）。**
否掉的原因：协议版本需要的是"是否兼容"这一个比特，三个数字带来的主要是沟通成本。此为实现层取舍。

**被否方案：只做向后兼容。**
否掉的原因：实践中"向后兼容"通常意味着静默降级，与理由 1 冲突。

## ADR-013 能力走工具层，协议保持窄

**决策**：新增能力一律以「工具提供者 / MCP 服务」形式接入，不往协议 C 里加消息。协议 C 只承载会话、事件、交互，外加固定的通道集合。

**理由**：

1. 避免协议膨胀与"每加一个能力就动核心层"。
2. 已出现三个形状相同的实例：桌面壳的内置浏览器、第三方 agent browser、uhub 的各类能力，全部走工具接入。
3. 它使"加能力"默认不需要架构讨论，决定了后续每次加能力的成本。

**被否方案：每新增一类能力就往协议 C 加一种消息。**
否掉的原因：协议迅速膨胀，每次新增都要动核心层与所有绑定。

**例外（被显式承认）**：模型端点是**驱动 agent 的东西**，而非 agent 用的工具，因此以模型供应商配置接入，不属"工具"。

## ADR-014 通道即身份

**决策**：核心层与 uhub 之间的通道由核心层主动 dial 到配置地址并走 TLS，**证书校验即完成"对端确实是 uhub"**。身份断言只作为信息性载荷随 attachment 传递，**不需要签名、验签、公钥分发或轮换**。

**理由**：

1. **签名防的是一个在拓扑里不存在的威胁**：断言在传递途中被第三方篡改。传递途中没有第三方，就是核心层与 uhub 之间的 TLS。
2. **签名对真正的威胁毫无用处**：uhub 被攻破或内部人员作恶时，它签的断言就是它自己的谎话——签名挡不住签名者。真正能缓解的是端到端加密。
3. 核心层对断言的处理因此只剩一件：记下"这条 attachment 属于谁"。

> **可复用原则**：核心层主动 dial 到配置地址 + TLS ⇒ 通道本身就是身份，不需要第二套信任机制。

**被否方案：uhub 签发断言，核心层用公钥验签并处理密钥轮换。**
否掉的原因：见上两条。

## ADR-015 AI SSH 是能力，不是执行后端

**决策**：AI SSH 以工具形式暴露，是一种**能力**；默认工具仍在核心层主机执行。

**理由**：

| | 当作执行后端 | 当作能力（本项目） |
|---|---|---|
| 默认工具在哪执行 | 可能被整体切到远端 | 仍在核心层主机 |
| 远端离线时 | 该会话工具全失败 | 只有这一个能力不可用 |
| 与逐轮改动集的关系 | 冲突扩大到所有工具 | 冲突只限它自己发起的改动 |
| 与 ADR-013 的关系 | 是个例外 | **又一个实例** |

**被否方案：把 AI SSH 做成执行后端（所有工具重定向到远端）。**
否掉的原因：远端离线会拖垮整个会话；与逐轮文件改动集冲突面过大；背离"能力走工具层"。

## ADR-016 中继覆盖全部通道

**决策**：uhub 中继必须承载协议 C 的**全部通道**（消息面、工作区文件/Git 查询、PTY 字节流），且新增通道时不需要重新设计中继。

**理由**：通道类型从设计一开始就是一等概念（[01 §1.4](01-架构.md)）。否则中继模式下终端（PTY）与文件树（工作区查询）会失效——而这两条正是协议 C 新增的通道。

**被否方案：中继先只转发 JSON 消息，字节流以后再补。**
否掉的原因：会导致两条通道在中继模式下不可用，事后补要重新设计中继的通道模型。

## ADR-017 会话数据留在各 host

**决策**：会话数据留在各 host 的数据层，**不做集中存储**。

**理由**：保住了数据层最核心的 per-host 不变量。
- 数据层仍是 per-host 的；
- "用户 A 经 uhub 连到机器 B，看到的是机器 B 上的会话"——数据没搬家；
- 多用户的影响因此被限定在访问层，不侵入数据层模型。

**被否方案：会话集中存储到 uhub。**
否掉的原因：一旦选择集中，数据层就从 per-host 变成中心化，协议 D 几乎要重写。B 端的集中诉求（离职回收、内容审计、换机恢复）属于**独立的后续能力**，不混进首发设计。

## ADR-018 关闭中继是本机退出机制

**决策**：本机提供「允许经 uhub 转发」开关，**建议默认关闭、由用户显式开启**。关闭后那台机器**没有通道**可达。

**理由**：

1. 它不是缓解措施，是**退出机制**：要么接受 uhub 的整套安全模型并给全权，要么不参与。中间状态（权限降级）既解释不清也测不干净。
2. "开了就代表你愿意被中继"这句话，只有在"开启是刻意动作"时才成立。
3. 机制上：核心层不监听公网端口，与 uhub 唯一的通路是它自己发起的出站连接；关闭即关掉这条连接上的中继用途——**不是"拒绝"，是"没有通道"**。
4. 开关与"使用 uhub 的能力"是两件事，方向相反：使用能力是**出站**（登录即有），被接入是**入站**（独立开关）。关闭中继不影响继续使用模型端点等能力。

**被否方案：对中继连接做权限降级（可达但被削弱）。**
否掉的原因：会得出荒谬结论（从手机登录自己的账号访问自己的机器，权限低于一个未经认证的本地进程）；且需要第二套规则，语义含糊。

**被否方案：中继服务侧强制某台机器开启中继。**
否掉的原因：做不到，也不需要做——两侧职责不交叉。

## ADR-019 项目级作用域只减不增

**决策**：项目级配置只能**关**（关闭能力），不能**开**（Hook、命令、自动连接的外部服务一律不允许）。

**理由**：项目配置是你刚 clone 的别人的代码，构成第三类信任边界。携带可执行内容等于"以你的身份运行他人的代码"，与"关闭能力"这种纯声明式动作的风险完全不同。规则越简单越容易被遵守：**它能关，不能开。**

**被否方案：项目级允许 Hook，但默认禁用。**
否掉的原因：默认禁用靠一个开关，一旦被打开就是在本机执行他人代码；而"只减不增"根本不给这个开关。

**被否方案：项目级允许自动连接 MCP。**
否掉的原因：自动连接的外部服务同样是在你机器上跑、用你的凭据，与 Hook 是同一份风险。团队共享 MCP 的需求改用组织级分发解决。

## ADR-020 无人值守采用持久化待决交互

**决策**：无 attachment 时不采用"拒绝/挂起"，而是**持久化待决交互**：请求写入数据层，会话进入等待态并释放运行资源，任何人/设备/时间应答后恢复，重启后待决请求仍在。超时策略可由"拒绝"降级为"agent 自决"。

**理由**：无人值守是一等需求（定时/闲时任务要跑数小时），它推翻了"必然有个客户端在等"的前提。持久化待决交互与"绝不无限阻塞"不矛盾：不阻塞指不占资源干等，而非必须立刻拒绝。

**被否方案：拒绝该操作并向所有 attachment 报告。**
否掉的原因：在无人值守下会直接终止任务，与需求冲突。

**被否方案：挂起等待。**
否掉的原因：死锁——没有对端能应答时等待永不结束。

**被否方案：默认放行。**
否掉的原因：把"没有人在看"当成"用户同意"，等于无人值守自动提权。

**被否方案：把降级策略做成可配开关。**
否掉的原因：无人值守需要的是"延后应答并保持待决"，不是"预先换一种降级行为"。

## ADR-021 自主级别是第二条权限轴

**决策**：在"绑定信任"之外新增**自主级别**（会话的执行模式：变更前确认/自动编辑/计划模式/完全访问）。有效能力 = f(绑定信任, 会话自主级别, 逐工具规则)。两条轴的关系是**一道门槛**而非能力取交集：自主级别允许免批准执行时，只有本机等价通路或已认证且有授权的通路能驱动该会话。

**理由**：

1. 绑定信任回答"这条通路可不可信"，自主级别回答"agent 在本次会话里获得多少自主权"，两者正交且都必须有。
2. 若只保留绑定信任，一个未认证通路的客户端在"完全访问"会话里发一句话，agent 就会免批准照做——"不具批准权"完全失效，等于间接拿到执行权。门槛堵住这个漏洞。

**被否方案：只保留绑定信任一条轴。**
否掉的原因：见理由 2。

**被否方案：两条轴取能力交集。**
否掉的原因：会得出"已认证远端通路比本地未认证进程权限低"这类荒谬结论；正确形态是门槛，不是逐项裁剪。

## ADR-022 控制层共享 UI 层

**决策**：控制层分出共享的 `ui/` 层（React 组件与视图模型），与 `client/`（headless 协议 SDK）分离。依赖方向为 `apps/* → ui → client → bindings/*`。Web 与桌面共用 `ui`；TUI 只复用 `client`。

**理由**：

1. Web 与桌面共享同一套交互（同以 ZCode 为蓝本），UI 与协议状态必须解耦才能复用——`client` 保持 headless，可被任意壳（含 TUI）复用。
2. 新增壳只加宿主集成，不改核心层与协议（ADR-003）。

**被否方案：每个壳各自实现 UI。**
否掉的原因：Web 与桌面的交互高度重合，重复实现会立刻分叉。

**被否方案：把 UI 与协议逻辑混在一个 `client` 包里。**
否掉的原因：会引入 DOM 假设，TUI 无法复用；壳与宿主细节会渗进共享层。

## ADR-023 品牌与产品标识参数化（构建期单品牌）

**决策**：产品名、数据层目录名、logo、appId、URL scheme 等属"运行期品牌"，集中在**品牌配置（brand profile）**里、构建期注入，代码不硬编码。B 端定制 = 换一份品牌配置与资源、重新构建。数据层默认目录由品牌派生，仍可被 `--data-dir` / 环境变量覆盖。

**理由**：

1. B 端定制会改产品名、logo 与数据层目录名；若硬编码，定制方要改代码，风险与成本都高。
2. 与"包 scope 改名"（编译期标识，机械替换）区分：品牌是**数据**，不该进代码。
3. 协议 D 只规定"目录以内"的布局，"目录叫什么"是产品参数，因此本决策不动协议。

**被否方案：多品牌运行时切换（一套二进制多品牌）。**
否掉的原因：定制交付是独立构建，运行时切换带来无收益的复杂度。

**被否方案：数据层目录名固定不可改。**
否掉的原因：用户/脚本需要 `--data-dir` 覆盖（CI、临时数据层、多实例）。
