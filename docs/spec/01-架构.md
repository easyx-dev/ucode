# 01 · 架构

本文定义 ucode 的技术构成：分层、边界、协议、不变量与依赖规则。它是实现与讨论的依据。标记含义见 [00 §标记说明](00-需求与功能.md)；关键决策的理由与被否方案见 [02 决策记录](02-决策记录.md)；尚未坐实的事项见 [03 假设与验证](03-假设与验证.md)。

**判别标准**：换一种做法，架构结论会变吗？会 → 属本文（约束，改动需记录）；不会 → 属【实现级】（可直接改，不影响结论）。文中以 **【实现级】** 标注具体格式、清单、分帧一类内容。

## §1 总览与分层

### 1.1 四层结构

```
控制层    TUI    桌面    Web    移动            ← 协议的具象化，各自独立可安装
─────────────────────────────────────────────
绑定层    stdio | JSON-RPC(uds/tcp) | HTTP+SSE | WebSocket
─────────────────────────────────────────────
核心层    对话 · agent loop · 工具执行 · skill · 插件 · 人类交互中转
（服务层）  ↑ 对外只有一套与传输无关的接口面
─────────────────────────────────────────────
数据层    ~/.ucode 目录（一台机器一个）
```

`uhub` **不属于其中任何一层，是外挂**：它作为能力提供者（模型端点、知识库、数据服务）走工具接入机制；作为通路提供者提供中继。它不实现 agent loop，也不持有会话数据。

### 1.2 三个协议

| 协议 | 定义什么 | 面向谁实现 | 边界 |
|---|---|---|---|
| **D** | 目录布局、文件格式、锁、原子写、版本规则 | 任何核心层实现（可跨语言） | 数据层目录边界 |
| **C** | 命令面、事件面、交互面、握手、能力声明 | 任何绑定层实现 | 核心层进程边界 |
| **B** | 分帧、寻址、流式、认证 | 任何控制层实现 | 每种绑定的对端边界 |

三者**独立演进**：新增一种绑定不影响协议 D；数据层换实现不影响协议 C。这是架构可被定点增补的结构前提。

**为什么是三个而不是一个**：把数据层格式混进核心接口，数据层就无法被独立实现；把传输细节混进核心接口，新增绑定就要改核心。

### 1.3 谁不知道谁存在

实现时每个"要不要 import"的问题由下表回答。

| 组件 | **不知道**这些存在 | 原因 |
|---|---|---|
| 核心层 | 绑定的任何一种传输 | 核心层只问"是否有可用 UI 承载交互"（`ctx.hasUI`），从不问是哪种传输 |
| 核心层 | 控制层的任何形态 | 不知道对端是终端还是浏览器 |
| 绑定层 | 控制层的任何形态 | 只面对协议 C 的消息 |
| 绑定层 | 其他绑定层 | 绑定之间不通信；跨绑定一致性由协议 C 语义保证 |
| 控制层 | 核心层的内部结构 | 只面对协议 B |
| store | 核心层 | 只实现协议 D，不 import 核心层 |
| 核心层 | store 之外的任何持久化途径 | 不得直接读写会话文件，一律经 store |

依赖方向，**严格单向**：

```
shells/*  →  client  →  bindings/*  →  core  →  store  →  data-layer-spec
```

反向依赖由依赖检查工具（`dependency-cruiser` 或等价物）在 CI 中拦截。

### 1.4 两条贯穿性原则

**原则一：能力走工具层，协议 C 保持窄。**
新增能力一律以「工具提供者 / MCP 服务」形式接入，不往协议 C 里加消息。已出现的同类实例：桌面壳的内置浏览器、第三方 agent browser、uhub 的各类能力。推论：**协议 C 只承载会话、事件、交互，外加固定的通道集合**；加能力的成本因此默认不需要架构讨论。

**原则二：通道类型是一等概念。**
协议 C 除消息面外，还显式定义**通道**（双向字节流与结构化查询）。通道从设计一开始就是一等概念，不是"先转发消息、字节流以后再补"——否则中继模式下终端与文件树会失效。首发定义两条通道：工作区文件/Git 结构化查询、PTY 字节流。

### 1.5 核心层的边界（措辞校准）

- **核心层的内置工具**（读写编辑、bash、搜索）在核心层所在主机执行。
- **通过 MCP 或等价机制接入的工具**在提供方所在处执行，核心层**不假设其位置**。

这是两者的固有区分，不是原则的破口。

## §2 信任模型

有三个**互相独立**的信任边界，机制不同、理由不同，不能混用一套方案。

### 2.1 三类信任边界

| 边界 | 信任来源 | 性质 | 机制 |
|---|---|---|---|
| **绑定信任** | 网络可达性 / 认证结果 | 临时；对端可能是攻击者 | 认证 + 能力矩阵，核心层强制执行 |
| **插件信任** | 文件系统所有权 | 持久，等价于登录用户身份 | **不需要机制**：能写插件目录的人本就能改数据层里的一切，做沙箱是假边界 |
| **项目配置信任** | 你刚 clone 的别人的代码 | 持久 | **项目级只减不增**（§3.9） |

**绑定信任为什么必要**：命令面里有 `bash` 与 `prompt`。`prompt` 会触发工具调用，即在服务主机上任意执行代码。任何可被非本机用户触达的绑定，都必须裁剪掉工具执行能力。

**项目配置信任为什么是独立边界**：项目配置既不是"你自己的文件系统"（插件信任那条），也不是"网络可达性"（绑定信任那条），它是别人仓库里的代码。处置方式是根本不让它携带可执行内容。

### 2.2 信任级别 = 认证的替代品

**它不是分级**，而是回答"这条通路需不需要身份认证"。判断依据是两条**互斥**分支，不是可叠加的三级：

```
连接到达
├── 这条路是否已完成身份认证？
│    ├── 是 → 按「身份 + 授权」判断（与 SSH 同构，不分级）
│    └── 否 → 按「通路来历」判断（信任矩阵）
└── 不需要认证的通路 = 结构性等价于「本机用户本人」
```

**互斥而非叠加**：用"已认证但来历是远端"去取交集会得出荒谬结论（"从手机登录自己的账号访问自己的机器，权限低于一个未经认证的本地进程"）。对照 SSH 很清楚：从手机 SSH 进自己的机器，就是自己的完整权限。

### 2.3 信任矩阵

| 通路 | 它证明了什么 | 给什么 |
|---|---|---|
| stdio（父进程 spawn） | 对端本来就是这台机器的主人 | 全部 |
| unix socket（受文件权限约束） | 对端是同一 OS 用户的进程 | 全部；高危操作需交互确认 |
| HTTP/WS 只监听 loopback | 同上 | 同上 |
| HTTP/WS 监听非环回、未认证 | **什么都证明不了** | 只读 + 对话；工具直调关闭，且**不具批准权**，**不能驱动免批准执行的会话** |

**最后一行的 `untrusted` 不是"比较不可信"，而是"没有身份，因此不能给它自主权"。**

### 2.4 已认证通路：身份与授权

- **能建立认证通路的，能力与本地对等，不做降级。** 把机器注册进组织这个动作本身就是一次显式授权声明；之后在本机再加一道门，等于对同一个决定要求第二次同意。
- 本机侧提供**退出机制**：关闭「允许经 uhub 转发」。关闭后那台机器**没有通道**可达（不是"拒绝"，是核心层不监听公网端口、也不接受入站连接，与 uhub 之间唯一的通路是核心层自己发起的那条出站连接）。建议**默认关闭，由用户显式开启**。
- 相关风险（认证强度、密钥与凭据管理、授权粒度、审计、快速撤销）归**uhub 组件的安全责任**，不是本机权限模型的输入。详见 §6.3。

### 2.5 自主级别：第二条权限轴

绑定信任之外还有一条正交的轴：**agent 在本次会话里获得多少自主权**（变更前确认 / 自动编辑 / 计划模式 / 完全访问）。

有效能力 = f(绑定信任, 会话自主级别, 逐工具规则)。

两条轴的关系**不是能力取交集，而是一道门槛**：

> **自主级别允许免批准执行时，只有「结构性等价于本机用户」的通路，或「已认证且有授权」的通路，才能驱动该会话。**

| 会话自主级别 | 谁能驱动它 |
|---|---|
| 变更前确认（默认） | **任何通路**都可以。未认证通路也能发消息，因为危险操作要人批准，而批准权在可信通路手上 |
| 自动编辑 / 完全访问 | **只有本机等价通路，或已认证且有授权的通路** |

**为什么需要这道门槛**：若会话是完全访问，agent 不请求任何批准，"不具批准权"就完全不起作用——一个未认证通路的客户端只要发一句话，agent 就会照做，等于间接拿到执行权。

### 2.6 交互请求路由

**先按身份分，再按来历分。**

1. **已认证的 attachment：广播**——所有 attachment 都显示，首个应答生效，其余同步关闭。
2. **未认证的 attachment**：按通路来历排序（stdio implicit > unix local > untrusted）；`untrusted` 不具应答权。
3. 若会话上有已认证的 attachment，优先走第 1 条；只有在没有已认证 attachment 时，才用第 2 条。

**为什么已认证时是广播而不是择一**：多个 attachment 不是多个上下文，而是**同一个会话的多个视图**——它们连的是同一个核心层、同一份数据层，状态本来就同步。由此：

- 不做"把请求发给某台设备"这种路由；"哪台设备"可记入审计，但不用于决定请求发给谁。
- **去重仍然必需**：首个应答生效，其余收到同步关闭，后续应答被忽略。

### 2.7 降级策略：持久化待决交互

当没有可承载交互的 attachment 时，核心层**不得"等着"**，也不简单拒绝：

- 请求写入数据层，会话进入等待态并**释放运行资源**；
- 任何人、任何设备、任何时间应答后恢复；
- 重启后待决请求仍在。

这与"绝不无限阻塞"不矛盾：不阻塞指不占资源干等，而非必须立刻拒绝。超时后的策略可由"拒绝"降级为"**agent 自决**"（不再只有一种处置）。

被否的处置：默认放行（把"没有人在看"当成"用户同意"，等于无人值守自动提权）、挂起等待（死锁）、静默失败（用户只看到卡住）。

## §3 数据层（协议 D）

### 3.1 定位与形态

数据层是**一台机器上的一个目录**，默认 `~/.ucode`。核心层以目录路径为入口参数启动。这是一台机器上全部持久状态的所在，也是核心层唯一的持久化入口。

**"唯一共享"的含义**：一台机器可以有多个核心层实例指向同一个目录。这是 **per-host 不变量——不跨机**。

协议 D 是这份目录规范的**协议**而非某个库的用法，因此它必须①可被任何语言实现，②附一致性测试套件。

> **已决**：数据层格式做成 **pi agent-dir 布局的超集**。收益是 `PI_CODING_AGENT_DIR=~/.ucode` 即可让 pi 生态直接读写数据层；代价是继承 pi 的会话格式演进。【待验证 V-2】【待验证 V-3】

### 3.2 状态分类

| 类别 | 内容 | 写入者 | 能否丢弃 |
|---|---|---|---|
| **配置** | 用户偏好、模型与供应商定义 | 用户；核心层受限写；**uhub 下发**（逐模型生效，仅覆盖 uhub 提供的模型） | 否 |
| **凭据** | API key、OAuth token | 用户；核心层 | 否，且**不进同步**（§3.8） |
| **上下文** | 全局提示词与项目上下文 | 用户 | 否 |
| **插件与资源** | 插件、技能、提示词模板、主题 | 用户 | 否 |
| **会话** | 对话历史与由此派生的全部状态 | **仅 owner**（§3.6） | 否 |
| **派生数据** | 索引、缓存等一切可从上面几类重建的东西 | 任何核心层实例 | **是，且必须随时可丢** |
| **锁与日志** | 协调用的锁、运行日志 | 任何核心层实例 | 锁是暂时的，日志视需要 |

**两条推论**：

1. **插件与资源是业务扩展点。** 业务功能主要通过"往这几个目录里放东西"接入，而不是改核心层代码。
2. **凭据与会话同处一个目录，但命运不同**（§3.8）。

### 3.3 会话的存储性质

协议 D 不规定会话文件的字节格式（那是【实现级】），但规定四条**性质**：

1. **追加式**。对既有内容的修改表现为追加新记录，不改写旧记录。压缩、编辑历史、打标都遵循这一条。
2. **带父指针的树**。每条记录指向父记录，分支不需要复制历史。
3. **单调游标**。每条记录可导出单调递增的序号，用于重放与断线续传。
4. **每会话独立**。游标、树、追加序列都以单个会话为作用域。

第 1 条是另外三条的前提，也是 §3.7 多实例方案的前提。【待验证 V-1】

### 3.4 不变量

1. **归属与权限**。数据层目录只对本人可读写；凭据权限更严。**权限不满足时拒绝启动**，不静默修正。
2. **非追加写必须原子**。除追加以外的任何写，要么完整生效、要么完全不生效。追加写是例外——它不修改既有内容。
3. **派生数据必须可丢弃**。派生目录内任何东西都能随时删除并在下次启动时重建；真相永远是扫描数据层本身的结果。**推论：派生数据损坏不是数据事故**，启动时对账即可修复。
4. **崩溃后可恢复**。崩溃可能留下不完整的尾部，接管者必须能识别并丢弃，不得把损坏内容当作数据。
5. **危险文件系统上拒绝运行**。目录位于网络文件系统（NFS/SMB）或被云同步（iCloud Drive/Dropbox/OneDrive）时**拒绝启动**——这两种环境下文件锁与变更通知都不可靠，并发写入会撕裂会话。
6. **版本前向拒绝**。读取者遇到高于自身的数据层版本，必须拒绝启动或转为只读，禁止"尽力而为"地解析。
7. **路径安全**。由会话标识或项目路径派生的文件路径必须经过校验，不得逃逸出数据层目录。

### 3.5 owner 语义

**一个会话同时只有一个 writer，即它的 owner。** 其他实例只读。

- owner 通过竞争产生，不由配置指定。
- owner 定期声明存活（心跳）；声明超时后其他实例可判定其已死并**抢占**，抢占时执行 §3.4 第 4 条的尾部处置。
- 优雅退出时主动释放。

**为什么需要 owner**：多个实例同时往一个会话追加会撕裂它；owner 是让"数据层唯一共享"与"多实例"共存的最小机制。竞争与心跳的具体机制属【实现级】。

### 3.6 写入顺序不变量：先落盘，再广播

核心层产生的每条会话记录，必须**先写入数据层，再向控制层广播对应事件**。顺序不能反——否则发生在两次操作之间的崩溃会让用户看到未持久化的内容，而用户会以为自己看到的东西已经保存了。这条在单实例与多实例下都成立。

### 3.7 多实例：数据层文件兼作事件总线

owner 实例往会话文件追加记录，其他实例通过**监听文件变更 + 按位置跟随**获得实时进展，**不需要实例间的专用通道**。这消掉了一整类复杂度：实例间服务发现、连接、认证、双向协议、断线重连。

依赖【待验证 V-1】。若不成立，多实例协作需改为显式通道或定期全量重读。跟随的实现注意（部分读取、变更通知不可靠、文件被整体替换）见【实现级】，可靠性另见【待验证 V-10】。

**范围边界**：非 owner 实例**不参与交互应答**（交互请求只发给 owner 实例上的 attachment，按 §2.6 路由）。

### 3.8 凭据边界

凭据与其余状态同处数据层目录，但它是唯一标注"**不进同步**"的一类。一旦目录被同步或跨机共享，凭据会跟着走，而用户通常不会预期"配置同步"等于"凭据外泄"。

登录能力引入后，凭据分**四类**，归属与生命周期不同：

| 类别 | 归属 | 已登录 | 未登录 |
|---|---|---|---|
| 自配模型凭据 | 数据层 | 保留（自配模型仍可用） | **必需** |
| uhub 模型凭据 | **uhub** | 由 uhub 持有，不下发到本机 | 不适用 |
| 节点注册凭据 | 数据层 | **新增**。证明"这台核心层属于哪个组织"，安全要求高于模型 key | 不适用 |
| 用户登录凭据 | 控制层 | 由各控制层自管（OS 凭据存储/钥匙串） | 不适用 |

### 3.9 项目级作用域：只减不增

配置分**用户级**与**项目级**。项目级配置跟着仓库走，因此它是"你刚 clone 的别人的代码"，构成第三类信任边界（§2.1）。

**规则：项目级只减不增。**

| 项目配置能做的 | 风险 |
|---|---|
| **关**：关闭能力（如关闭知识库、关闭某个 MCP） | 无。声明式的"关"不执行任何东西 |
| **开**：携带 Hook / 命令 / 自动连接的外部服务 | 高。它是"在你机器上执行、用你的凭据"，不是配置，是**以你的身份运行他人的代码** |

所以 Hook、命令、自动连接的外部服务一律不允许。团队共享 MCP 的需求改用**组织级分发**（uhub 能力或插件）解决。

### 3.10 新增的状态类别

- **临时会话**：存在但可丢弃，不进索引、不提供恢复（辅助对话用）。
- **逐轮文件改动集**：会话记录与工作区状态是两个独立的可回滚对象。**每条记录必须能对应该轮的文件改动集**，且该对应关系在终端命令介入时**明确失效**——由终端命令造成的改动不可撤销，Git 是兜底。

### 3.11 版本演进不变量

数据层里存在**两个独立版本概念**，不要混淆或合并：

| 概念 | 含义 | 演进责任 |
|---|---|---|
| 数据层协议版本 | 协议 D 本身的版本 | 我们 |
| 会话记录格式版本 | 会话文件内部格式的版本 | 沿用 pi 的格式，由 pi 演进 |

**必须独立演进**。合并的话，"升一次协议版本"会变成"必须重写所有会话文件"，而重写会作废所有客户端的游标，也与追加式冲突。

演进规则：**严格 additive**——新版本只能增加，不得改变既有语义；低版本读到高版本按 §3.4 第 6 条处置。【待验证 V-5】

### 3.12 【实现级】目录布局与文件形状

```
~/.ucode/
├── version       {"protocolVersion":1,"minReadableVersion":1}
├── settings.json 配置
├── models.json   模型与供应商定义
├── auth.json     凭据（0600，标记不进同步）
├── AGENTS.md / SYSTEM.md
├── extensions/  skills/  prompts/  themes/
├── sessions/     会话，按项目路径分桶
│   └── --<escaped-cwd>--/<timestamp>_<session-id>.jsonl
├── cache/        派生数据（含会话索引）
├── locks/        全局锁
└── logs/         日志
```

- 会话文件：JSONL，第一行为版本化 header，其后每行一条记录；记录公共字段 `type`/`id`/`parentId`/`timestamp`。
- `id` 与 `parentId` 构成树；分支就是指向更早记录的新子节点。
- 幂等与并发：临时文件 → fsync → rename（非追加写）；追加写走 `O_APPEND`。
- owner：目录锁 + 心跳 mtime；抢占取全局锁 → 校核心跳超时 → 处置尾部 → 取得 owner。
- 游标：**序号 = 记录在文件中的行序号**（header 为第 0 行），不改 pi 格式即可拿到游标。唯一例外是格式迁移（唯一允许重写的操作），此时必须主动通知所有 attachment 重新全量同步。
- 危险文件系统检测：检查是否落在已知云同步目录下，`statfs` 判断文件系统类型。

## §4 核心层接口面（协议 C）

### 4.1 核心层职责

| 职责 | 说明 |
|---|---|
| 会话生命周期 | 创建、加载、切换、分支、克隆、重命名 |
| agent loop | 驱动模型调用与工具循环 |
| 工具执行 | 内置工具在核心层所在主机执行（§1.5） |
| 资源与插件 | 从数据层加载技能、提示词、主题、插件 |
| 人类交互中转 | 把"需要人回答的问题"转成交互请求发给控制层，等待应答 |
| 持久化 | 一切经数据层写入，不绕过数据层直接读写会话文件 |

核心层**不渲染界面**，**不知道对端是什么传输**。

### 4.2 为什么必须分三个面

| 面 | 方向 | 语义 | 为什么不能合并 |
|---|---|---|---|
| **命令面** | 控制层 → 核心层 | 请求-应答 | 基础能力，但表达不了流式输出 |
| **事件面** | 核心层 → 控制层 | 单向、有序、可重放 | 模型输出是流式的，用轮询模拟会引入延迟与竞态 |
| **交互面** | **核心层发起** → 控制层应答 | 阻塞式 | 工具执行需要人类批准时是**服务端问客户端**，方向与命令面相反，硬塞进请求-应答会死锁 |

三面划分属约束。新增绑定、新增命令都不影响它。

### 4.3 握手

连接建立后先握手。消息形状属【实现级】，但必须满足三条：

1. **能力声明与能力授予分离**：控制层声明自己**能承载什么**，核心层回告**实际授予什么**。理由是可诊断性——操作被拒时要能区分"承载不了"与"能承载但信任不足"。
2. **版本双向校验**：双方都必须校验对方版本，不支持则**显式拒绝**。
3. **从不静默降级**：版本或能力不匹配必须是显式错误，不允许"尽量兼容"。

新增可选能力走能力协商，**不升版本号**；只有改变既有消息语义才升版本号。

**身份信息载荷**：握手/挂载时携带「谁、哪台设备」的身份信息，按 **attachment** 逐条给出。它只是**信息性载荷**，不涉及可验证性——核心层对 uhub 的身份确认由"核心层主动 dial 到配置地址 + TLS 证书校验"完成（§6.3），**不需要签名与验签**。核心层对它的处理只有一件：记下"这条 attachment 属于谁"，用于交互路由与审计。

### 4.4 命令面：覆盖范围

命令面必须覆盖四类操作（具体命令清单属【实现级】）：

| 类别 | 必须覆盖 |
|---|---|
| 会话生命周期 | 新建、列出、取状态、取历史、取分支结构、分叉、克隆、重命名、挂载、卸载 |
| 驱动 | 发起一轮对话、运行中介入、排队后续消息、中止、清空队列 |
| 配置 | 切换模型、切换思考层级、手动压缩上下文 |
| 工具直调 | 直接执行工具（**受信任矩阵约束**） |

三类响应形态：成功、失败（带可诊断错误标识）、**解析失败**——解析失败必须能被识别，且不能假设请求里可用来关联的信息一定可用。

**命令引用参数**：`发起一轮对话` 需要一个引用参数，可引用对象至少包括：文件/文件夹、会话、**已登记的 SSH 连接**、技能/子智能体。

### 4.5 事件面：三条不变量

事件面是单向、有序、可重放的流，事件类型属【实现级】。

1. **流式增量不是权威，落盘才是权威**。流式内容增量仅用于展示，可能合并、乱序、丢失；权威信号是"这条内容已经落盘"。**推论**：控制层在收到权威信号之前，不得把累积的增量标记为"已保存"。这与 §3.6 的顺序不变量是同一件事的两面。
2. **"一轮结束"不等于"完成"**。一轮结束后可能还有后续自动工作（agent 触发了新的工具链）。真正的完成信号是"不再有任何自动工作待办"。控制层不得在一轮结束时解除"运行中"状态。
3. **必须支持中途挂载与断线续传**。中途挂载要求"取状态快照 + 取历史"的能力，不能只有事件流；断线续传要求控制层带上次收到的位置，核心层补齐缺失部分。**游标失效必须有显式信号**：若发生导致游标失效的事件（如格式迁移），核心层必须主动通知所有 attachment 重新全量同步。

### 4.6 交互面

**方向与命令面相反：核心层发起，控制层应答。** 分两类：

| 类 | 语义 | 例子 |
|---|---|---|
| **阻塞式** | 需要应答，按标识配对 | 选项、确认、单行输入、多行编辑 |
| **通知式** | 不需应答，发完即忘 | 提示、状态、进度、标题 |

**为什么分开**：可靠性要求完全不同。通知可以丢，阻塞式不能丢也不能重复应答（丢一次权限确认会让 agent 永久挂起）。

**核心层的义务**：发出阻塞式请求后等待应答，必须有超时，且超时行为由策略显式定义（§2.7）。若当前没有可承载交互的 attachment，请求不应发出，直接走 §2.7。

### 4.7 两条通道

除消息面外，协议 C 定义两条通道（§1.4）：

1. **工作区文件/Git 结构化查询**。控制层要渲染文件树、Git 图谱、变更筛选，而工作区在核心层那台机器上。**不能用工具调用代替**：文件树需要增量刷新、Git 图谱需要分页加载，用 bash 跑 `ls`/`git log` 来喂 UI 是把 UI 性能绑在命令解析上。【待验证 V-6】
2. **PTY 字节流通道**。终端仿真需要双向字节流 + 窗口尺寸变更 + 信号，不能塞进 JSON 消息面（base64 会毁掉交互式程序的体验）。【待验证 V-7】

### 4.8 工具执行位置

- **内置工具**在核心层所在主机执行。
- **通过 MCP 或等价机制接入的工具**在提供方所在处执行，核心层不假设其位置。

### 4.9 插件与资源

核心层从数据层加载四类资源：**插件、技能、提示词模板、主题**。

**插件分两层**：

| | 清单式插件 | 进程内 TS 插件 |
|---|---|---|
| 能注册新工具 | 否 | **是** |
| 能注册模型供应商 | 否 | **是** |
| 能订阅内部事件 | 有限（子进程 hook 事件） | 完整 |
| 跨语言 | **是** | 否 |
| 能崩掉核心层 | 否（进程边界） | **是** |
| 能读核心层内存中的凭据 | 否 | **是** |

- **清单式是分发默认形态**：无代码、可跨语言、可兼容外部生态的 plugin/command/skill/hook 格式。
- **进程内 TS 是可选高性能层**：只在"需要注册新工具或供应商"时使用，复用 pi 的扩展运行时。【待验证 V-4】
- **新的安全规则**：**来自市场/远端的插件不得包含进程内代码。** 进程内 TS 插件只能来自本机显式安装或用户自建。（理由：本地安装的插件信任仍等于文件系统所有权，但"来自市场的进程内插件"其作者不是那个能写你目录的人。）

**加载失败不得致命**：单个插件加载失败不应导致核心层启动失败——记录错误、跳过该插件、上报给控制层。

### 4.10 attachment 模型

一条 attachment = 一个控制层连接挂到某个会话上的挂载记录。

- 一个会话可以有多条 attachment（多个壳子同时看同一个会话）。
- 每条 attachment 携带绑定的信任级别与核心层授予的能力，以及身份信息（§4.3）。
- 交互请求按 §2.6 路由。
- **attachment 是内存态，不写入数据层**。核心层崩溃后消失，控制层重连后重建（持久化只会带来"陈旧 attachment"的清理问题）。
- 同一连接重复挂载同一会话是幂等的。

### 4.11 无人值守

会话在没有 attachment 的情况下可持续运行（定时/闲时任务）；一条权限请求可被**延后应答**而不中断会话；核心层重启后能恢复。机制是 §2.7 的**持久化待决交互**，会话进入等待态时**释放运行资源**。这意味着"待决事项"是核心层暴露的一等**可查询状态**，控制层据此自行决定是否通知用户。【待验证 V-8】

## §5 绑定层与信任（协议 B）

### 5.1 绑定层职责

把核心层接口面适配到具体传输，**只做三件事**：序列化、寻址、流式。

绑定层里**不得出现**：会话逻辑、状态机、重试语义、业务规则、能力判断的实现（能力判断由核心层执行，绑定只**声明**自己的信任级别与承载能力）。

### 5.2 三条硬规则

1. **协议 C 定义一次，绑定只做映射**。同一命令序列经任何绑定，结果必须一致；差异只允许体现在承载能力与信任级别上。
2. **信任级别是绑定的属性，不是协议的属性**。协议 C 只收到绑定的信任级别并查表。这是"控制层直连异地服务"能否安全实现的唯一保障。
3. **交互承载能力按绑定声明，核心层必须能降级**。双向传输（stdio、unix socket、WebSocket）原生支持；纯请求-应答传输（HTTP）必须**配对**（下行推请求，上行提交应答，按标识配对）。声明不支持的绑定，核心层不得发出交互请求，而是走 §2.7。

### 5.3 信任矩阵与认证

见 §2.3、§2.4。补充暴露面规则：

- stdio 与 unix socket 绑定：信任来自进程关系与文件权限，不需要认证。
- HTTP 与 WebSocket 绑定：**首发仅监听 loopback**。监听非 loopback 时若无认证配置则**拒绝启动**——要么显式配置认证，要么只监听本机。**不允许出现"无意间暴露了一个无认证的端口"。**
- 握手预留认证字段，首发恒为空（**置位不实现**），目的是远程能力进入后续版本时不必改协议结构。

### 5.4 降级策略

见 §2.7。绑定层的职责只是：在无可用交互承载时，把核心层的降级动作正确传递。

### 5.5 分帧

采用行分隔 JSON 的绑定**必须按字节切分，禁止使用语言内置的行读取器**。原因不是风格：JSON 字符串里可以合法包含 `U+2028`/`U+2029`，部分运行时的行读取器会把它们当作换行，导致消息被静默截断。

【实现级】分帧方案：

| 绑定 | 传输 | 分帧 |
|---|---|---|
| `stdio` | 标准输入输出 | 行分隔 JSON（JSONL） |
| `rpc` | unix socket 或 TCP | 4 字节大端长度前缀 + JSON 载荷 |
| `http` | HTTP + SSE | SSE 下行 / POST 上行，按标识配对 |
| `ws` | WebSocket | 一帧一消息 |

stdio 用 JSONL（可被人直接阅读、可用 `jq` 处理），rpc 用长度前缀（纯机器通道，彻底绕开换行歧义）——两者刻意不统一。

### 5.6 跨绑定一致性

同一个命令序列经不同绑定必须产生一致的会话状态变化。这是测试要求：对同一组命令分别经不同绑定执行，断言产出的会话内容与事件顺序一致。允许的差异只有三条：能力集合、交互请求的承载方式、分帧与寻址细节；**不允许**出现在会话状态、记录内容、事件顺序上。

### 5.7 绑定的开放集合

绑定是**开放集合**：首发交付一组（stdio、unix socket、HTTP+SSE、WebSocket），新增绑定是**加一个包**而不是改核心层。具体分帧与认证机制随传输与环境变化，属【实现级】。

## §6 远程与 uhub

三种远程形态，**都不改协议 C**——这是分层的实际收益。

### 6.1 AI SSH —— 一种能力

**形态**：已登记的 SSH 连接可被引用；用户 @ 选取一个连接，agent 就在那条连接上执行远端命令。**目标机不安装任何 ucode 组件。**

**定位：能力，不是"执行后端"，也不是一种模式。**

| | 当作"执行后端" | 当作"能力"（本项目） |
|---|---|---|
| 默认工具在哪执行 | 可能被整体切到远端 | **仍在核心层主机** |
| 远端离线时的影响 | 该会话的工具全部失败 | **只有这一个能力不可用** |
| 与逐轮文件改动集的关系 | 冲突面扩大到所有工具 | 冲突只限 AI SSH 自己发起的改动 |

**两个构件**：SSH 连接登记表（命名连接：名称、主机、端口、用户、凭据引用；凭据不进数据层明文）；引用机制（协议 C 的 `prompt` 引用参数可引用已登记连接）。

**推荐实现路径：常驻 PTY over SSH**（有状态，`cd`/环境变量/交互式程序可用，控制台是真终端），**与 §4.7 的 PTY 通道是同一条通道的两个使用者**，不是两套机制。

**能力边界**：远端离线 → 只有该能力不可用；经 AI SSH 产生的远端改动**不可撤销**（远端没有我们的改动记录，靠远端自己的 Git）；**不做远端配置同步**（远端没有 ucode 组件）。

### 6.2 远控 —— 控制层（桌面壳）本地行为

**形态**：SSH 连上后**先探测目标机是否已安装核心层**；没有则安装；然后桌面壳直接接入那个服务；端口未开放时用**端口映射**打通。

**架构归属：远控不进协议。** 探测、安装、端口映射**全部是控制层宿主的本地行为**（需要本机凭据、本机 ssh 客户端、本机包管理能力）。隧道一旦建好，控制层用**标准协议 C** 连上去；对核心层而言这是一个普通连接，**它不知道自己是本机还是穿过隧道的**。

**隧道接入不需要核心层做认证**：能建立那条 SSH 隧道的人，已经能在该机执行命令——这正是 `implicit`/`local` 两档所依据的东西。**远控隧道的连接在核心层看来就是「来自环回」**，落在 §2.3 的既有判据上。前提：核心层**只监听环回**，隧道由 SSH 提供。

**多种接入方式**（WSL、Docker、其他隧道）遵循同一模式：探测 → 必要时安装 → 端口映射 → 标准协议接入。差别只在"怎么打通那条隧道"。这些都在控制层，核心层与协议对它们一无所知。

### 6.3 uhub —— 外挂的能力与通路来源

**不是层，不是第五个组件，是外挂。** 它对核心层提供两类东西：

| 角色 | 提供什么 | 接入方式 | 架构后果 |
|---|---|---|---|
| **能力提供者** | 模型端点、企业知识库、内部数据服务…… | **走工具/MCP 接入机制**（模型端点是特例：它是驱动 agent 的东西而非 agent 用的工具） | 不需要新协议能力 |
| **通路提供者** | 中继（异网可达） | 又一种绑定 | 不需要新协议能力，但需要新增信任与授权 |

**登录可选**：登录不是使用智能体的前提，而是"要不要接入组织 uhub"的选择。

| 状态 | uhub 的能力集 | 中继 |
|---|---|---|
| 未登录 | 全部不可用 | 不可用 |
| 已登录 | 按账号授权可用 | 可用 |

**登录是"获得能力"，不是"获得许可"。** 未登录时本地模型完全不变：核心层只监听本机、自配模型端点、各壳直连。**不登录 ≠ 没有远程能力**——AI SSH 与远控不依赖 uhub。

**模型端点**：uhub 暴露 OpenAI/Anthropic 兼容端点，已登录时可选择使用，也可继续用自己的。**权威性逐模型**：uhub 提供的模型由 uhub 权威（本地改动会在下次同步被覆盖，需对用户明示"这是有意设计，不是配置丢失"），用户自配的模型由本地权威。两者可共存。

**中继：认证 → 转发。** 只有一种形式：流量经 uhub 转发，**不存在不过 uhub 认证的接入路径**（没有旁路）。转发对象包括已登录的核心层与 uhub 托管的 Web 壳。**中继必须覆盖全部通道**（含工作区查询与 PTY），通道类型从设计一开始就是一等概念。

**一个核心只绑定一个 uhub**：认证与授权只有一个判定点；本机开关保持单一二值开关。若需服务两个组织，用两个核心层实例共享同一数据层。

**通道即身份**：核心层与 uhub 之间的通道是**核心层自己发起的**（dial 到配置地址，走 TLS，证书校验就完成了"对端确实是 uhub"）。因此不需要签名断言、公钥分发或轮换——签名挡不住签名者（uhub 被攻破时它签的就是自己的谎话），而真正能缓解那个风险的是端到端加密。核心层对身份断言只需一件事：**记下"这条 attachment 属于谁"**。

> **可复用原则**：核心层主动 dial 到配置地址 + TLS ⇒ **通道本身就是身份**，不需要第二套信任机制。

**可用性语义**：uhub 关的是**通道**，不是 agent。账号被停/凭据失效 → 中继通道关闭，远程接入断开；agent 正在跑的任务不受影响（数据层与模型配置在自己机器上）。若 agent 正在调用 uhub 提供的能力，那些调用会失败——这是**普通的运行时错误，不是状态变更**，agent 不需要"被告知"。因此不需要"降级为未登录状态"这种东西，也不需要凭据失效通知机制：**封禁/冻结/撤销就是让通道不可用**。控制面短时抖动不应断开已建立的中继，也不应让已登录机器拒绝本地使用。

**关闭中继是本机的退出机制**：见 §2.4。它不是缓解措施，要么整套接受并给全权，要么不参与。

**P2P 打洞不做**：纯优化非功能。转发的唯一前提是"核心层能连上 uhub"，去掉打洞不丢失任何功能，只是放弃"少一跳"。复评条件：跨地域托管部署叠加大量终端交互使那一跳延迟明显，或 uhub 带宽成为瓶颈。

**端到端加密暂不做，但保留一条约束**：uhub **只按通道转发不透明字节，不解析协议 C**。这条成本几乎为零（uhub 只需知道"这个客户端要连哪台核心层"），却保住了将来加端到端加密的可能性。

**凭据传递**：uhub 签发的账号凭据交给 MCP 客户端——远程类型（HTTP/SSE）走 OAuth 授权流程，本地 stdio 类型走环境变量。

**能力目录与开关**：登录后应能知道"这台 uhub 提供哪些能力""哪些对我可用"。**关闭的落点在项目级**（§3.9）：可在项目中显式关闭这些能力。【待业务确认 B-10】

### 6.4 三种形态对照

| | AI SSH | 远控 | uhub 中继 |
|---|---|---|---|
| 目标机装 ucode | **否** | 是（探测后装） | 是（注册进组织） |
| 核心层位置 | 本机 | 目标机 | 目标机 |
| 数据层位置 | 本机 | 目标机 | **目标机** |
| 模型凭据位置 | 本机 | 目标机 | 目标机（自配）或 uhub（用其端点时） |
| 网络要求 | SSH 可达 | SSH 可达 + 端口或映射 | **无** |
| 身份来源 | 本机 SSH 凭据 | 本机 SSH 凭据 | uhub 账号 + 节点注册凭据 |
| 可跨组织纳管 | 否 | 否 | **是** |
| **本机关闭后** | 全部停止 | 远端继续 | 远端继续 |
| 需要新协议能力 | PTY（复用通道） | 无 | 无（中继是又一种绑定） |

**AI SSH 与远控的本质区别**：在远控下，会话记录、模型调用都在远端，本机只是显示，**本机可以关掉，远端继续跑**；AI SSH 则相反，本机关掉一切停止。这是判定一个功能该归哪种形态的依据。

### 6.5 路径优先级与并存规则

三种通路都能把"另一台机器"变得可用，同一个核心层可能有多条接入路径。规则：

- **远控与 uhub 中继不是并列关系，是先后关系**：远控是**纳管动作**（把还没纳入组织的机器变得能连），uhub 中继是**纳管之后的常态通路**（机器已在组织里，之后连它不该再需要 SSH）。
- 用户可见的路径只有两档取舍：

| 情形 | 走哪条 | 理由 |
|---|---|---|
| 坐在这台机器前 | 环回 / stdio | 根本不需要网络 |
| 在同一局域网 | 局域网直连 | 少一次绕行，纯粹是省 |
| 在别处 | **uhub 中继** | 远程操作的正常形态；组织没部署 uhub 时退回远控隧道（唯一手段） |

- 核心层必须有**稳定身份（nodeId）**；控制层按身份去重，一个核心层在列表里只出现一次，**路径是它的属性而不是并列条目**。
- **本机到本机优先走环回，不经 uhub。**
- **每条连接只走一种通路，通路之间不串联。**（例外：核心层自己的出站网络路径，如经跳板机出网——那是它自己的网络环境问题，对控制层不可见。）
- **不把"经 uhub"当作需要规避的状态**：它带来的额外一跳是远程操作的固有成本。

### 6.6 节点注册表与身份认证

- **节点注册表**：控制层记住并接入多个核心层节点（本机、若干远端），每个节点有地址、认证凭据、显示名。归属**控制层侧的本地状态**（"这台机器上的壳认识哪些节点"）。
- **节点身份认证**：探测到一个端口有服务时，必须先验证节点身份，再交出任何凭据；同时需要一个**建立协议连接之前**的轻量端点（"这个端口上是什么服务、协议版本多少"），否则探测只能靠猜端口。**范围只为 uhub 通路服务**（确认对端是哪个 uhub 及其身份载荷），**不服务远控**——远控靠 SSH + 环回判据，不需要核心层做身份判断。

### 6.7 授权、可见性与审计

- 登录引入账号，但**多用户影响被限定在访问层**：数据层仍是单用户目录模型，不引入 tenant 概念。
- 需要定义（都在访问层）：账号与身份、核心层准入（哪台机器可注册进组织）、用户→核心层的授权映射、**会话可见性**（远程接入者能看到主人的多少东西）。
- 最后一条**不是多租户问题**：数据层属于那台机器的 OS 用户，远程接入者是**访客**——问题是"访客能看到主人的哪些东西"，是授权粒度问题。
- **审计**：经中继的每条连接至少能回答"谁、从哪台设备、连了哪台机器、做了什么"。身份可信度完全来自"那条通道是核心层自己 dial 的"，没有密码学产物可供事后核对，**记录因此是唯一的追溯手段**。建议两侧都记（uhub 记接入，核心层记操作），用 attachment id 关联。【待业务确认 B-5】

## §7 包结构与依赖

### 7.1 包边界

```
data-layer-spec/     协议 D 的规范与一致性测试套件
store/               协议 D 的参考实现
core/                核心层（协议 C 服务端实现）
bindings/*           绑定层，每种传输一个包
client/              控制层共用 SDK
shells/*             控制层，每个壳一个包
uhub/                uhub（能力与通路提供者）及其管理面
cli/                 核心层与壳子的启动入口
```

**包边界是架构，包内文件划分不是。** 划这个边界的唯一目的，是让三条需求在结构上成立：

| 需求 | 由什么结构保证 |
|---|---|
| 核心层可脱离控制层单独安装 | `core` 不依赖任何 `shells/*` |
| 数据层可被独立实现 | `data-layer-spec` 不依赖任何内部包 |
| 新增绑定（或新增壳）不改核心层 | `bindings/*` 与 `shells/*` 都是叶子方向的加法 |

### 7.2 依赖方向与禁令

```
shells/*  →  client  →  bindings/*  →  core  →  store  →  data-layer-spec
```

**严格单向。** 具体禁令：

| 禁止 | 对应 |
|---|---|
| `core` 依赖任何 `bindings/*` | 核心层不知道传输 |
| `bindings/*` 依赖任何 `shells/*` | 绑定层不知道对端形态 |
| `bindings/*` 之间互相依赖 | 绑定之间不通信；一致性由协议 C 语义保证 |
| `store` 依赖 `core` | 数据层可被任何实现消费 |
| `core` 绕过 `store` 直接读写会话文件 | 绕过 owner 语义与写入不变量 |
| `data-layer-spec` 依赖任何内部包 | 它必须能被外部独立实现者使用 |

**强制手段**：用依赖检查工具做成 CI 门禁。规则写成**允许列表**而非禁止列表——显式列出每个包允许依赖什么，理由是新增包时禁止列表会静默漏掉，允许列表会直接报错。

### 7.3 CI 验收

**"核心层可脱离控制层单独安装"**：

1. 空目录里只装 `core` 与一个绑定包（不装任何壳）；
2. 启动核心层，指向临时数据层目录；
3. 用**纯协议测试客户端**（不依赖 `client` 包，直接按协议收发）完成：握手 → 新建会话 → 发起对话 → 收到完整事件流 → 取回历史校验；
4. 断言退出码为 0。

这一个任务同时验证三件事：核心层不依赖壳、协议 C 可被独立实现、数据层可被独立实现。

**反向验收**：再跑一个只装 `shells/web` 的任务，断言其依赖树里**不出现 `core`**。

**数据层一致性套件**：`data-layer-spec` 导出"接收一个实现工厂函数"的测试套件，任何实现传入自己的工厂即跑全套。必测范围：并发竞争 owner 恰好一方成功、owner 崩溃后可接管且尾部得到处置、派生数据删除或损坏后可重建、非追加写的原子性、权限不满足拒绝启动、版本过高拒绝启动、危险文件系统拒绝启动、路径逃逸被拒。

### 7.4 测试分层

| 层 | 必须覆盖什么 |
|---|---|
| 数据层 | 一致性套件；任何实现都要跑 |
| 绑定层 | 线格式往返；跨绑定一致性 |
| 核心层 | 用**假模型供应商**的录制式测试（对话 → 事件 → 落盘）；交互超时与降级；信任矩阵约束；自主级别门槛 |
| 控制层 | 端到端：起真核心层 + 无头浏览器，验证挂载、权限弹窗、断线续传 |

**假模型供应商是必要设施**：核心层测试不能让结果依赖真实模型调用。

### 7.5 实施里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M0** | 验证 [03](03-假设与验证.md) 的技术假设 | 可重跑脚本 + 结论。**不通就停下来重新选基座** |
| **M1** | 数据层：不变量 + 参考实现 + 一致性套件 | §7.3 必测范围全绿；两进程抢 owner 恰好一方成功；kill 持锁进程后可接管 |
| **M2** | 核心层 + stdio 绑定 | 纯协议客户端完成握手 → 新建会话 → 对话 → 完整事件流 → 取回历史 |
| **M3** | 交互面 + 多 attachment + 跟随 | 第二个控制层挂载收到全量重放 + 增量，且不获应答权；高信任 attachment 断开后路由正确移交 |
| **M4** | 其余绑定 + 信任矩阵生效 | HTTP 上工具执行被拒并给出可诊断原因；无法承载的交互请求走降级而非挂起 |
| **M5** | Web 壳 + 断线续传 | 杀掉核心层再拉起，壳自动重连并用游标补齐，UI 不丢不重 |
| **M6** | 多实例 + 远程 | 同机两实例指向同一数据层，writer/reader 角色正确；WebSocket 绑定启用认证 + TLS |

M0 是阻塞性的，且其结论会影响 M1 的设计，不应与其他阶段并行。

## §8 附：外部依据

本节记录架构所依据的外部事实。作用是：当讨论中有人提出"为什么不用 X"时，答案在这里，不必重新调研。

### 8.1 pi（基座）

pi 是一个 headless 的 agent harness，TypeScript monorepo，核心包 `pi-agent-core`（agent loop、`Agent`、`AgentTool`）、`pi-ai`（统一多供应商 LLM API）、`pi-tui`（差分渲染 TUI）。扩展机制：入口为 `export default function (pi) { ... }`，本地扩展经 jiti 加载、`.ts` 免编译；注册面包括 `registerTool` / `registerCommand` / `on()` / `pi.events` 等；资源目录为 `extensions/` `skills/` `prompts/` `themes/`；分发复用其 packages 机制。

数据布局：agent-dir 默认 `~/.pi/agent`，可用 `PI_CODING_AGENT_DIR` 覆盖；会话文件按项目路径分桶、JSONL、版本化 header + entry 流，entry 经 `id`/`parentId` 构成树。数据层的目录布局与文件命名沿用这套约定。

**刻意不复用的部分**：pi 存在一套实验性 server/client/protocol（多实例注册、CBOR + unix socket、attachment 概念），形态上接近本架构，但明确标注 experimental、无兼容承诺、source-only、**协议层无认证**、client 不自动重连与重放。因此不作为地基；其命名与概念（服务实例、会话、attachment）被沿用以便将来迁移。

### 8.2 同类系统对照

| 项目 | 数据层 | 服务层 | 可远程 | 多实例共享数据层 |
|---|---|---|---|---|
| OpenCode | XDG 目录 + SQLite + 全局文件锁 | headless HTTP + SSE | 是 | 单机单数据目录 |
| Codex CLI app-server | `$CODEX_HOME` + 历史文件 + 状态库 | JSON-RPC over stdio/WS/unix | **第一方支持** | 未文档化 |
| OpenHands Agent Canvas | 按 workspace 持久化 | HTTP/WebSocket + 事件流 | 是 | 一个前端挂多个后端 |
| LangGraph/LangSmith | Postgres + Redis pub/sub | REST + 独立 worker | 是 | **明确文档化**（stateless 容器共享 Postgres/Redis） |
| Letta Code | 云状态 | App Server | 是 | **是**（多机共享云状态） |

**值得记下的实现**：Roo Code 的 `TaskHistoryStore` 是少见的有明确文档与测试的"多实例共享磁盘数据层"实现（单任务 JSON 文件 + `_index.json` + 跨进程 `proper-lockfile` + `fs.watch` + reconcile），与本架构的派生数据对账思路一致。

**协议标准对照**：ACP（编辑器 ↔ agent，客户端持有 fs/terminal 与权限）与 ucode 哲学相反——ucode 是**核心层拥有环境**、只把人类交互委托给控制层，因为远程壳子的动机通常是"环境在那台机器上"。AG-UI 面向 agent ↔ UI，MCP 面向 agent ↔ 工具，A2A 面向 agent ↔ agent。

### 8.3 失败模式与启示

以"本地启动器"形态出现的编排产品，agent 都是 CLI 子进程，状态散落在 git worktree 加一个本地 DB 里；远程 UI 是事后补的或根本没有。结果要么转向云沙箱，要么关停。共同病灶是**状态散落**。

对本架构的三条启示：

1. **数据层必须先定，且必须是单一真相。**
2. **远程能力不能后补。** 后补意味着协议要重设计。本架构首发就在协议 C 里留好认证字段、在信任矩阵里留好未认证行。
3. **生命周期是真实的产品问题。**
