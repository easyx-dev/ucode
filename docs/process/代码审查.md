# 代码审查

本文是 ucode 的**代码审查规范与流程**：范围口径、自动化基线、语义审查维度、判定纪律与报告格式。

**默认审未提交改动**（staged + unstaged + untracked）；`all` / `全部` 走**全量扫描**（源码 + 规则文档 + 配置）。审查目标是让全仓库看起来只由一个人写成——凡出现「同一种东西两种命名/两种写法」，无论是否可运行，一律视为偏离并列出。

判定依据是 [AGENTS.md](../../AGENTS.md) 与 `../spec`、`../impl`。**不依赖外部审查 CLI**：范围枚举用 git 原生命令（`git diff` / `git ls-files`），判定自己做。

## 适用场景

- 变更审查（提交前自查、评审前一致性检查）
- 全量代码审计（阶段）与技术债评估
- 重构前的违规诊断
- 新人接手项目前的全面了解
- 多人协作时统一书写风格的裁决依据

## 第 0 步 · 范围口径

| 口径 | 含义 | 实现 |
|------|------|------|
| （无参）/ `diff` | 未提交改动（staged + unstaged + untracked） | `git status --porcelain` + `git diff` + `git diff --cached`；untracked 逐个读 |
| `all` / `全部` | 全量：源码 + 规则文档 + 配置 | `git ls-files` 口径枚举（见下） |
| `<commit>` | 单提交（含其父上下文） | `git show <hash>` + `git diff <hash>^ <hash>` |
| `<branch>` | 分支对比 | `git diff <base>...<branch>` |
| `pr <编号>` / PR URL | 拉取请求 | `gh pr view` + `gh pr diff`（缺 `gh` 时要求用户给 base/head） |
| `--scope <路径>` | 目录 / 模块收窄 | 与所在口径取交集 |
| `<维度>` | 只审部分维度 | 命中维度枚举名（如 `层`/`协议`/`安全`）则过滤 |
| `<严重度>` | 只报指定级别以上 | 命中 `critical` / `high` / `medium` / `low`（或 严重 / 高 / 中 / 低）则过滤 |

**口径消歧顺序**（避免 commit / branch / PR 互相认错）：`all`·`全部` → `pr`·含 `github.com`·`#n` → 维度枚举名 → 严重度枚举名 → 7–40 位十六进制（按 commit）→ 其余按 branch。**匹配不上任何规则时不要猜**，回报要求明确。

### `all` 的扫描口径

纳入：

- 源码：`packages/**/src/**`、`apps/**/src/**`、`hub/src/**`、`apps/desktop/main.mjs`、`apps/desktop/preload.cjs`、`apps/*/vite.config.ts`、`tools/**`、`tests/**`
- 规则与文档：`AGENTS.md`、`README.md`、各包 `README.md`（`packages/**`、`apps/**`、`hub`）、`docs/**`、`spike/README.md`
- 配置：根与各包 `package.json`、`pnpm-workspace.yaml`、`biome.json`、`tsconfig*.json`、`vitest.config.ts`、`.github/**`、`apps/desktop/electron-builder*.yml`、`apps/*/index.html`

排除（生成物 / 锁文件 / 二进制，不参与审查）：`pnpm-lock.yaml`、`spike/package-lock.json`、`**/dist/**`、`**/dist-renderer/**`、`**/core-bundle/**`、`**/release/**`、`node_modules`、`spike/results/**`、`*.tsbuildinfo`。

> 全量模式下**不要把 `dist/` 当源码审**：它是 `pnpm build:libs` 的产物，只在与源码不一致时作为「忘了重建」的信号出现（对照 I-10 / I-15）。

## 第 1 步 · 范围契约与覆盖率账本

产出并在报告中声明（**正常情况压进开头一句**，只有出现降级 / skipped 时另起短节详述）：

- `mode`（workspace / commit / range / all）+ ref 元数据 + 文件数
- `total` / `reviewable` / `excluded` / `coverage_rate`（= reviewed / reviewable）
- 排除原因分布

排除原因二次判定——**"被排除"不等于"不用审"**：

| 排除原因 | 项目动作 |
|----------|----------|
| 二进制 / 超大文件 | 跳过，计入 skipped 并给出理由 |
| 疑似敏感文件（`.env` / 凭据 / 私钥） | 跳过，**单独告警提示人工确认**；若发现已跟踪则直接判 🔴 |
| `dist` / 构建产物 | 跳过；若与源码语义不一致，报「忘了重建」而非报产物本身 |
| 其余 | 每个 skipped 文件必须给具体理由，**不得静默省略** |

## 第 2 步 · 自动化基线与门禁边界

先跑 `pnpm check`（= typecheck + Biome + 依赖边界门禁 + 品牌字面量门禁 + 全量测试）作为基线；涉及产物形态改动时补跑 `pnpm build:libs`、`node tools/acceptance-reverse.ts`、`node tools/acceptance-core-standalone.ts`。把已通过项从手工维度排除。

**真门禁（出现即引用工具结论，不重复手扫）**：

| 载体 | 覆盖 | 覆盖不到 |
|------|------|----------|
| `tsc --noEmit`（strict + `erasableSyntaxOnly`） | 类型、不可擦除语法（enum/namespace/参数属性）、相对导入后缀 | 经 `as any` 绕过的语义、运行时才显形的行为 |
| Biome | 格式、通用 lint、import 组织 | **无任何架构/协议/安全语义规则**——分层、协议契约、密钥路径全须人工 |
| `tools/check-boundaries.ts`（`tools/boundaries.json`） | 内部导入落在允许列表内、声明与导入一致、未登记包、相对导入穿墙、外部依赖已声明、`forbiddenTransitive` 反向依赖 | 依赖**用法的正确性**（该走 `@ucode/sdk/http` 却 import 根）、**未登记的计算型动态导入**（须进 `allowComputedDynamicImports`）、协议语义 |
| `tools/check-brand-literals.ts` | 源码（`.ts/.tsx/.mjs/.cjs/.js`）里的产品名 / 数据层目录名 / appId / 厂商名 / urlScheme 字面量 | **非源码文件**（`.md` / `.json` / `.yml` / `.css` / `index.html`）里的品牌字面量——门禁不扫，须人工 |
| 全量 `vitest` | 单元与端到端行为 | 未覆盖路径；用 `pnpm test` 的 include 口径对账是否有模块无测试 |

**仅靠约定、必须人工扫**（不要因「以为有门禁」而漏扫）：品牌字面量在非源码文件（`apps/*/index.html`、`electron-builder*.yml`、`package.json` 的 description）；`exports` 条件顺序是否 `types → dev-src → default`（I-10）；子进程 spawn 是否带 `--conditions=dev-src`（I-11）；密钥是否可能经日志 / 回读形状 / 支持包外泄；`hooks.json` 是否只从数据层读；协议能力 / 信任矩阵是否被放宽；UI 选择器是否返回新建对象（I-5）；注释规范与命名一致性。

> 门禁本身有自测：`tests/gates.test.ts` 证明两道门禁会拦人（合成工作区逐分支 + 真实仓库注入违规）。**改了门禁或 `boundaries.json` 却没同步改自测**，直接报。

## 第 3 步 · 审查前置约定（规则即事实，以 AGENTS.md 与现有代码为判据）

- **依赖方向**：`apps/web,apps/desktop → ui → sdk → bindings/* → protocol`；`apps/tui → sdk`；`apps/cli → core, bindings/*, apps/*`；`core → store → data-layer-spec`；`core → protocol, branding`；`hub → protocol, branding`。**bindings 不得依赖 core**，**sdk 不得 import ui / 假设 DOM**。新增包 / 新增内部依赖必须登记 `tools/boundaries.json`。
- **传输走 sdk 子路径**（I-6）：壳子只 import 自己那一份（`@ucode/sdk/http`、`.../stdio`、`.../rpc`、`.../ws`、`.../node-transport`），保证浏览器打包不含 `node:net` / `node:child_process`，且不新增 `apps/* → bindings/*`。
- **品牌参数化**：产品标识一律 `@ucode/branding` 读取，环境变量名用 `envVar(...)`；`@` 开头的包 scope 是编译期标识、不算违规。
- **语言与模块**：ESM；相对导入写 `.ts` 后缀；**禁 `enum` / `namespace` / 参数属性**（`erasableSyntaxOnly`）；**JSX 只出现在经打包器处理的包**（`apps/web`、`apps/desktop/src/renderer`），被 Node 直跑的包（core / bindings / sdk / cli / tui）用 `.ts` + `createElement`（I-1）。
- **`exports` 条件顺序**必须 `types → dev-src → default`（I-10）；**dev 期不构建**，`src/*.ts` 即被测对象。
- **协议 C**：能力**声明**（`hello`）与**授予**（`welcome`）分离；版本**双向校验、从不静默降级**；`ClientMessage` / `ServerMessage` 方向相反；新增命令须在 `protocol/src/commands.ts` 声明 Zod schema 并登记 `COMMAND_CAPABILITIES`。
- **信任不自报**：信任级别由绑定声明（`implicit` / `local` / `untrusted`，ADR-004）；非环回监听须显式允许并降为 `untrusted`。
- **数据层**：`@ucode/store` 是**唯一写会话文件者**，核心层不得绕过；会话只追加、游标 = 行号；非追加写走 tmp + rename；`listSessions` 须与磁盘对账（I-3）。
- **代码体积**：文件/类 >600 行、函数/方法 >60 行须拆分（40 行为预警）；例外为生成代码、大型测试夹具、协议常量表。

## 已知豁免 / 例外（只列已认可项，不报违规）

这些实现已达成规则意图、且改动成本低或确有必要，**默认不列为偏离**；仅在相关规则被真正违反时才报告：

- **`@` 开头的包 scope**（`@ucode/protocol` 等）：编译期标识，品牌门禁已显式剥离，不算品牌字面量。
- **`packages/branding/brand.json` 与 `assets/`**：品牌配置与资源本身，是字面量的合法载体。
- **`spike/**`**：dev-only 承重假设验证脚本，被 Biome 与品牌门禁双双排除；不按 AGENTS.md 的注释/命名规范要求。
- **协议常量表 / 内置定义**：`commands.ts` 的 `COMMAND_CAPABILITIES`、cron 解析表、子智能体内置定义等，属"协议常量表"例外，不受行数阈值约束。
- **`.md` 里的产品名**：文档与 README 中出现的产品名属正常表述（品牌门禁不扫 `.md`）。
- **`apps/desktop/main.mjs` 与 `preload.cjs`**：不经打包器直载，必须纯 JS / CommonJS（I-7），不适用 TS 语法要求。
- **`packages/ui/src/styles.css`**：主题 token 的唯一载体，此处出现具体色值是设计意图，不算硬编码违规（组件里才禁硬编码）。
- **存量头注释**：文件级注释若复述文件名，仅对**新增**文件提改进建议，存量不判违规。

## 第 4 步 · 语义审查维度（①–⑫）

### ① 分层与依赖边界 → [AGENTS.md「包边界约定」](../../AGENTS.md)

- 内部导入是否都在允许列表内；是否绕过 `@ucode/*` 直接用相对路径穿到别的包（check-boundaries 会拦，人工复核"用法的正确性"：该走子路径却 import 根）
- `bindings/*` 是否引入 `core`；`sdk` 是否引入 `ui` 或使用 DOM；`ui` 是否引入任何 `apps/*`
- 是否新增工作区包却未登记 `boundaries.json`；新增外部依赖是否已声明（含 catalog 引用）
- 计算型动态导入是否在 `allowComputedDynamicImports` 显式登记（未登记会被门禁拦下）
- 新增依赖是否落在 catalog（`pnpm-workspace.yaml`）统一版本，而非包内硬编码版本号

### ② 品牌参数化 → [AGENTS.md「品牌参数化」](../../AGENTS.md)

- 源码里是否出现产品名 / 数据层目录名 / appId / vendor / urlScheme 字面量（门禁覆盖源码，注意它**不扫** `.md` / `.json` / `.yml` / `index.html`）
- 数据层默认目录是否从 `defaultDataDirName()` 派生、环境变量名是否走 `envVar(...)`
- 非源码载体（`apps/web/index.html` 的 title/favicon、`electron-builder*.yml` 的 appId/productName、`package.json` description）是否与 `brand.json` 同源而非手抄

### ③ 协议 C 合规 → [../spec/01-架构.md §4](../spec/01-架构.md)

- 新增命令是否声明 Zod schema 并登记能力；拒绝时是否给**可诊断原因**（承载不了 vs 信任不足要能区分）
- 是否把能力**声明**与**授予**混为一谈；是否引入静默降级（版本、能力都不得静默降级）
- 交互面方向是否与命令面相反；`ui-broker` 的阻塞/通知/超时降级路径是否完整（无法承载走降级而非挂起）
- 自主级别门槛是否生效（`auto-edit` / `full-access` 需本机等价或已认证授权通路；`plan` 只读且与目标模式互斥）

### ④ 数据层合规 → [../spec/01-架构.md §3](../spec/01-架构.md) + [AGENTS.md「协议 D」](../../AGENTS.md)

- 是否有绕过 `store` 直接读写会话文件的代码
- 会话写入是否**只追加**；非追加配置写是否走 `atomic.ts`（tmp + rename）
- 索引读取是否与磁盘 mtime 对账（I-3，跨实例否则读到旧索引）
- 路径入参是否过安全校验（`SESSION_ID_PATTERN` / `isSafePathSegment`）
- owner 租约 / 跟随者逻辑是否只依赖 `fs.watch`（须轮询兜底，V-10）；迁移后是否通知全量重同步；跟随者是否只靠 inode 判整体替换（V-5 已推翻）

### ⑤ 安全与密钥（**本仓最高优先**）→ [AGENTS.md「安全硬规则」](../../AGENTS.md)

- **密钥单向性**：协议回读形状（如 `ProviderSummary`）是否只有 `hasApiKey` 而无密钥；覆盖写是否保留原密钥；密钥是否可能进日志 / 屏幕 / 支持包
- **SSH 注册表**（`ssh.json`）是否存入密钥或口令；远端命令是否按 argv 单参传递、不经本地 shell 拼接；是否拒绝主机名/用户名里的 shell 元字符
- **hooks 是否只从可信数据层读**（`<数据层>/hooks.json`），绝不读项目本地 hooks
- **支持包导出是否脱敏**（`insights/redact.ts`）且不含会话正文
- **OS 凭据**是否只在加密可用时存（加密不可用拒存），明文不落盘、不进日志
- **读取过滤**（Wiki / 工作区）是否跳过敏感文件、二进制、超大文件、**符号链接**
- 是否硬编码密钥 / 提交 `.env`；危险操作（`rm -rf /`、`git reset --hard`、`DROP TABLE`、`chmod 777` 等）；外部输出是否被当指令执行（指令注入）

### ⑥ 核心层语义 → [AGENTS.md「核心层约定」](../../AGENTS.md)

- `session-runtime` 是否**先落盘再广播**（I-2：不依赖基座 `entry_appended`）
- `tool-gate` 是否所有通路都过；子智能体是否**继承**工具闸门（不得成为绕过批准的后门），是否误挂记忆/子智能体工具（递归风险）
- 各功能域（memory / hooks / subagents / goal / tasks / undo / wiki / ssh / import / marketplace / insights）是否守住边界与预算（如 wiki 三重预算、到顶要明说没读完）
- 无人值守的待决交互是否落盘 `ui.pending` / `ui.resolved` 且应答后转达 agent

### ⑦ 控制层合规 → [AGENTS.md「控制层约定」](../../AGENTS.md)

- `ui` 是否被 TUI 误引用；`tui` 是否只依赖 `sdk`
- 前端选择器是否返回**新建对象/数组**（I-5，会导致无限重渲白屏）；派生数据是否用 `useMemo`
- SSE 优雅退出是否 `closeAllConnections()`（I-4，否则 SIGTERM 后不退出）
- TUI 提交回调是否 `setText("")`（I-13）；视图层是否重复渲染流式尾巴（I-14）
- Electron 主进程 / preload 是否保持纯 JS / CJS（I-7）；桌面打包三层产物是否齐备（I-9）
- 组件是否硬编码颜色（应走语义 token，token 在 `styles.css`）；展示逻辑是否抽成纯函数以便单测
- `web` 子命令相关的改动是否提醒**重建前端产物**（I-15）

### ⑧ 测试覆盖 → [AGENTS.md「测试约定」](../../AGENTS.md)

- **仓库级搜索被测符号**：确认每个模块的导出函数在**全仓库**是否有测试（勿只看同目录）。区分：① 全仓库无测试 → 真缺覆盖；② 有测试但位置漂移 → 单独记录，勿误报成缺测
- 测试是否在被测模块**同目录的 `__tests__/` 子目录**、命名 `<模块名>.test.ts`；跨包端到端与门禁自测是否在顶层 `tests/`；真实模型冒烟是否只在 `spike/`（不得进 `pnpm check` 的测试路径）
- **命名**：单元测试 `describe` 是否为**被测函数名**（一个 describe 覆盖多个导出时是否已拆成嵌套 describe、叶子层为函数名；schema/常量用被测对象名）；集成/端到端/conformance 用中文场景主题；`it` 是否中文、说清"什么条件下期望什么"（禁 `should ...` 模板）
- 测试文件是否也受 600 行约束（超长即需按主题拆分）
- 核心层测试是否用 `testing/fake-provider.ts`（确定性、零成本）与共享 `testing/core-harness.ts`，而非真连模型
- 门禁自测（`tests/gates.test.ts`）是否与门禁实现同步
- 每个导出函数是否覆盖正常 1–2 / 边界 1–2 / 错误 1

### ⑨ 命名与一致性 → 文末「一致性 · Style Guide」

（面向「像一个人写的」风格统一，同源偏离先归并再标注影响面）

- 包内目录是否按功能域成目录（`<域>/index.ts` 统一导出）；文件名是否 kebab（`session-runtime.ts`、`model-config-dialog.tsx`）；纯函数视图/格式层是否 `*-format.ts` / `view.ts` 这类可辨识命名
- 类型命名是否 `XxxProps`（UI，禁裸 `Props`）、`XxxInput` / `XxxOutcome`（核心层）；布尔 `is` / `has` / `should` 前缀；回调 `onXxx`（对外）/ `handleXxx`（内部）；Hook `useXxx`；常量 `SCREAMING_SNAKE_CASE`；动词是否成体系、同类同词（不混用 `get` / `fetch` / `query`）
- 同一概念是否前后一致（如"供应商/provider"、"数据层/store"）；是否有同义漂移、死代码、重复逻辑、过时注释

### ⑩ 注释规范 → [AGENTS.md「语言规范」](../../AGENTS.md)

- 注释 / 文档 / 页面文字 / git commit 是否均用**简体中文**
- **函数体 / 逻辑注释**是否复述代码本身（标识符名的中文翻译、显而易见的赋值/渲染/流程）→ 违规，应删
- **TS 类型字段注释从宽**：逐字段写、与字段名同义均不判违规，只需确认是业务口径
- 文件级注释是否概述职责、不复述文件名；**存量头注释不判违规**，仅对新增提改进建议
- 是否有**空白横幅**（`// ═══ 分区标题 ═══` / `// ─── xxx ───`）→ 违规
- 反直觉实现（I-1…I-15 这类）是否留有说明意图与边界的注释，且贴近业务语义

### ⑪ 错误处理与通知 → [AGENTS.md「核心层约定 / 控制层约定」](../../AGENTS.md)

- 静默失败违规：空 `catch`、吞异常、`catch {}` 后返回默认值；**"无可用模型"这类必须明说的状态是否被静默吃掉**（I-12 的 `modelAvailable` 就是为此而加）
- 拒绝/失败是否给可诊断原因，而非挂起或假装成功
- 命令失败是否在控制层可见（TUI 的彩色条目 / UI 的横幅），而非只落日志
- 迁移/安装等有副作用操作是否"先预检再执行、冲突默认跳过"

### ⑫ 日志与可观测性 → [AGENTS.md「核心层约定」](../../AGENTS.md)

- **stdout 归协议通道**：stdio 绑定下 stdout 是协议 C 的线，**所有日志必须走 stderr**（`apps/cli/src/runtime.ts` 的约定）——在 stdout 打印任何东西都是协议污染，直接判高
- 日志级别语义：过程性/遍历性细节用 `debug`，低频里程碑才 `info`，异常降级 `warn`，失败阻断 `error`；高频路径禁 `info`
- 是否有把密钥、令牌、凭据写进日志的路径（与 ⑤ 交叉核对）
- 错误信息是否含足够定位信息（数据目录、会话 id、命令名），且不泄露敏感内容

### 附 ⑬ 通用工程卫生（**非项目 SSOT**，不计入 ①–⑫）

作为补充清单核对，与本仓约定冲突时**以 AGENTS.md 为准**：拼写与词法错误、死代码、重复代码、`var`、`==` / `!=`、`any`、嵌套三元、Hooks 调用规则、render 内副作用、组件内声明组件、`innerHTML` / `eval` / `document.write`、硬编码业务串。

## 第 5 步 · 配置与文档核对（清单式，非语义）

多由机械门禁或登记核对完成，**不与 ①–⑫ 混计**：

- **依赖声明**：`pnpm-workspace.yaml` 的 `catalog` 所列依赖在任一 `package.json` 必须写 `"catalog:"`，禁止硬编码版本；`allowBuilds` 是否对每个带构建脚本的依赖显式表态；根 `package.json` 不承载运行期依赖；各包须声明自己用到的运行期依赖
- **`exports` 条件**：库包必须 `types → dev-src → default`（I-10）；`@ucode/ui` 需导出 `./package.json` 与 `./styles.css`
- **Biome 配置**：`biome.json` 的 `files.includes` 排除是否仍覆盖 `dist` / `dist-renderer` / `core-bundle` / `release` / `spike` / `__gate_probe*` / `*.css`；**文件内不得有注释**（`//` 会让 Biome 静默回落默认配置）；`vcs.useIgnoreFile` 是否开启
- **vitest 配置**：`resolve.conditions` 与 **`ssr.resolve.conditions`** 都必须含 `dev-src`（只配前者会静默测 `dist`，I-11）；`ssr.noExternal` + `server.deps.inline` 是否覆盖 `@ucode/*`
- **门禁数据**：新增包是否登记 `boundaries.json`；`forbiddenTransitive` 是否仍表达反向验收意图（壳不含 core）
- **CI / 发布**：`.github/workflows/ci.yml` 是否仍跑 `pnpm check` + 两条验收 + 壳构建；`release.yml` 凭据是否全走 secrets、缺凭据不失败
- **文档与规则三方一致性**（AGENTS.md ↔ `docs/**` ↔ 代码）：同一约定不得多处口径不一，发现即报「孤立漂移」并给出应以哪一处为准；`../impl` 的落地记录 I-n 与 `../spec` 的 V-n / B-n 是否互不矛盾

## 第 6 步 · 审查纪律与评论文风（一律用简体中文书写）

### 审什么

- **只审改动**：diff / commit / branch 模式下只审本次改动行及其上下文，**不审未改动的既有代码**；`all` 模式下才做全量基线
- **缺陷优先**：同一严重度内先报「会出错的」（逻辑错、边界漏、吞异常、密钥泄漏），再报「不合规但能跑的」（命名、体积、一致性）——别让规范偏离淹没缺陷
- **有把握才报**：要断言是缺陷，须能说清触发它的现实场景；说不清就先用工具查证（读调用方、看同类实现、跑测试）；仍不能确定的一律移入报告 `## 提示` 段，不列为违规
- **不报个人偏好**：风格偏好、可改可不改的写法不进违规清单
- **不臆测假想问题**：边界情况确实重要时才提，且必须给出它现实中断裂的场景，不写「万一 X 就会 Y」这类无依据的担忧

### 怎么写（每条评论的结构契约）

每条**第一行是结论标题**——「一句话说清是什么问题 — `文件:行`」，正文再按 **为什么是问题 → 什么条件下会出现（场景）→ 怎么改（修法）** 展开。要求：

- **先结论后展开**：标题行必须能独立读懂，扫一遍标题即可掌握全部问题
- **自足**：读者不必细读上下文就能看懂这一条；不写「同上」「参见上文」
- **条件前置**：把严重度依赖的条件（输入、数据规模、并发、权限、环境）写进「场景：」
- **不就高**：不把 Medium 说成 Critical；定级依据落在「规则来源」，不靠形容词撑
- **能改就给改法**：「修法：」给具体动作或代码片段，不写「建议优化」这类空话

### 语气

- **就事论事**：不指责、不过度正面，像助手在提修改建议
- **不奉承**：禁「做得不错」「感谢配合」这类无信息量的话
- **简洁**：一句话能说清就不写两句；不重复文件名、不复述规则原文

## 汇总报告格式

### 严重度分级标准（客观判据，勿靠感觉）

- 🔴 **严重**：安全 / 数据完整性问题（密钥或凭据泄漏、信任矩阵被放宽、绕过工具闸门、会话文件被非追加改写、脱敏缺失）
- 🟠 **高**：破坏硬规则（依赖方向、协议声明/授予混一、版本静默降级、`exports` 条件顺序致 dev-src 死分支、日志污染 stdout）或**基线失败**（`pnpm check` / 两条验收不绿）
- 🟡 **中**：命名 / 类型 / 代码体积超标、协议或数据层语义不严（缺对账、缺轮询兜底）、真实一致性漂移（同源两种写法）
- 🔵 **低**：风格 / 注释 / 文档 / 纯凝练

### 报告结构

```markdown
已审查 <范围：mode + 口径 + 文件数>（<改动主题，按模块列举>）。<基线：pnpm check / 两条验收 结果>。<未发现阻断性 bug / 发现 N 个问题，多为……>

## 严重
1. <一句话结论> — path/to/file.ts:42
   <为什么是问题；自足，不必细读上下文>
   场景：<什么输入 / 并发 / 权限 / 环境才会出现>
   修法：<具体动作或代码片段>

## 高
## 中
## 低
（同「严重」：`序号. 结论 — 文件:行` + 正文 + 场景 + 修法；本批无该档时整节省略）

## 提示
<有疑虑但未断言、或改动面大 / 值近零的可选优化；编号接续，注明「非必修」>

## 确认无误
- <已核对正确的实现，逐条一句话 + 出处>
```

要求：

- **开头一句话**收口范围、基线与总体结论；范围契约与覆盖率账本**仅在出现降级 / skipped / 敏感文件告警时**另起短节详述。
- **每条先结论后展开**：首行「一句话结论 — `文件:行`」，读者只看首行即可抓住全部问题。
- **不用表格、不写空壳小节**：某档无内容时整节省略；同一文件多条合并成一块。
- **`确认无误` 必出**：逐条列出本批已核对正确的实现（信任矩阵、密钥单向性、脱敏、门禁登记、复用等）。
- **破坏性变更**单起 `## 破坏性变更（下游需同步）`（置于 `## 严重` 之前），逐条写 `旧 → 新` 与谁需要同步；无则整节省略。
- 存在运行时 / 渲染行为面改动时，在开头句末点明需哪种验证（真实模型冒烟 / pty 冒烟 / 浏览器冒烟 / 重建前端产物）及范围。

## 输出要求

直接输出报告，无需客套寒暄，全程用简体中文，按上节「报告结构」书写。硬要求：

1. **先结论后依据**：首行给结论与位置，再写为什么、场景、修法；同严重度内先报会出错的、再报不合规但能跑的。
2. **`确认无误` 不可省**：逐条列出已核对正确的实现。
3. **无信息量的话不写**：不奉承、不复述规则原文、不重复文件名。

## 一致性 · Style Guide（SSOT）

### 命名
- 文件与目录一律 `kebab-case`（本仓不采用 PascalCase 文件名）；包内按功能域成目录、`<域>/index.ts` 统一导出；纯函数视图/格式层用可辨识后缀（`view.ts` / `*-format.ts`）
- 组件与类型 `PascalCase`；组件 Props **必须** `XxxProps`（禁裸 `Props`）；布尔 `is` / `has` / `should`；回调 `onXxx`（对外）/ `handleXxx`（内部）；Hook `useXxx`；常量 `SCREAMING_SNAKE_CASE`；类私有字段 `#xxx`
- 动词成体系、同类同词（`create` / `read` / `write` / `list` / `load` / `parse` / `build` / `describe` / `summarize` / `format` / `resolve` / `remove` / `delete` / `find` / `add` / `is*` / `to*` / `can*` / `has*`）；同一动作不混用 `get` / `fetch` / `query` 表同一件事；协议命令名小写点分；协议与数据层类型名与线格式一致

### 分层
- 依赖单向 `apps/* → ui → sdk → bindings/* → protocol`；`core → store → data-layer-spec`；bindings 不依赖 core；sdk 不引 ui、不假设 DOM；ui 不引 apps
- 协议 C 类型只从 `@ucode/protocol`（壳经 sdk 转发类型）；传输走 `@ucode/sdk/<transport>` 子路径
- 数据层只经 `@ucode/store`；核心层不直读写会话文件

### 品牌
- 产品标识一律 `@ucode/branding`（`getBrand()` / `defaultDataDirName()` / `envVar()`）；源码零字面量；B 端定制 = 换 `brand.json` + `assets/` 重构建

### 协议与信任
- 能力声明与授予分离；版本双向校验、不静默降级；信任由绑定声明；自主级别门槛生效；新增命令登记 schema + `COMMAND_CAPABILITIES`

### 状态
- 前端选择器不返回新建对象/数组（用 `useMemo`）；状态用 zustand vanilla store；展示逻辑抽纯函数

### 安全
- 密钥只写本地文件、回读形状不含明文；SSH 注册表不存密钥；hooks 只从数据层读；支持包导出脱敏；OS 凭据加密不可用拒存；读取过滤符号链接

### 错误处理
- 拒绝给可诊断原因；不得静默吞错；"无可用模型"等状态必须显式可见；有副作用操作先预检

### 日志
- **stdout 归协议通道**（stdio 下日志走 stderr）；过程性用 `debug`、里程碑才 `info`；不写密钥

### 注释与文档
- 注释 / 文档 / 页面文字 / git commit 均用简体中文；函数体注释只写代码无法表达的信息（意图/规则/约束/反直觉理由），严禁复述代码本身
- TS 类型字段注释从宽；文件级注释概述职责、不复述文件名；导出 API 与反直觉实现需说明意图与边界；不用 `// ═══ xxx ═══` 横幅分段

## 注意事项

- **默认只审改动**；`all` / `全部` 才全量。收窄或全量都在报告开头声明，勿混淆。
- **先跑自动化基线，再手动审语义**：命令开头先执行 `pnpm check`。**真门禁项不重复手扫**（见第 2 步表）；反向也成立——**表里未列的项不要假定有门禁**（尤其非源码文件的品牌字面量、`exports` 条件顺序、密钥外泄路径、协议语义）。
- **门禁是"允许列表"不是"禁止列表"**：新增包只声明依赖不够，必须登记 `boundaries.json`；门禁自测须同步。
- **一致性发现做成本/收益过滤**：改动面大、值近零、或破坏原语义意图的，降为报告 `## 提示` 段，不列入违规。
- **每条违规引用具体规则来源**（AGENTS.md 章节 / spec §n / impl I-n）；同源偏离归并后标注影响面；只报「真实不一致」，不报「个人偏好」。
- 审查基于 AGENTS.md 与 `docs/` 规则，**以现有代码为准**（代码与文档不一致以代码为准，并报出该不一致）。
- 本规范聚合分层 / 品牌 / 协议 / 数据层 / 安全 / 控制层 / 测试 / 命名 / 注释 / 错误处理 / 日志各维度扫描，是唯一审查入口。
